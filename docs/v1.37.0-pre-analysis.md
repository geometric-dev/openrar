# v1.37.0 Pre-Analysis — Intra-Entry Parallel Decode Driver (Gate 0)

Arc inputs: `docs/ROADMAP.md` v1.37.0 entry, `docs/question-log.md` Entry 8
(the slot model, black-box), `docs/v1.34.0-implementation-plan.md` §3 (the
mandatory measurement protocol), `docs/v1.34.0-pre-analysis.md` (baseline:
extraction ~2x behind UnRAR, decode = 84% of it, `-mt8` does nothing on
single members).

## 0. The window-half question — answered

**The question.** A block's matches reference window bytes that a
neighbouring worker may not yet have produced. Any intra-entry parallel
decode design must say how those references resolve. The ROADMAP forbade
decoder code until Gate 0 answers this.

**New black-box evidence (this session, Rar.exe 7.20, 2C/4T host,
alternating-order interleaved runs, min-statistic per v1.34 §3).**

| member | blocks (512 KiB) | mt1 | mt4 scale | mt8 scale |
|---|---|---|---|---|
| 2 MiB text (2 MiB dict) | 4 | 0.085 s | 0.95x | 0.95x |
| 8 MiB text | 16 | 0.126 s | 1.10x | 1.05x |
| 16 MiB text | 32 | 0.172 s | 1.08x | 1.08x |
| 64 MiB text | 128 | 0.457 s | 1.29x | 1.30x |
| 64 MiB text (128 MiB dict) | 128 | 0.647 s | 1.33x | 1.50x |
| 64 MiB zeros (2.8 KB archive) | 128 | 0.210 s | — | 1.07x |

Three findings:

1. **Scaling tracks member length, not block count.** A 4-block member does
   not scale at all; a 128-block member scales 1.29x. If work units were
   blocks, 16 blocks would saturate 4 workers — they don't. The reference
   splits members into ~threads contiguous ranges and amortizes fixed
   per-range costs over range length.
2. **The parallelized work is the decode itself.** Real text scales
   1.28–1.50x; the overhead-dominated zeros control does not. Whatever the
   reference overlaps, it is not table building or CRC alone — with our
   measured table-build cost (~7 us per 512 KiB block vs ~9 ms block decode)
   a table pipeline would cap at ~0.1%.
3. **Bigger dictionaries scale better** (1.28x @ 2 MiB dict vs 1.50x @
   128 MiB dict). Snapshot-copy-per-range would predict the opposite
   (snapshot cost grows with dict). Conclusion: the reference does not copy
   window snapshots; its ranges most plausibly decode concurrently into a
   shared window/coordinate space and resolve cross-range references by
   waiting on producer progress or by deferred patching. That is the
   reference's choice — it constrains what we must INTEROPERATE WITH
   (nothing: the design is decoder-internal), not what we must build.

**The design answer (ours) — revised after the Gate 0 review.** The
originally proposed per-range window snapshots are **unimplementable
concurrently**: the snapshot for range k is the decoded output of ranges
0..k−1, which does not exist when worker k starts (a wavefront is a serial
chain; a primer decode of the first dict bytes serves only the first
range). The evidence had already pointed away from snapshots (bigger dicts
scale better), and the arithmetic confirms why: at absolute position p a
match satisfies `dist ≤ p` and `dist ≤ dict`, so `p − dist ≥ max(0, p −
dict)` — **a shared pre-transform output buffer indexed from absolute
position 0 needs no snapshot machinery at all.**

- The entry's output buffer (pre-transform bytes, absolute coordinates) is
  allocated up front, sized `min(dest_size, gate budget)`. Ranges decode
  concurrently into disjoint absolute regions; a match copy at p reads
  `output[p − dist .. p)` directly — those bytes are either the worker's
  own (already written, sequential within the range) or another range's,
  in which case the worker **waits on that range's frontier** (condition
  variable per range; predicate: `p − dist < frontier(producer)`).
- Deadlock-freedom is structural: references are strictly backward
  (`dist ≥ 1`), ranges are processed by ordered producers, so the wait
  graph is acyclic. On hostile all-cross-range streams the design
  degenerates toward serial — never deadlocks, never corrupts. On real
  data cross-range matches are rare (distances cluster small), so workers
  run nearly independently.
- The window IS the output buffer: no ring, no per-worker window copies,
  no lag bounds. The pre-transform/post-transform split that the decoder
  already maintains (filter regions are extracted from the window without
  modifying it) maps directly: workers emit pre-transform bytes into the
  buffer and RECORD filter applications; filters are applied in order over
  the buffer post-join, in absolute coordinates (the v1.21.1 frame rule);
  the final consumer sees post-transform bytes exactly as the sequential
  path emits them.
- Table state per range comes from the description-tracking pre-scan
  (unchanged). CRC32/BLAKE2sp verification runs on the post-transform
  output exactly as today.
- For solid chains, cross-entry references resolve via the carried window
  of the in-order predecessors — the one place a legitimate "snapshot"
  remains: predecessor entries are fully decoded before the entry starts
  (concurrency-safe by the existing solid ordering).

## 1. Gating rules (when intra-entry MT engages)

All must hold; otherwise the sequential path runs (bit-identical, unchanged):

- G1 `-mtN` with N ≥ 2 requested (default-thread decision and kill switch
  pinned in the plan per review directive 9), AND the entry is a single
  file member (not split across volumes; solid chains are fine — cross-entry
  references resolve via the in-order predecessors' carried window).
- G2 algorithm version 0 (RAR5 stream), method 1–5; stored (method 0)
  members stay on the stored path.
- G3 member packed size ≥ `workers × 4 MiB` (amortization floor; below it
  the measured reference scaling is ≤ 1.1x anyway).
- G4 the pre-scan completes cleanly (every block header checksum-verified,
  descriptions parse, member ends where the scan says); any anomaly →
  sequential fallback. The pre-scan is a READER, never a trust boundary:
  all validation that the sequential decoder applies still applies.
- G5 `dest_size ≤ PARALLEL_DECODE_BUDGET` — the shared pre-transform buffer
  is O(dest_size), so a huge or bomb-class dest_size falls back to the
  streaming sequential decoder (budget: 1 GiB native; WASM never engages —
  G6). Extraction byte-caps debit unchanged.
- G6 WASM/ILP32 runtimes never engage the driver (single-threaded product
  surface; `should_use_parallel_decode` answers false unconditionally).

## 2. Alternatives considered and rejected

- **Per-range private window snapshots (the original proposal).** Rejected
  by the Gate 0 review: the snapshot for range k is the decoded output of
  ranges 0..k−1 — a concurrent-start dependency that does not resolve
  (wavefront = serial chain; a primer serves only the first range). See §0.
- **Faithful slot-model pipeline (round-robin tables built ahead, serial
  decode).** Rejected by measurement: the parallelizable fraction
  (table build ~0.1%, CRC ~1%) caps the win at ~1.02x on real data. The
  slot model documents TABLE-state semantics for INTEROPERABILITY, not a
  parallelization strategy.
- **Per-block work units.** Rejected by measurement (finding 1): scaling
  tracks member length, not block count; block granularity both
  over-synchronizes (each block's first match may reference its
  predecessor) and under-amortizes per-unit costs.
- **Per-worker ring windows with dict-bounded lag.** Equivalent concurrency
  to the chosen design but strictly more machinery (ring arithmetic per
  worker, lag coordination) for no gain at the gated budget; the shared
  absolute-coordinate buffer subsumes it. The reference's own mechanism is
  unknown — ours is not required to match it, only the wire does.

## 3. Security posture (normative)

- The pre-scan adds a parse-only pass over untrusted bytes. It runs the
  SAME header reader and description parser the sequential decoder uses, in
  the same sandboxed-worker context (v1.30 §5.1); it allocates nothing
  proportional to attacker-controlled counts except the existing per-block
  bounds (vint caps, 2 MiB header ceiling, D/NR-style caps).
- Workers are pure functions of (range bytes, snapshot, table state) →
  output bytes + recorded filter applications. No shared mutable state
  during decode; the merge is the single writer. A hostile stream that
  desyncs a worker fails that worker's validation → the whole entry fails
  exactly as a sequential decode would (fail-closed), never partially
  extracted.
- The sequential decoder remains the default for every non-gated case and
  the fallback for every anomaly. Extraction containment, journaling,
  atomicity (v1.24) are untouched — the driver changes WHO computes the
  bytes, not how they reach disk.
- Fuzz/attack corpus: the MT path must survive the existing corpus
  (CVE-2025-8088/2023-38831/2023-40477 classes, bombs, hostile vints) and
  differential-vs-UnRAR, plus new MT-vs-ST byte-identity fuzzing.

## 4. FMM summary (full rows in the implementation plan)

| # | Failure | Behavior |
|---|---|---|
| F1 | Pre-scan anomaly (bad header CRC, description overrun, size mismatch) | Sequential fallback |
| F2 | Worker output length ≠ range length | Entry fails (fail-closed), no partial extract |
| F3 | Worker throws/aborts (OOM, bad_alloc) | Entry fails; fallback to sequential retry only if deterministic-safe |
| F4 | Filter application crosses range boundary | Applied in order post-merge (absolute positions) — by design, not an error |
| F5 | Gating rule not met | Sequential path, byte-identical behavior |
| F6 | Table state at range start wrong (pre-scan bug) | Caught by MT/ST byte-identity gate + fuzz; fail-closed at merge validation |
| F7 | `-mt1` or single-threaded build | Sequential path |

## 5. Named tests (expanded in the implementation plan)

- T-UNIT-1: MT/ST byte-identity across the whole interop corpus and the
  fuzz corpus (the bit-exactness gate, decoder side).
- T-UNIT-2: gating rules (each rule individually forces the sequential
  path; observable via a reported flag, not behavior guessing).
- T-UNIT-3: F1/F2 rows — crafted anomalies fall back / fail closed.
- T-UNIT-4: solid-chain + filter-spanning members decode MT byte-identical
  (the v1.21.1 cross-boundary filter corpus).
- T-ORACLE: reference archives (Rar 7.20-produced, incl. RR, QO, solid,
  multivolume) extract byte-identical under `-mtN` N∈{1..8} vs sequential.

## 6. Measurement plan (the claim protocol)

Paired deltas, min-statistic, alternating order, wiped `build/rel` binaries,
single session (v1.34 §3). Claim shape: intra-entry decode-bound extraction
(text member, `-mt4`/`-mt8` vs sequential) with the hardware disclosure, plus
the honest no-regression rows (small members, stored, multivolume, `-mt1`).
The roadmap's prediction (1.15–1.35x) stands as the floor claim; snapshots
may exceed it on this host — measure, don't promise.

## 7. Scope

Decoder-side driver + pre-scan + merge + gating + tests. NOT in scope:
encoder changes (none), kernel changes (v1.38), CLI surface changes beyond
honoring the existing `-mt` on single members, stored-path or durability
changes.
