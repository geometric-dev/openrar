# v1.38.0 Pre-Analysis — Decode Kernel Rework (Gate 0)

Arc inputs: ROADMAP v1.38.0 ("flat tables / SIMD"), `docs/v1.34.0-implementation-plan.md`
(the measured-negative that scoped this arc, its §3 measurement protocol, and the
flat-table build-cost trap claim), `docs/v1.37.0-design-wall.md` §3/§4 (the kernel
rework does not hit the two-phase wall), and the v1.37.0 two-phase plan M4 record
(the apply-floor model this arc's numbers feed back into). Measurement protocol:
v1.34 §3 (paired deltas, min-of-N, alternating order, wiped configure directories,
single session) — every number below is from one session on the fresh v1.37.4
Release build (2C/4T i7-7500U) unless labeled otherwise.

**Provenance.** Two consultations with outside format/hardware analysis are
recorded here (impersonal: "outside analysis" / "independent format
verification"): a hardware-acceleration rundown for the decode pipeline (§5),
and a validation of the format assumptions the flat-table design rested on (§4).
Probes, variants, and measurements are ours (§1/§2).

## 0. The founding premise — tested and refuted

The roadmap's v1.38 prediction: single-lookup 15-bit flat Huffman tables with
lazy second-level pages give ~1.2–1.4x on decode-bound extraction, and a SIMD
decode kernel targets 1.5–2x on the kernel (highest-risk item). The premise
chain: the kernel carries 84% of decode; the kernel is ~1.7x behind the
reference; v1.34 proved call-pattern changes exhausted, so the lookup structure
must be the gap.

**The premise is measured false on this host.** The shipped 10-bit quick table +
canonical slow path beats every flat variant on the symbol-decode hot path —
not by a little, and monotonically in primary-table size:

| variant | text m3 | text m1 | exelike m3 | random m3 |
|---|---:|---:|---:|---:|
| VQuick (shipped structure, replica) | **94.1** | **108.9** | **142.3** | **123.6** |
| VFused (single peek(15)) | 99.5 | 114.9 | 151.7 | 136.5 |
| VFlatLazy PB=10 (primary + lazy pages) | 116.4 | 135.8 | 207.1 | 184.9 |
| VFlatLazy PB=11 | 121.5 | 142.3 | 227.1 | 200.3 |
| VFlatLazy PB=12 | 130.3 | 154.6 | 254.2 | 231.1 |
| VFlatLazy PB=13 | 152.3 | 176.7 | 313.8 | 303.9 |
| VFullFlat (single-lookup 15-bit) | 131.7 | 158.0 | 167.2 | 156.0 |

(units: ms per 16 MiB member, symbol stage only; all rows hash-verified
against the real kernel's token stream in the same session)

The mechanism is cache, not branches: the shipped structure keeps its hot data
in 4 KiB per alphabet (L1-resident); every flat variant trades the rare
canonical walk (1–4 predictable iterations over an L1-hot 64-byte array) for a
wider, colder primary and — for lazy pages — a second dependent load. The
single-lookup full-flat table is 17–45% slower across corpora (best on
match-dense exelike, worst on text m1). A
SIMD dispatch layer (gather/dual-speculative) sits on top of the same tables
and the same serial chain — outside analysis concurs it is a trap (§5), and the
flat measurements reinforce it: anything that grows the table working set loses.

This is the v1.34 pattern repeating at the algorithmic level: the shipped
decode kernel is at a genuine local optimum for its structure, and the roadmap's
remaining gap to the reference class does not live in the Huffman lookup.

## 1. The probe (`tools/decode_kernel_probe.cpp`, + `decode_kernel_probe.inc`)

A non-test probe binary (tokencensus precedent) that:
- compresses in-memory corpora with the in-repo encoder (text m1/m3, exelike
  m3, zeros m3, random m3 — 16 MiB each), pre-scans, and times the real symbol
  stage (`decode_span` over the whole member) and full sequential decode;
- runs hash-verified A/B: a replica token loop (BitReader replica, canonical
  tables replica, `slot_to_length`/filter-data replicas) whose token-stream
  hash must equal the real kernel's `decode_span` record hash for the member —
  **every variant row is only counted when its hash matches the anchor**;
- sweeps lookup variants against the same bitstreams: shipped-structure
  replica, fused single-peek, lazy-page flat tables (PB 10–13), full 15-bit
  flat; a 32768-value table-resolution self-check per description per alphabet;
- measures per-table-set build cost through the real
  `initialize_from_description` and through replica builds;
- decomposes record-emission cost (shipped vs warm-buffered `decode_span` vs
  no-record replica) and apply-stage kernels (filter-region extraction, delta).

Probe-development notes (kept for honesty): the first probe revision measured
nonsense because its loop bound mixed absolute member bit positions with
block-relative reader positions — blocks 1+ decoded past their end into the
next block's header bytes as garbage tokens (6–10x slowdowns, hash
mismatches). The blockwise divergence finder (`decode_kernel_debug.cpp`,
diagnostic-only, not built by the default target) traced both decoders
token-by-token and pinned the frame bug; after the fix, every variant row
reproduces the real kernel's token hash on every corpus, and the VFlatLazy
direct-fill base shift (`code >> 16` → `code >> (16 - l)`) was caught by the
32768-value self-check the same way. Two observations about our own encoder
fell out: blocks carry exactly 2^15 tokens at m1/m3 (a token-count budget in
the block builder), and every text m3 block re-emits its table description
(94/94, 104/104) while zeros re-emits on 17/32 and random on 383/512.

## 2. What the kernel time actually is (current v1.37.4 build)

Corpus composition (16 MiB members, m3 unless noted, min-of-7; the no-record
replica row doubles as the session-drift control for cross-build
comparisons — it is untouched code and measured flat across every build):

| corpus | blocks (desc) | symbol-only | decode_span (sym + records) | sequential |
|---|---|---|---:|---:|
| text m3 | 94 (94) | 94.1 ms | 148.0 ms | 148.5 ms |
| text m1 | 104 (104) | 108.9 ms | 157.8 ms | 170.1 ms |
| exelike m3 | 396 (396) | 142.3 ms | 216.1 ms | 411-551 ms (high var; stabilized 413.5) |
| zeros m3 | 32 (17) | 0.14 ms | 0.16 ms | 6.4 ms |
| random m3 (stored) | 512 (383) | 123.6 ms | 195.3 ms | 158.2 ms |

Sequential-exelike variance note: the same binary reads 411-551 ms across
runs (match-dense content, thermal/cache state); stabilized readings are
the second and later runs of a fresh build. Cross-build comparisons use the
replica row as the drift control and stabilized readings only.

Decomposition on text m3: symbols ≈ 94 ms; **record building ≈ 54 ms (36% of
the phase-1 span)**; window apply + flush + callback ≈ 54 ms (36% of
sequential). On exelike m3 the apply stage is 195 ms (47% of sequential) —
filter regions + match-dense copies. On zeros the kernel is header-bound
(0.16 ms of symbols in a 6.4 ms sequential — flush cadence and callback
overhead dominate trivial streams).

Record-emission split (text m3): shipped `decode_span` 146.6 ms → with warm
(pre-reserved) record buffers 128.8 ms → no-record replica 94.0 ms. So
allocation/growth costs ~18 ms per span in the current driver — and the driver
creates a **fresh `SpanRecords` per span per worker**
(`parallel_decode.cpp` `worker_body`), so production pays the cold number;
the remaining ~35 ms is the per-token record machinery itself (per-byte
`lit_pool.push_back`, per-token `rec_bytes()` cap lambda, `close_run`
bookkeeping). A 2 MB push_back-vs-bulk-insert micro-bench measures 3.24 ms →
1.66 ms for the literal pool portion.

Apply-stage kernels: the filter-region extraction in `flush_pending` reads the
region out of the ring **one byte per iteration**; two memcpys do the same
region 24x faster (0.849 → 0.035 ms per MiB, memcmp-equal). The delta filter's
scalar ch>1 path measures 0.60 ms/MiB (ch=1 already SSE2; E8/E8E9/ARM already
SSE2+NEON since the v1.22 line) — the remaining delta ceiling is < 0.5 ms/MiB
even at 4x, on content that rarely carries it.

## 3. The rebuild-trap arithmetic — corrected

`docs/v1.34.0-implementation-plan.md` §4 projected the naive flat table at
"~131K writes per block build" ≈ +0.3–0.5 s per 64 MiB member (implying
~1–5 ns per span-fill write). Measured: a full 4×32768 span fill costs
**24.8 µs per table-set rebuild** (0.19 ns/write — sequential broadcast
stores are far cheaper than assumed) against the shipped build's 10.1 µs —
a +14.7 µs delta, ≈ **+5.6 ms per 64 MiB m3 member** (~380 rebuilds). The
trap is ~30x smaller than recorded and was never the binding constraint; the
lookup deficit (§0) is. The lazy-page build in the probe (47–530 µs) is
dominated by `std::vector<std::vector>` bucket churn — a production build
would use flat arrays — but no build-side improvement rescues a lookup that
starts 24% behind even at its best configuration (PB=10, text m3). Hostile
sparse tables: the shipped build path costs
6.5 µs/rebuild and stays O(symbols); any flat replacement must preserve that
(the lazy-page hostile probe measured 11.1 µs at PB=10 including 64 decodes
through materialized pages — no trap, but no win either).

## 4. Format validation (independent format verification)

The flat-table design rested on equivalence claims about the shipped canonical
decoder; they were validated item-by-item, with two corrections that matter
for any future table work:

1. **Covered-peek equivalence — exact.** For any 15-bit peek v covered by a
   code, "smallest i in 1..15 with (v<<1)&0xFFFE < decode_len_[i]" is the
   covering code's length, and the walk's index arithmetic recovers
   `decode_num_[decode_pos_[i] + w]`. The shipped scan starting at
   i = QUICK_BITS+1 is equivalent to a full scan (empty classes produce
   decode_len_[i] == decode_len_[i-1] and cannot false-hit).
2. **Uncovered peeks — NOT a single fallback symbol; per-v.** With
   T = total code count and upper_15 the covered-region end, an uncovered v
   lands at pos = T + (v − upper_15): for v < upper_15 + (max_num − T) the
   walk returns **symbol 0** (decode_num_'s zeroed tail), not decode_num_[0];
   only v beyond that band clamps to decode_num_[0]. Observable only on
   incomplete (hostile/corrupt) tables. Any flat fill must reproduce the
   two-band behavior per v; the probe's replica does (hash-verified on the
   zeros corpora's sparse tables).
3. **Over-subscription — skip, never wrap.** Over-subscribed symbols (first +
   index ≥ 2^len) have empty peek intervals; the mechanism is that
   decode_len_[i] merely exceeds 16 bits (decode_len_ must stay ≥17-bit
   arithmetic — ours is uint32), not saturation or wrap. A flat fill that
   masks or wraps the code value would alias over-subscribed codes onto low
   peek indexes: skip the symbol, fill nothing.
4. **Length cap 15 — confirmed.** Both wire length sources (the BD nibble
   prefix with its 15/zero-run escape, and the BC-coded length stream with its
   four escapes 16–19) cap at 15; no 16-bit codes exist; a 15-bit peek
   resolves everything. The 446-entry RAR7 extra-dist flavor uses the same
   coding (matches our use_extra_dist_/cur_table_size_ model).
5. **Table cadence — unconstrained.** Any block may carry a description; cost
   is bits only. Frequent per-block descriptions (our encoder's shape) are a
   legal, data-driven choice, which is why per-rebuild build cost matters at
   all.
6. **BlockBitSize / Entry 23 — the concern dissolves; recorded as a non-goal
   with a corrected model.** Outside format verification corrected the Entry
   4/23 reading: the reference discipline is a **token-start check** — decode
   a token iff the current bit position is strictly before the declared
   block-bit end; a started token runs to completion; the next header aligns
   up from wherever the stream sits. That is exactly what our decoder does
   (`block_end_bit` + `cur_bit() >= end_bit` gate). The Entry 4 corruption
   experiment is re-explained without byte-boundary semantics: those padding
   bits sat **inside** a declared BlockBitSize=8 region — token payload by
   definition, decoded identically by both readers. Switching to a
   byte-boundary reader is strictly negative (it would mass-corrupt the
   838/954 WinRAR blocks declaring 1–7 whenever a zero tail completes a
   short code). `docs/question-log.md` gains an entry recording the corrected
   model; no decoder change ships.

## 5. Hardware-acceleration rundown (outside analysis; the arc's SIMD question)

Per decode stage, with expected magnitudes and traps — the full record lives in
the arc's review notes; the load-bearing conclusions:

- **Bit reader (BMI1/BMI2 BEXTR/SHRX/BZHI):** 3–8% class, near-zero risk;
  PDEP/PEXT are a trap for MSB-first streams (and microcoded on Zen1/2).
- **Huffman dispatch:** scalar flat/two-level tables plus cache design is what
  the fast third-party decompressors do; SIMD dispatch (VGATHERDD,
  dual/speculative decode, GFNI) does not break the serial dependency chain —
  not recommended; our measurements agree (§0).
- **Window copy:** ERMS `rep movsb` for dist ≥ len (already ours via memcpy),
  vector doubling for dist < 32 overlaps (already ours via the wildcopy
  expansion), no non-temporal stores, over-allocate/tail-guard vector paths.
- **Filters:** E8/E8E9 + ARM already SSE2+NEON in-tree (scan vectorized,
  skip-5 preserved, per-hit fix scalar); delta ch=1 already SSE2 prefix-sum.
  The one remaining data-parallel piece — delta ch 2..32 row-subtract —
  ceilings at < 0.5 ms/MiB on rare content.
- **CRC:** PCLMUL folding shipped since v1.30; AVX-512 variant and cross-chunk
  recombination are the only remaining moves (the two-phase CRC is already
  off the decode path).
- **wasm32:** no carry-less multiply, no gather, no AES/SHA — scalar stays;
  per docs/versioning.md the wasm baseline degrades gracefully and SIMD decode
  paths must compile out (they do — they never existed in this arc).

## 6. The re-scoped arc (predictions stated before implementation)

The measured levers, in the order they will be implemented and verified:

- **M1 — phase-1 record-emission slimming** (two-phase workers):
  per-worker `SpanRecords` reuse across spans (the driver currently allocates
  a fresh set per span; `decode_span` is capacity-preserving by contract),
  pre-reserve from the existing G5 bound, bulk literal-run emission (stack
  run buffer + single insert per run), hoisted record-cap counter.
  *Prediction:* span decode −12–15% on literal-heavy members (measured
  components: −12% warm-vs-cold, −2–3% bulk runs + cap hoist); end-to-end at
  `-mt4` on this 2C/4T host ~neutral (the apply floor binds — v1.37.0 plan
  M4), with the win growing on ≥4-core hosts where the symbol stage is the
  wall. Records stay byte-identical (the `two_phase_span_records` identity
  harness pins it).
- **M2a — apply-stage filter-queue cursor**: replace the
  `filters_.erase(filters_.begin())` queue discipline (one O(pending) shift
  per consumed region) with a head cursor compacted once per flush call.
  *Prediction:* neutral at the measured scale (~16 pending regions on
  exelike m3); principled O(n²)→O(n) on many-region members; queue
  semantics (.empty()/.back()/bounds) preserved by compacting at the end of
  each flush call.
- **M2b — filter-region extraction memcpys: measured negative, declined.**
  The wrap-split two-memcpy region read (24x on the isolated micro-bench,
  memcmp-equal) measured **+16% end-to-end on exelike m3 sequential**
  (413.5 → 479.7 ms stabilized readings; the per-byte walk restored,
  cursor-only build reads 410.5/414.6). The isolated win inverts in the
  integrated loop — the same cache-state lesson as the flat tables (§0):
  the region read is the hot path's neighbor, and flooding it costs more
  than the copy saves. Recorded so nobody re-applies the micro-bench's
  verdict.
- **M3 — declined, with measurements**: flat tables (§0), SIMD dispatch (§0,
  §5), delta ch>1 vectorization (<0.5 ms/MiB ceiling on rare content), BMI2
  bit reader (3–8% class on a security-relevant surface; deferred to its own
  measured micro-arc if ever scheduled — not folded into this one blind).
- **M4 — measurement + docs**: paired-delta protocol rows for M1/M2; section H
  re-record (fresh v1.37.4 baselines already captured this session);
  two-phase ratios re-measured with the slimmed workers; pack-side rows must
  stay byte-identical (encoder untouched — the free regression signal).

## 7. Security posture

The shipped HuffmanDecoder — including its bounds behavior, Kraft-tolerant
build, over-subscription semantics, and hostile-table surface — ships
**unchanged**. M1/M2 touch data movement (record pools, ring reads), not
validation: every sequential check (rep sentinel, distance window, filter
overlap/length/budget/count) runs verbatim; the MT-vs-ST differential fuzzer,
hostile-table unit rows, and the attack corpus gate the changes. The
per-worker buffer reuse keeps the resident-memory bound of review R4 (each
worker holds at most its current span plus the publish window); no new
allocation class is introduced.

## 8. Scope

In: M1, M2, the question-log Entry 23 disposition (non-goal + corrected

HuffmanDecoder/BitReader semantics, the encoder, the two-phase driver's

## 9. RAM invariant note (docs/invariants.md §2)

Extraction memory stays O(dictionary window + slice buffers): no
table-memory delta exists (flat tables rejected; the shipped decoder's table
footprint is 4 KiB quick tables + ~2 KiB canonical arrays per alphabet, per
decoder instance, unchanged). M1's buffer reuse trades per-span allocation
churn for per-worker steady-state buffers already bounded by the R4
publish-window analysis — peak resident memory is unchanged or lower.
