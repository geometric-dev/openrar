# v1.29.0 Pre-Analysis — Archive Migration & Transcoder, Phase 1: ZIP / TAR / GZIP (Gate 0 Review)

**Status:** pre-implementation analysis for the v1.29.0 arc, submitted for
architect-challenge (Gate 0 per docs/ROADMAP.md §v1.29.0 and Guiding
Principle 2). This document deliberately argues BOTH sides before
committing to a scope. Written against the v1.28.0 baseline
(tag v1.28.0 @ 08089ec); every current-state claim below was verified in
this worktree this session.

**Flagship claims under scrutiny:**

1. **v1.29.0 adds a new PARSED-byte surface and ZERO new emission code.**
   Four new readers (ZIP, TAR, GZIP, legacy RAR 1.5–4) consume foreign
   bytes. The RAR 5.0 output of the new `cv` command is produced ENTIRELY
   by the shipped writer pipeline (`prepare_add_file`/`write_batch_add`) —
   the arc must not touch `src/format/` at all, nor any byte-emission path.
   The interop gate (17 stages) + golden bytes must stay green UNCHANGED;
   the `FHEXTRA_XATTR`/0x08 record set shipped in v1.27.0 stays CLOSED.
2. **ZIP reader hardening is a release gate** (SECURITY_ARCHITECTURE §2.1
   normative): Central-Directory vs Local-Header metadata mismatch (names,
   sizes, methods, offsets, flags) → structural-integrity abort BEFORE any
   output byte exists — not best-effort reconciliation.
3. **Foreign-format legality is argued per spec** (ZIP: APPNOTE.TXT
   structure + the CD/LF invariant; TAR: POSIX ustar + a documented
   GNU/pax subset; GZIP: RFC 1951/1952; legacy RAR: public-knowledge
   documentation of the 1.5–4.0 header format), each mapped onto the
   §2.1/§5.3/§3.1/§4.1/§4.4/§5.4 security constraints BEFORE design
   (§2 below), and verified against at least one oracle reader
   (WinRAR/UnRAR always; 7z/Info-ZIP availability-gated).
4. **Bit-for-bit extraction equivalence** is a per-entry contract: the
   transcoder records a strong hash (BLAKE2sp) of every source payload at
   decode time; `cv` verifies the emitted RAR5 by re-extracting and
   comparing hashes per entry. `-df` deletes the source ONLY after a
   100%-verified roundtrip.

**Normative inputs:** SECURITY_ARCHITECTURE §2.1 (ZIP CD-vs-LFH hardening),
§5.3 (legacy VM filters: not implemented, never; VM-filtered entries fail
with an explicit per-entry error), §3.1 (exit taxonomy — no new codes),
§4.1/§4.4/§5.4 (containment, name escaping, limits — apply to FOREIGN
formats with zero relaxation); docs/ROADMAP.md §v1.29.0 + Shipped Baseline
(v1.28.0 = starting point) + Risk Register item 5 (settled by THIS review

## 0. Gate 0 statement: the surface claim, stated precisely (then confirmed)

The v1.28 Gate 0 argued the ABSENCE of new bytes. The v1.29 Gate 0 argues a
SPLIT: new bytes are PARSED (a larger attack surface), no new bytes are
EMITTED by new code. Concretely:

**Must show NO hunks (the untouched-emission claim):**

- `src/format/` — the entire directory: `header_writer.cpp`,
  `header_reader.cpp`, `headers.hpp`. Foreign formats get their own
  parsers; the RAR5 record layouts, extra-area and service-header framing
  are closed (the 0x08 record set stays as shipped in v1.27.0).
- `src/archive/archive_mutator.cpp` — the byte-emission region:
  `write_batch_add` / `write_batch_add_ex` and everything below them
  (header serialization, ENDARC, atomic rename, SFX prepending). NOTE: the
  v1.28 briefing refers to "archive_writer.cpp" — the emission path in
  THIS tree is `archive_mutator.cpp` (there is no archive_writer.cpp; the
  mutator is both stage-1 prepare and stage-2 write). The diff-surface
  check therefore pins: ZERO hunks in `src/format/` AND zero hunks in the
  `write_batch_add*` region of `archive_mutator.cpp`. cv consumes
  `prepare_add_*` + `write_batch_add` as-is, through their existing public
  signatures. If a milestone needs anything else from the mutator, that is
  a Gate 0 violation by definition and must come back to the review.
- The reader's RAR5 decode paths (`archive_reader.cpp` decode/crc/containment
  logic) except the ONE sanctioned rollover change in §0.1 (FILECOPY
  materialization policy) — every other hunk there is a violation.

**Expected touched paths (the challenge confirms the actual diff against
this list):**

- NEW `src/compress/inflate.{hpp,cpp}` — RFC 1951 DEFLATE decoder, a codec
  peer beside `decompressor50` (rank 3). Clean-room; no zlib code.
- NEW `src/archive/foreign_{reader,zip,tar,gzip,legacyrar,transcode}.*` —
  foreign container readers + the cv orchestrator, as archive-layer (rank
  4) files; every include points downward (core/io/compress/crypto/format)
  — `tools/layer_check.py` needs no changes because no new subsystem
  directory is created.
- `src/cli/main.cpp` — `cv` dispatch, switch handling, output lines (all
  through the §7.1 sanitizers), `--json-summary` wiring, exit mapping.
- `src/archive/extraction_report.{hpp,cpp}` — additive cv fields on the
  existing JSON schema only (valid-UTF-8 guarantee inherited).
- `tests/unit/foreign_format_tests.cpp` (new suite), `tests/unit/transcode_tests.cpp`
  (new suite), `tests/unit/cli_tests.cpp` (cv contract tests),
  `tests/unit/compress_tests.cpp` (inflate KATs), CMakeLists.txt.
- `tools/interop_gate.py` — Tracks 11+ appended, data-driven (v1.30
  appends its stages onto our version).
- README rows, CHANGELOG, docs/spec/11-foreign-formats.md,
  docs/spec/12-legacy-rar.md (spec-first: these land BEFORE their parsers,
  per the repo's documented ground rules), ROADMAP Shipped Baseline.

**How the Gate 0 review CONFIRMS the claim rather than assumes it:**

1. diff-surface review of every milestone commit against the two lists
   above (any hunk inside the must-show-no-hunks set = violation);
2. the interop gate (17 stages, incl. Track 10 crafted-0x08 vs the UnRAR
   oracle) green UNCHANGED on every milestone — a writer regression fails
   it even without a review catch;
3. golden bytes (`tests/fixtures/golden` + `tools/check_golden.ps1`) green
   UNCHANGED;
4. NEW for this arc, because the arc makes the WRITER work harder on
   hostile inputs: a cv-vs-`a` differential control — for a staged local
   tree, `a` (direct add) and `cv` (through the transcoder) must produce
   archives whose extracted payload bytes and metadata are equivalent, so
   any accidental writer drift inside the transcode path is caught against
   the direct path. The interop gate remains the oracle-facing proof;
   this control is the regression net for the orchestrator itself.

### 0.1 Rollover dispositions (settled HERE, in §0, before design)

**1. FILECOPY default-materialization policy (deferred twice: v1.26, v1.27)
— SETTLED: default-ON, decoupled from `-ol`.** Today a `FHEXTRA_REDIR`
type-5 (FILECOPY) entry materializes only under the links opt-in (the `-oi`
README row: "materializing references on extraction follows the `-ol`
links opt-in"), and the materialization already debits the cumulative byte
caps (v1.27 §5.4 consistency, archive_reader.cpp:2615–2631). The case for
default-on: a FILECOPY record is an in-archive copy directive pointing at
another entry of the SAME archive — it is not a filesystem link, it
escapes no containment boundary (the copy lands on the entry's own
contained path; the source is resolved under the same root and
symlink-parent-checked, archive_reader.cpp:2615–2623), and the extraction
outcome is byte-identical to re-emitting the payload. Leaving it behind
`-ol` is silent data loss for `-oi`-produced archives extracted without
the switch — WinRAR materializes, so our own archives degrade on our own
extractor. The case against: it changes default extraction behavior of
shipped archives (a policy change, not just a feature), and one could
argue for strictness. Resolution: the strictness concern is already
covered where it is real — actual links (symlink/hardlink/junction,
redir types 1/2/4) remain default-deny under `-ol` untouched; FILECOPY
joins plain files. The caps debit (shipped v1.27) is the DoS boundary and
it predates this change. This arc lands the policy change with named
negative tests (plan §-pattern) and a CHANGELOG behavior-change entry —
NOT because cv requires it (Phase 1 cv reads foreign formats that have no
FILECOPY records and emits none itself — see §3 CV-B/CV-H), but because
the brief directs the policy to be settled here and the reasoning is
complete. `-ol` documentation and the `-oi` README row are updated to
match; `transcode` itself does not read or emit FILECOPY in Phase 1.

**2. RR 0x11D vintage, parallel fingerprint pass, multi-volume
no-data-area entries, macOS Gatekeeper / root-mode xattr e2e legs —
RE-DEFERRED.** None interacts with a foreign-format reader or the `cv`
pipeline (they are RAR5 recovery/mutation/bench surfaces). Each is
re-deferred in the plan's rollover ledger with this same one-line reason;
the FILECOPY item was the only rollover with transcoder interaction.

**3. C ABI: ZERO new exports in v1.29.** `cv` is a CLI command; the
foreign readers are internal archive-layer modules. The v1.30 ABI freeze
therefore covers nothing new from this arc — the strongest possible form
of "keep the C ABI minimal". DLL/WASM surface unchanged; binding negative
statement (v1.28 pattern, directive 11): **C ABI unchanged; DLL/WASM have
no transcode surface; no binding conformance test required.** The WASM
build must keep compiling and stay inside the 500 KiB budget — new
sources are wired so the wasm target either excludes them or stays under
budget (verified at release preflight; inflate is the only wasm-adjacent
addition and it is excluded from the wasm lib — the browser surface has
no foreign-format reader).

## 1. Current-state facts (verified this session, with anchors)

1. **No DEFLATE implementation exists in the tree.** src/compress holds the
   RAR5 codecs only (`compressor50`/`decompressor50`, `filters50`,
   `stream_{en,de}coder`); the only "inflate" hits are a comment in
   compress_tests.cpp. ZIP method 8 and GZIP require an RFC 1951 decoder —
   this is a NEW codec, and the arc's single most correctness-critical new
   component (a decode bug corrupts migrated payloads silently; the
   BLAKE2sp roundtrip check below is the backstop).
2. **No legacy RAR support exists.** Only RAR5 is parsed
   (`format/header_reader.cpp`); there is no rar15/20/29 unpacker, no PPMd,
   and no legacy header parser anywhere. "Legacy RAR input" is 100% new
   code, and its decompressors (rar 1.5/2.0/2.9 LZ, PPMd) are the largest
   clean-room items conceivable for this arc (see CV-C).
3. **The add pipeline is disk-file-shaped.** `ArchiveMutator::prepare_add_file(
   src_file, arc_entry_name, ...)` reads a LOCAL file, computes CRC,
   packs (memory ≤ 16 MiB, `SPOOL_MEMORY_THRESHOLD`, else spool to disk),
   optionally encrypts, and fills `PreparedAdd{fb, payload|spool_path,
   entry_name}`; `write_batch_add` then writes SFX prefix + headers +
   payloads + ENDARC and atomically replaces the archive. Stage-1 variants
   exist for dirs/symlinks/hardlinks/FILECOPY
   (`prepare_add_dir`/`_symlink`/`_hardlink`/`_filecopy`). Everything cv
   needs is already public — the orchestrator never touches the writer's
   internals (§0 claim).
4. **The caps vocabulary exists and is reusable.** `ExtractionLimits`
   (max_member_output_bytes, max_total_output_bytes, max_header_count,
   max_header_bytes; UNLIMITED sentinel) + `LimitState` cumulative debit +
   `debit_bytes()`; `MtimeBounds`/`clamp_mtime`/`mtime_out_of_bounds` in
   src/archive/extraction_limits.hpp. The CLI itself does not set limits
   for interactive `x` (UNLIMITED default); DLL/WASM callers pass them.
   The foreign readers consume the same structures — §5.4 applies to
   foreign formats with zero relaxation (§2).
5. **The name-mapping machinery is exactly what cv needs.**
   `io::sanitize_archive_path` (path_util.cpp:169) normalizes separators,
   strips drives + leading slashes, resolves `.`/`..` lexically
   (component pop), percent-encodes invalid UTF-8 losslessly (§4.4: the
   escaped name IS the name), and hardens components
   (`make_safe_component`: controls → `_`, Windows-forbidden chars,
   trailing dots/spaces, DOS-device stems). The disk-name layer and the
   display layer (`cli::sanitize_for_display`, idempotent, v1.28 render
   choke point) are both directly reusable — cv's output lines and JSON
   inherit the §7.1 gate by calling the same two functions, and the
   non-TTY contract (zero escape bytes, exit-code parity) applies to the
   cv command like any other (v1.28 M3 pattern, pinned by tests).
6. **Exit taxonomy constants** live in src/cli/main.cpp
   (EXIT_WARNING=1, EXIT_CRC=3, EXIT_USAGE=7, EXIT_NO_FILES=10,
   EXIT_BAD_PASSWORD=11, EXIT_BAD_ARCHIVE=13, EXIT_FATAL=2,
   EXIT_USER_BREAK=255) — §3.1 forbids new codes; cv maps entirely into
   this set (§3 CV-H).
7. **The interop gate is finder-based and appendable.** tools/interop_gate.py
   locates openrar/UnRAR/WinRAR (`find_openrar`/`find_unrar`/`find_rar`),
   runs numbered `test_*` stages from `main()`; stages are plain functions
   — appending Tracks 11+ is mechanical, and the brief requires keeping
   stage definitions data-driven so the v1.30 arc's stages append cleanly.
   Foreign SOURCES for the new tracks can be generated in-script with
   Python's stdlib (zipfile/tarfile/gzip) — no new oracle dependency for
   building the inputs; the ORACLES remain WinRAR/UnRAR (and 7z where
   installed, availability-gated).
8. **Reader hooks exist for progress/cancel** (v1.28):
   `ReaderHooks{progress,cancel}` polled per chunk on all write loops;
   cv's foreign readers carry the same hook shape so the TUI (dual-progress
   renderer, ESC/q/^C cancel → 255, temps swept) drives transcode runs
   with no new rendering code.
9. **Crypto inventory** (for the encrypted-ZIP decision): aes256, blake2sp,
   crc32, crc64, sha256, pbkdf2 (PBKDF2-HMAC-SHA256, the RAR5 KDF), rng.
   There is NO SHA-1 in the tree. WinZip AES-ZIP is keyed by
   PBKDF2-HMAC-SHA1 with HMAC-SHA1 authentication — implementing AES-ZIP
   decryption in Phase 1 would first require a new crypto primitive with
   its own KAT set (ground rule: crypto changes come with known-answer
   vectors). This seals CV-D's encryption decision (§3).
10. **Collision detection is a standalone component** —
    `collision_detector.{hpp,cpp}` (the v1.24 four-class detector:
    duplicate-identical, case-fold, NFC/NFD, file-vs-dir) — directly
    reusable over the translated entry list before cv emits anything
    (§3 CV-G: cv output must never contain collisions our own extractor
    would abort on, §3.2).
11. **Test/gate conventions:** 33 ctest suites today; tests are
    assert()-based executables registered via `add_openrar_test()`;
    cli_tests.cpp is OUTSIDE namespace openrar (fully qualified names,
    explicit includes), uses `system_exit_code()` and `get_cli_path()`;
    the pre-commit hook runs clang-format + the interop gate when
    compress/archive/format code changes — new compress/archive files
    will trigger it locally. WSL preflight mirror for this arc:
    `~/openrar-m2check-v129` (NOT the shared mirror).

## 3. Candidate designs, argued honestly

### CV-A — transcode orchestration: how foreign payloads reach the RAR5 writer (three options)

**CV-A1: stage-to-temp, reuse the add pipeline verbatim (PROPOSED).**
For each foreign entry: decode (caps-debited, hooked, hash-on-the-fly)
→ write payload into an engine-controlled staging file → set its mtime to
the clamped foreign mtime (`std::filesystem::last_write_time`) →
`prepare_add_file(staging, translated_name, ...)` → staging file deleted
immediately → collect `PreparedAdd` → `write_batch_add`. Directory
entries: create real staging dirs (times set) → `prepare_add_dir`.
- Pros: ZERO writer-side hunks (the §0 claim becomes structural: cv
  cannot drift the writer because it never enters it); metadata paths
  (CRC, method downgrades, solid packing, encryption, HTIME) exercised
  through their shipped, oracle-verified forms; temp files are
  engine-named so no archive name ever touches a local path.
- Cons: one extra disk round-trip per entry (read foreign → staging →
  read staging → pack). Mitigation: staging files are deleted right after
  their prepare, so peak extra disk ≈ largest single entry, plus the
  writer's own spool (≤ packed size; direct_stream keeps the streaming
  variant available). Migration is a one-shot operation — I/O cost is the
  price of zero emission drift, and the honest one.

**CV-A2: in-memory prepare variant (new `prepare_add_buffer` beside
`prepare_add_file`).** Rejected for Phase 1: it requires refactoring
prepare's internals to a byte-source abstraction (hunks inside
archive_mutator.cpp's prepare region — defensible but contrary to the
spirit of the §0 claim), duplicates the spool/encrypt/CRC orchestration
drift risk, and buys only the elimination of the staging round-trip.
Revisit only if cv profiling shows the staging cost is user-visible.

**CV-A3: direct emission (a transcode-specific writer path). REJECTED
outright** — it is precisely the "new emission code" the §0 claim forbids,
and it would demand a whole new interop/oracle matrix for bytes the
shipped writer already knows how to make.

### CV-B — does Phase 1 EMIT foreign formats (RAR5 → ZIP/TAR/GZIP)? (DEFER: yes, defer)

- **For emitting now:** "Transcoder" reads symmetric; WinRAR can write
  ZIP; a tar writer is trivial; users migrating OFF RAR exist.
- **Against (PROPOSED — defer):** the roadmap's deliverable is migration
  INTO OpenRAR/WinRAR-readable RAR5 and the stated oracle is
  "WinRAR/UnRAR/7z readability of EMITTED archives" — i.e., RAR5-out.
  Each foreign writer is its own format-legality project (APPNOTE
  write-side choices: version-needed, general-purpose bits, external
  attrs conventions, data-descriptor usage; pax/GNU emission dialects)
  with its own oracle matrix (Info-ZIP, GNU tar, bsdtar disagree), its
  own weaponization surface, and its own Gate 0 — roughly doubling the
  arc for zero migration value in the stated direction. README will state
  the direction explicitly ("read-only; foreign emission is not
  implemented") so the feature-row stays truthful, and the "Not yet" row
  gains the write side.

### CV-C — legacy RAR depth (PROPOSED: parse + store-extract + explicit per-entry errors; no legacy decompressors in Phase 1)

- **For full legacy unpacking now:** the skeleton wording says "extract
  non-VM entries"; most real 2.x/3.x corpora are compressed (rar29 is the
  RAR3-era default), so parse+store-only migrates empty for many archives;
  unrar proves the algorithms are publicly documented.
- **Against (PROPOSED — Phase 1 as stated):** "non-VM extraction" for
  1.5–4.0 requires up to FOUR clean-room codecs (rar 1.5/2.0 LZ, rar 2.9
  LZ, PPMd, plus the rar3 unicode-name decoding), each with its own CVE
  history, each needing oracle verification on real corpora — a second
  full arc by size and risk profile. §5.3's actual normative requirement
  is the VM boundary, and Phase 1 satisfies it in its strongest possible
  form: a binary containing NO legacy decoder cannot execute ANY legacy
  filter — provable by absence, not by audit. The per-entry error
  channel distinguishes "VM filter required" (§5.3's named case) from
  "legacy compression method not implemented in Phase 1" — both explicit,
  both method-named, both skip-with-report. Stored entries (method 0x30),
  directories, and small-file metadata migrate today; the decompressors
  are a candidate later arc with their own Gate 0 IF user demand exists.
  README "Not yet" row gains the legacy-codec line so the claim stays
  truthful.

### CV-D — ZIP reader design (PROPOSED)

1. Signature/EOCD: locate EOCD by bounded backward scan (spec comment max
   64 KiB; scan window capped — prepended SFX stubs tolerated; a hit must
   validate EOCD field consistency else exit 13). ZIP64: EOCD64 locator +
   EOCD64 + per-entry ZIP64 extra fields, full read support.
2. Pre-flight pass (the release gate): parse the ENTIRE central directory
   (header-count/bytes caps apply), then for every entry read the local
   file header at the CD-recorded offset and compare: name bytes,
   method, flags (bit-3 size tolerance documented — descriptor entries
   legitimately carry placeholder sizes in the LFH; name/method/offset
   mismatches remain fatal), sizes, offset continuity. ANY mismatch →
   structural abort (exit 2) — the whole pass completes before the first
   staging file is created (§2.1: integrity failure, NOT best-effort).
3. Decode pass: per entry, DEFLATE (method 8) via the new inflate codec,
   store (method 0), CRC32 verified per entry (format-level integrity,
   distinct from the transcoder's BLAKE2sp roundtrip hash); unsupported
   methods (bzip2/LZMA/PPMd ZCL) → per-entry error (method-named).
4. Encryption: general-purpose bit 0 → per-entry refusal. ZipCrypto →
   explicit "legacy weak cipher refused by policy" error; AES-ZIP (0x9901)
   → explicit unsupported error — Phase 1 implements NO foreign decryption
   (the SHA-1 primitive it requires does not exist in-tree, fact 1.9);
   both documented in README. No `-p` password is accepted for foreign
   sources in Phase 1 (the refuse-by-default decision has no opt-in flag
   yet; a future flag is a Phase-2 decision with its own review).
5. Names: bit-11 UTF-8 / cp437 rule + sanitize-at-transcode (§2 table);
   comments: archive-level comment migrates to the RAR5 `CMT` service
   (UTF-8 sanitized); per-entry ZIP comments have no RAR5 representation →
   skip-with-report (documented lossy, `comment_skipped` flag).
6. Collision classes run over the translated name list (fact 1.10) before
   emission — cv output must not contain an archive our own extractor
   aborts on (§3.2).

### CV-E — TAR reader design (PROPOSED: ustar + a documented GNU/pax subset)

Typeflags: `0`/`5` (file/dir) migrate; `1`/`2` (hardlink/symlink) migrate
as FHEXTRA_REDIR records (data in transit — downstream extraction stays
default-deny per §4.2; `link_migrated` JSON flag); `3`/`4`/`6`
(char/block/fifo) and `7` → skip-with-report; `L`/`K` (GNU long
name/link) supported (bounded); `x`/`g` (pax) with the documented subset
{path, linkpath, size, mtime, atime, uid, gid, uname, gname, hdrcharset}
— unknown keys skipped per POSIX self-describing semantics, records
size-bounded; GNU sparse (`S` typeflag and `GNU.sparse.*` keys) →
per-entry refusal (documented subset boundary, not silent corruption).
End-of-archive: two zero blocks; EOF before padding accepted (streamed
tapes), documented. Sizes vs remaining input enforced (a member claiming
more than the file holds → truncation error, exit 3).

### CV-F — GZIP reader design (PROPOSED)

RFC 1952 header (FLG FTEXT/FHCRC/FEXTRA/FNAME/FCOMMENT), CRC32 + ISIZE
verified per member; **multi-member files decode as ONE logical entry —
the concatenation of member payloads** (the zcat/`cat a b | gzip`
semantics; the single-vs-concatenated decision the brief directs: RFC
1952 members are independent streams and concatenation IS the documented
interoperable reading; a multi-member .gz therefore yields ONE RAR5
entry). FNAME of the first member names the entry (sanitized); absent →
derived from the source stem per the RFC's convention (documented);
FCOMMENT → skip-with-report; FEXTRA → bounded skip. In-flight member cap
+ cumulative cap (the §5.4 bomb case — §2 table).

### CV-G — metadata translation layer (PROPOSED summary)

mtime-only in Phase 1 (times_mask = MTIME): foreign ctime/atime sources
(ZIP UT/NTFS extras, pax atime) are mapped where the staging-file
mechanism can express them portably — and ctime is not settable on POSIX,
so cv stores mtime only and documents it (high-precision times remain an
`a`-side feature). Attrs: DOS bits → file_attr; unix mode only with
0170000 type bits (§4.3); uname/gname/uid/gid (TAR, ZIP unix fields) →
FHEXTRA_UOWNER records. All timestamps clamped through MtimeBounds.
Comments per CV-D.5. Names per §2 table. Charset: emitted RAR5 names are
valid UTF-8 always (the escaped name IS the name, §4.4).

### CV-H — the `cv` CLI surface (PROPOSED)

`openrar cv <source> [dest.rar]` — dest defaults to source stem + `.rar`.
Refuses RAR5/legacy-RAR-signature COLLISION cases honestly: a RAR5
signature source is a usage error (7) in Phase 1 (re-packing existing
RAR5 is `a`/`u`/`f`, not cv); legacy RAR (1.5–4 signature) IS a cv
source. Switches (parsed by the global parser, parity with existing
behavior — unknown switches warn-and-ignore per the shipped M7 pattern):
`-m0..-m5`, `-md<n>`, `-s`, `-p`/`-hp` (output encryption only — no
foreign decryption), `-o+`/`-y` (dest overwrite; otherwise the shipped
prompt path with its PROMPT-state handling), `-df`, `--json-summary[=path]`,
`-q`/`-plain` (render contract). NOT accepted meaningfully in Phase 1
(warn+ignore): `-oi` (no FILECOPY emission — §0.1), `-ts*` (mtime-only),
`-ep*` (names preserved from source), `-v` (no volume split in Phase 1 —
refused with usage error 7, not ignored: volume-splitting a migration is
a correctness-sensitive feature that should be explicit), `-rr`
(similarly explicit-refused? — no: RR on the output is harmless and the
writer supports it; PROPOSED: accepted). Exit codes: the shipped `x`
aggregation rule inherited exactly (challenge D1) — see the §2 table
row; per-entry FAILED → 2, encrypted-refused → 11, policy skips → 0 +
report, structural → 2/13 pre-output, usage → 7, cancel → 255. JSON:
existing schema + additive top-level `format`,
`verified`, `source_deleted` and per-entry flags `method_refused`,
`encrypted_refused`, `vm_filter_refused`, `comment_skipped`,
`link_migrated` — additive fields only (schema_version bump + parse test
per challenge D3), UTF-8 guarantee inherited.

### CV-I — `-df` verify-before-delete (PROPOSED)

The transcoder keeps, per migrated entry, the BLAKE2sp of the source
payload computed during decode. After `write_batch_add`: re-open the
emitted archive (fresh ArchiveReader), test-extract every entry
(compressed path through the shipped decode + checksum), hash the
payloads, and require per-entry hash equality PLUS entry-count parity —
the "byte-verified roundtrip". Only then delete the source (plain
delete). Any skip/failure (encrypted refused, VM, unsupported method,
name-sanitizes-to-empty) ⇒ the migration is incomplete ⇒ source NOT
deleted, exit 1 with the report saying so. Verify failure ⇒ source not
deleted, exit 3 (CRC class). Cancel during verify ⇒ source not deleted,
255.

  per-entry BLAKE2sp source-hash verification (the transcoder never trusts

  documented (CV-A1); direct_stream remains available if profiling

  changelogged, negative-tested, and scoped: actual links stay
  default-deny; only the in-archive copy directive becomes default-on.

  (no TZ stored) — documented divergence class, same as every other zip
  tool; Unix/NTFS/UT timestamp sources are unambiguous and preferred when
  present.
- **R5:** `\`→`/` normalization loses a legal-if-rare Unix name shape —

  percent-encoding remains the lossy-but-reversible channel for

  boundaries, path lengths) — pinned by unit tests on all legs; the WSL
  Release -Werror mirror + the macOS/ARM legs of the release preflight
  catch build-level surprises (no `<windows.h>` at namespace scope, no
  `::sigemptyset`-style POSIX collisions — the v1.28 trap list).
- **R7:** a hostile foreign archive crafted so the CD/LF pre-flight passes
  but decode diverges (TOCTOU inside one file) — the source file is
  opened once and read sequentially from the pinned handle; no re-open
  between pre-flight and decode; offsets are pre-flight-verified; the
  decode pass re-verifies every payload CRC, so a raced file fails with
  3, not corruption.

## 2. 🚨 Critical Red Flags & Fatal Flaws

None fatal to the scope. The following are critical-class findings that
the plan MUST absorb (each is a directive below):

- **[Exit-mapping error — D1]** The pre-analysis (§2 table, CV-H) maps
  per-entry failures to "exit 1 warnings". The shipped `x` path aggregates
  any_failed → EXIT_FATAL (2), bad-password → 11, and policy SKIPS (e.g.
  default-deny links) are NOT failures (they do not flip the exit code) —
  main.cpp:2896. A cv that exits 1 where `x` exits 2 for the same class of
  outcome breaks the taxonomy parity §3.1 exists to protect, and the
  interop stage-15 exit-code pins would catch it late. Corrected in this
  revision: cv inherits the shipped aggregation rule exactly.
- **[Declared-size trust — D5]** As written, the inflate decode trusts the
  CD's declared unp_size as the output bound. A crafted archive pairs a
  small declared size with bit-3 (descriptor) semantics or simply lies
  before the pre-flight comparison order is even reached; the ZIP CD/LF
  gate compares DECLARED values against each other — it cannot bound
  ACTUAL inflate output. The RFC 1951 decoder MUST carry a mandatory
  in-flight output cap wired to the same LimitState debit (the GZIP cap
  reasoning generalized: no declared value is a bound; declared values are
  hints verified against actual bytes).
- **[Build wiring vs wasm budget — D2]** `OPENRAR_CORE_SOURCES` is an
  explicit list (CMakeLists.txt:27) linked into EVERY native target AND
  every wasm target. The pre-analysis never says how inflate.cpp and the
  foreign readers enter the build without silently entering the lean wasm
  block-codec build (500 KiB hard CI gate, wasm-limitations §5.3). The
  shipped precedent is the `OPENRAR_INMEM_ARCHIVE` option
  (CMakeLists.txt:87): a `OPENRAR_FOREIGN_FORMATS` option (default ON for
  native, OFF for the lean wasm preset) isolates the new sources the same
  way buffer_archive.cpp is isolated.

## 3. ⚠️ Weak Assumptions & Fragile Invariants

- **[Assumption: additive JSON fields are free]** The report schema pins a
  stable field order and schema_version = 1
  (extraction_report.hpp:29,55). "Additive fields, guarantee inherited"
  glosses over whether consumers see a schema change. D3 forces the
  explicit decision (append + bump to schema_version 2 with a parse test,
  or append under v1 with a documented additive-fields contract — pick
  one and pin it).
- **[Assumption: CD/LF comparison is well-defined by prose]** "name,
  method, flags-compat, sizes, offsets" needs the exact tolerated subset:
  WHICH flag bits are compared (0/3/11) and how bit-3 tolerance composes
  with the ZIP64 extra-field size override (a ZIP64 entry's LFH sizes are
  ALSO placeholders). D6.
- **[Assumption: TAR detection is decidable]** TAR has no magic (v7
  archives lack even the ustar magic at offset 257); ZIP/GZIP/legacy-RAR
  have signatures. A single detection function with documented precedence
  (signatures first, TAR last via header-checksum validation) is required,
  tested for ambiguity, or two commands will disagree about the same file
  (Pillar 7 pattern 8). D8.
- **[Assumption: staging cleanup is trivial]** The staging area lives in
  the system temp dir; a crash leaves engine-named orphans that the
  extraction-journal machinery does NOT cover (journals anchor user
  destinations). The orphan shape and the sweep story must be stated, not
  improvised (D10).
- **[Assumption: `prepare_add_file` mtime fidelity equals `-a`]** Yes —
  and that is the honest ceiling: the staging file's mtime is set through
  `std::filesystem::last_write_time`, whose precision is filesystem- and
  clock-dependent. Documented as mtime-only with FS-bound precision; ctime
  is not portable-settable (POSIX). Accept as stated; keep it in the FMM
  platform row.
- **[Assumption: verify is a -df concern]** The pre-analysis implies the
  roundtrip verify belongs to -df. It must be UNCONDITIONAL (the arc's
  headline contract is bit-for-bit equivalence; -df only adds the delete
  gate on top). D9.
