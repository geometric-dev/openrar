# v1.37.0 — The intra-entry parallel-decode design wall (scoped negative result)

Status: **measured and recorded; the arc is re-scoped** (the v1.32
optimal-parse and v1.34 extraction-throughput precedent). The roadmap's
v1.37 prediction — ~1.15–1.35x on decode-bound single-member extraction —
presumed a parallelizable design exists. It does not, for RAR5 streams as
defined, and this record closes the door the v1.34 record left open
("intra-entry parallel decode via the documented slot model (window half
open)").

Artifacts: branch `arc/v1.37.0-parallel-decode-wip` (the scout, three
complete range-decode designs, the driver, and the identity-test harness —
committed, format-gated, interop-gate-green 24/24 on the gate corpus).
Gate 0 record: `docs/v1.37.0-pre-analysis.md`; plan:
`docs/v1.37.0-implementation-plan.md`.

## 1. What was validated before the wall

- **The scout** (symbol-only sequential pass recording per-block
  resynchronization state — rep distances, Huffman tables, filter
  applications, output spans): validated **block-by-block against the
  sequential decoder, 141/141 blocks byte-identical output spans and
  states**. The scout itself is sound, cheap (α ≈ symbol-decode fraction
  of one decode), and remains the correct foundation for any future
  design (including the demand-driven one below).
- **Block-start checkpoints** match the independent reuse-scanner walk
  (scan_table_reuse.py) on every corpus member tested.
- The reference-scaling probes (Gate 0 §0) stand: Rar 7.20 scales 1.29x on
  64 MiB text at `-mt4` (1.50x at 128 MiB dict), 0.95x on a 4-block
  member, 1.07x on overhead-bound zeros — **its mechanism does not
  serialize the LZ dependency chain**, and replicating it remains the
  open research question.

## 2. The three designs built and measured

All three passed MT/ST byte-identity on the test corpus where applicable
and failed on the property that matters:

1. **Shared pre-transform buffer + wait-on-producer** (the Gate-0-approved
   design). Measured **0.72–0.74x sequential** on decode-bound extraction
   (paired-delta protocol, 0/9 pairs faster, three thread counts). Root
   cause: the token stream is strictly sequential — worker r's first
   cross-range match stalls until range r−1 produces the referenced tail
   bytes, which happens at range r−1's END. The stalls chain: wall time ≈
   serial. This is not an implementation defect; it is the dependency
   structure of LZ77.
2. **Redundant-overlap decode** (each worker starts `dict` bytes before
   its range and re-decodes the overlap state-only, no waits). Measured
   **wrong bytes**: during the overlap, matches legally reference bytes
   *before* the overlap checkpoint (the reference chain reaches back past
   any finite overlap); `copy_match`'s zero-fill branch then poisons the
   ring, and the poison propagates forward through the reference graph
   into the written region. A longer overlap only delays the poison —
   matching the reference's own window semantics requires the full prefix.
3. **Redundant-from-zero** (every worker decodes from the member start,
   discarding until its range). Correct by construction but the last
   worker decodes the whole member: wall ≈ sequential. No win.

## 3. Why the wall is structural

Decoding position n requires output bytes [n−dist, n), and dist can reach
anywhere in the window (≤ dict), including the entire prefix. With no
per-block reset markers on the wire (state = rep distances + Huffman
tables + window content, none carried across blocks), **the dependency
chain of a RAR5 member is the whole member**. Every parallel scheme
reduces to one of: serialize the chain (design 1), poison (design 2),
or O(member) redundant work per worker (design 3). The reference's
measured 1.29–1.50x implies a mechanism outside this space — replicating
it needs either reference-internal knowledge we do not have, or the
demand-driven design below.

## 4. The remaining lever (recorded, not scheduled)

**Demand-driven backward decoding**: workers decode their ranges; a match
source before the range start triggers a memoized sub-decode of the
referenced region (snapped to block boundaries — the scout supplies state
at every block start), recursing on the sub-decode's own backward
references. Truly parallel, no serialization — but: recursion in a
security-critical decode path needs a bounded work/memory budget per
worker (adversarial reference graphs could recurse to the member start —
cap-and-fail-closed), and the win depends on reference locality (real
data: sub-decodes converge near the dict tail; adversarial: budget
exhausted → fallback). This is a full arc on its own, with its own Gate 0.
It is recorded as the candidate successor lever; v1.38's decode-kernel
work (single-threaded flat tables/SIMD) does **not** hit this wall and is
unaffected.

## 5. Pre-existing defect discovered en route (P2, v1.36.0 confirmed)

`sandboxed-worker `t`` reports **false FAILED for members whose unpacked
size is ≥ 64 MiB** — confirmed on the v1.36.0 binary (12/12 fails on a
64 MiB RAR-made archive; 56 MiB passes; threshold exactly at the 64 MiB
output boundary; the identical archive verifies OK in-process and via
UnRAR). The WIP driver path in the worker verified 12/12 OK at 64 MiB —
the defect is in the worker's sequential-streaming verify path
(`extract_entry_sink` + IPC payload reassembly), not in decode itself.
Not caused by this arc; recorded with the repro recipe (mtprobe corpus,
`Rar.exe a -m3 -mt1`, `openrar t`) as a fix candidate for a 1.36.x patch.
