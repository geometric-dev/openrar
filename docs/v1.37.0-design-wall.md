# v1.37.0 — The intra-entry parallel-decode design wall (scoped negative result)

Status: **measured and recorded; re-scoped after verification** (the
v1.32 optimal-parse and v1.34 extraction-throughput precedent). The
roadmap's v1.37 prediction — ~1.15–1.35x on decode-bound single-member
extraction — presumed a parallelizable single-pass design exists. It does
not, for RAR5 streams as defined; the three measured designs close that
door. A later independent format verification identified the mechanism
the reference actually uses — two-phase decode (parallel symbol decode,
serial window application) — which the single-pass wall does not cover;
see §3/§4: the "no parallelizable design" conclusion is retracted, the
wall's measurements stand.

Artifacts: branch `arc/v1.37.0-parallel-decode-wip` (the scout, three
complete range-decode designs, the driver, and the identity-test harness —
committed, format-gated, interop-gate-green 24/24 on the gate corpus).
Gate 0 record: `docs/v1.37.0-pre-analysis.md`; plan:
`docs/v1.37.0-implementation-plan.md`.

## 1. What was validated before the wall

- **The scout** (symbol-only sequential pass recording per-block
  resynchronization state — rep distances, Huffman tables, filter
  applications, output spans): validated **block-by-block against the
  sequential decoder, 141/141 blocks byte-identical output spans and
  states**. The scout itself is sound, cheap (α ≈ symbol-decode fraction
  of one decode), and remains the correct foundation for any future
  design (including the demand-driven one below).
- **Block-start checkpoints** match the independent reuse-scanner walk
  (scan_table_reuse.py) on every corpus member tested.
- The reference-scaling probes (Gate 0 §0) stand: Rar 7.20 scales 1.29x on
  64 MiB text at `-mt4` (1.50x at 128 MiB dict), 0.95x on a 4-block
  member, 1.07x on overhead-bound zeros — **its mechanism does not
  serialize the LZ dependency chain**, and replicating it remains the
  open research question.

## 2. The three designs built and measured

All three passed MT/ST byte-identity on the test corpus where applicable
and failed on the property that matters:

1. **Shared pre-transform buffer + wait-on-producer** (the Gate-0-approved
   design). Measured **0.72–0.74x sequential** on decode-bound extraction
   (paired-delta protocol, 0/9 pairs faster, three thread counts). Root
   cause: the token stream is strictly sequential — worker r's first
   cross-range match stalls until range r−1 produces the referenced tail
   bytes, which happens at range r−1's END. The stalls chain: wall time ≈
   serial. This is not an implementation defect; it is the dependency
   structure of LZ77.
2. **Redundant-overlap decode** (each worker starts `dict` bytes before
   its range and re-decodes the overlap state-only, no waits). Measured
   **wrong bytes**: during the overlap, matches legally reference bytes
   *before* the overlap checkpoint (the reference chain reaches back past
   any finite overlap); `copy_match`'s zero-fill branch then poisons the
   ring, and the poison propagates forward through the reference graph
   into the written region. A longer overlap only delays the poison —
   matching the reference's own window semantics requires the full prefix.
3. **Redundant-from-zero** (every worker decodes from the member start,
   discarding until its range). Correct by construction but the last
   worker decodes the whole member: wall ≈ sequential. No win.

## 3. Why the wall is structural — and what the verification pass corrected

Decoding position n requires output bytes [n−dist, n), and dist can reach
anywhere in the window (≤ dict), including the entire prefix. With no
per-block reset markers on the wire (state = rep distances + Huffman
tables + window content, none carried across blocks), **the dependency
chain of a RAR5 member is the whole member**. Every scheme that decodes
AND applies in one serial pass per worker reduces to one of: serialize
the chain (design 1), poison (design 2), or O(member) redundant work per
worker (design 3).

Independent format verification of the three-design record corrected the
original conclusion: the reference **does** parallelize — via a
**two-phase decode**. Phase 1 parallel-decodes the Huffman/token symbol
stream into operation records (literals + match descriptors; per-thread
private table slots, workers claim spans at block boundaries — a
productionized generalization of the scout). Phase 2 applies the records
to the window serially (a memcpy-bound pass that parallelizes poorly and
does not need to). The LZ dependency chain binds the WINDOW APPLY stage,
not the symbol-decode stage; our wall measured the coupled design only.
The claim "no parallelizable design exists" is therefore **retracted**;
what stands is: no *single-pass* design parallelizes, and the two-phase
design was within reach of the parked branch (scout = symbol-stage
prototype; sequential decoder = the applier).

## 4. The remaining levers (recorded, not scheduled)

1. **Two-phase decode (now dominant)**: parallel symbol decode into
   operation records + serial window application. Hazards called out by
   the verification: record memory scales with member size (bound per
   range or spill to disk for very large members), and very small blocks
   should fall back to inline single-phase decode (~128 KiB blocks
   amortize the handoff). This supersedes the v1.37.0 re-scope when
   scheduled; it can land as the revised v1.37 arc.
2. **Demand-driven backward decoding**: workers decode their ranges; a match
   source before the range start triggers a memoized sub-decode of the
   referenced region (snapped to block boundaries — the scout supplies state
   at every block start), recursing on the sub-decode's own backward
   references. Now *dominated* by lever 1 for the common case (it
   parallelizes the memcpy-bound stage too, but pays recursion +
   memoization overhead); kept as the fallback candidate where phase-1
   record memory is the binding constraint. Security-critical: bounded
   work/memory budget per worker, cap-and-fail-closed on adversarial
   reference graphs.
3. v1.38's decode-kernel work (single-threaded flat tables/SIMD) does
   **not** hit this wall and is unaffected.

## 5. Pre-existing defect discovered en route (P2, root-caused and fixed in 1.36.x)

`sandboxed-worker `t`` reported **false FAILED for members whose unpacked
size is ≥ 64 MiB** — confirmed on the v1.36.0 binary (12/12 fails on a
64 MiB RAR-made archive; 56 MiB passes; threshold exactly at the 64 MiB
output boundary; the identical archive verifies OK in-process and via
UnRAR). Not caused by this arc.

**Root cause** (isolated by a shadow-reader differential inside BitReader):
`BitReader::refill()` fetched the next input chunk only when the 64 KiB
staging buffer was *completely* drained. When the bit accumulator and the
buffer were both nearly exhausted (`n_ + 8·bufleft < count`) while stream
bytes remained unfetched, `peek_bits` returned a zero-padded value
mid-stream — zero padding is end-of-stream semantics. Corruption then
depends on the resolved Huffman code length (a code fully inside the real
bits is benign; one that needs a padded bit desyncs the stream), which is
why only *some* large members corrupted and why the divergence point
(input byte 0x180000·k boundaries, output ~60.3 MB on the 64 MiB repro)
wandered. The contiguous reader (buffer = whole stream) is structurally
immune, which contained the blast radius to streaming consumers.
Fixed by making `refill()` loop — top the accumulator to ≥ 57 bits,
fetching successive chunks, returning short only at the true end of
stream; regression `bitreader_stream_tests` drives both variants over the
same stream with the same op sequence and requires value equality (it
fails on the pre-fix reader at chunk=1 within 1 MB).
