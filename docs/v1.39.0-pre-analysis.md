# v1.39.0 Pre-Analysis — Durability Batching: the Extraction Crash-Consistency Contract Revision (Gate 0)

Arc inputs: ROADMAP v1.39–v1.43 discovery pool ("durability batching …
default-off until the contract revision is proven"),
`docs/SECURITY_ARCHITECTURE.md` §3.3 (atomic extraction),
`docs/invariants.md` §5 (durability & temp-file lifecycle) and §2 (RAM
ceiling), `docs/v1.34.0-implementation-plan.md` §5 addendum (the measured
contract price), `docs/v1.38.0-pre-analysis.md` §6/§9 (predecessor; the
measurement protocol is v1.34 §3 and governs this arc too). **This arc is
security-normative end to end: the contract revision is the deliverable; the
performance claim is only valid against the revised contract.**

## 0. The founding premise — decomposed and measured

The roadmap's claim: batching the per-entry journal sync takes stored-path
extraction from ~205 MB/s toward the ~400 MB/s I/O-bound ceiling (~1.8–2x)
and ~16% on text, at the price of coarser crash-consistency granularity.
The v1.34 addendum named the per-entry price: a durable-first journal record
(append + fsync BEFORE the temp exists), a temp-file flush before the commit
rename, "plus per-session journal creation syncs". One component was missing
from that list and turns out to be material: **the per-entry journal
LIFECYCLE** — `release_temp` closes and unlinks the directory journal when
its in-flight count drops to zero, and sequential extraction drops to zero
after every entry, so every entry pays a full sweep rescan + journal create +
header sync + close + unlink cycle on top of the record sync.

The probe (`tools/durability_probe.cpp`, not a test; three sessions on the
v1.38.0 Release build, 2C/4T i7-7500U, min-of-N reported) priced every
component:

**Flush cost vs payload** (create + write + rename, no flush vs pre-rename
`FlushFileBuffers` vs post-rename flush through the renamed handle):

| payload | no flush | flush before rename | flush after rename |
|---|---:|---:|---:|
| 4 KiB | 1.52–1.66 ms | 2.84–6.79 ms | 2.75–6.45 ms |
| 1 MiB | 3.22–3.45 ms | 6.70–11.42 ms | 6.91–11.38 ms |
| 8 MiB | 10.8–12.6 ms | 47.6–48.8 ms | 49.7–49.0 ms |
| 64 MiB | 80.1–103.7 ms | 357.3–393.3 ms | 359.1–368.5 ms |
| 256 MiB | 372–382 ms | 1466–1501 ms | 1438–1479 ms |

Two readings: the flush costs ~1.2–5 ms fixed plus ~4.5 s/GiB scaling (the
64 MiB flush ≈ 280 ms of the 357–393 ms row), and **flush-after-rename costs
the same as flush-before-rename** — reordering the flush buys nothing; only
deferring or dropping it buys time.

**Journal components** (median/min of 20/200):

| component | cost |
|---|---:|
| sweep rescan, dir with 1 file | 0.07–0.10 ms |
| sweep rescan, dir with 2000 files | 2.4–2.5 ms |
| AtomicWriter open+abandon full lifecycle (sweep + journal create + header sync + record append + sync + temp create + dispose + close + unlink) | 4.7–10.1 ms min |

**End-to-end pipelines through the real mechanism** (entry-granularity =
today's `AtomicWriter::open/write/commit` per file; batched replica = journal
held for the whole run, records appended unsynced and synced per 32, no
per-temp flush, rename per entry through the open handle):

| pipeline | entry (today) | batched replica | ratio |
|---|---:|---:|---:|
| 2000 × 16 KiB | 18.1–50.1 s | 4.6–4.8 s | **3.8–10.7x** |
| 500 × 128 KiB | 5.3–12.2 s | 1.2–1.6 s | **3.2–9.7x** |
| 1 × 64 MiB | 0.34–0.42 s | 0.12–0.18 s | **1.9–3.5x** |
| 4 × 32 MiB | 0.53–0.77 s | 0.18–0.22 s | **3.4–6.3x** |

The batched replica sits at 355–709 MB/s on the big-file rows — the
cache-write ceiling (UnRAR's stored row reads ~372 MB/s on the same host,
which is the same class of number: a reference extractor writes into the page
cache and lets writeback race ahead of the timer). The entry-granularity
column is session-sensitive (background writeback state); the robust quantity
is the per-entry delta: **~7–24 ms of durability overhead per entry today,
~2 ms in the batched shape.**

The premise is therefore confirmed in structure but the attribution is
corrected: the stored-path gap is THREE components, not two —

1. **temp flush before rename** (~4.5 s/GiB + ~1–5 ms fixed) — dominant for
   big payloads;
2. **per-entry journal lifecycle** (~5–10 ms + sweep rescan) — dominant for
   many small entries (sequential extraction re-creates the journal per
   entry);
3. **per-entry journal record sync** (~1–5 ms fixed) — part of 2's cycle in
   sequential extraction.

And the contract consequence that drove the design below: **a boundary that
flushes data preserves today's big-file cost** (flush-after-rename =
flush-before-rename), so a "batched durability with boundary fsyncs" contract
would recover only the journal components — the single-big-file stored row
would read ~1.0–1.1x and the roadmap's ~1.8–2x claim would fail on that row
by construction. The measured claim is only reachable by a contract that
delegates data durability to OS writeback (reference-tool class) — which is
exactly the coarser crash-consistency granularity the roadmap priced.

## 1. Format surface — none

This arc touches no RAR5 bytes: no header parsing, no emitted stream, no
record types. Extraction content identity (byte + chunk), the containment
walk, collision policy, link policy, and namespace traps are all unchanged —
the arc changes only HOW DURABLY the boundary is committed, never WHAT is
extracted. No rar5-expert consultation is required (the standing
clean-room/black-box posture applies as always); the interop gate is the
format-legality proof that nothing moved. Pack-side rows must stay
byte-identical (encoder untouched — the free regression signal).

## 2. The revised crash-consistency contract (the deliverable)

Two granularity levels. `entry` is the shipped v1.24 contract, byte-for-byte
unchanged in behavior. `batch` is the opt-in revision.

### 2.1 Granularity `entry` (default — unchanged)

Per extracted file:
1. the journal record is **fsynced before the temp exists** (durable-first);
2. the temp data is **fsynced before the commit rename**;
3. the commit is an **atomic no-follow rename**;
4. the journal is closed + unlinked at zero in-flight temps; the next run's
   sweep validates every record and deletes journal-referenced temps.

Guarantees: a destination is never partial (rename atomicity); committed
data survives power loss; every crash orphan is journal-referenced and
swept; forged journals can only name this build's temp shape inside the
journal's own directory.

### 2.2 Granularity `batch` (opt-in — the revision)

Per extracted file:
1'. the journal record is **appended before the temp exists** (the
    durable-first ORDER is preserved) but the record sync is **deferred to
    the next boundary** — a boundary is every 32 record appends, journal
    eviction under the LRU cap, and session teardown (each boundary syncs
    the journal);
2'. **no explicit temp-data flush**: data durability is the OS writeback's —
    the same class the reference extractors (UnRAR/WinRAR: write + close)
    provide;
3'. atomic no-follow rename — unchanged (rename remains the commit point);
4'. the session's journals stay open + locked for the session (LRU cap 64;
    an evicted journal is synced, closed, and unlinked; teardown syncs,
    closes, and unlinks all), so a crashed session's journal is recovered by
    the next run's sweep exactly as today.

### 2.3 What survives a power loss, at every point (batch mode)

| crash point | destination files | temp files | journal |
|---|---|---|---|
| mid-entry (temp dirty) | previous content, or nothing | in-flight temp; its record reached the file but may not be durable | earlier records per last boundary |
| between boundaries (N committed) | the last ≤window commits are present, contents = whatever writeback completed before the power loss — possibly missing, complete, or torn | none for committed entries (rename consumed them); ≤ parallelism in-flight temps | records not yet synced may be lost |
| after a boundary | everything committed before the boundary: journal-valid; contents = writeback state (still NOT forced) | ≤ parallelism in-flight temps | records durable |
| normal completion (teardown) | present; contents = writeback state (NOT forced — documented) | none | synced, closed, unlinked |

**What the sweep recovers (batch mode):** identical validation semantics —
a temp whose record reached the disk is deleted by the next run's sweep;
an unsynced record's temp becomes an **unreferenced orphan**. The orphan
exposure is bounded by **in-flight parallelism** (≤1 sequential, ≤ workers
parallel), NOT by the window: a committed entry's temp was consumed by its
rename and cannot be an orphan. Unreferenced orphans are inert files in this
build's exact temp shape; they are never pattern-swept (SECURITY_ARCHITECTURE
§3.3 stands — a forged journal can still only name candidates the engine
itself would create, and the sweep's validation is unchanged); cleanup for
them is documented as manual, and they are reported by nothing (they cannot
be distinguished from pre-planted files without violating the no-pattern rule).

**What weakens, for whom, what the user sees:** only crash durability of
committed data (and of the last window's journal records) weakens, and only
for the surfaces where the user or integrator explicitly opted in (§4).
Atomicity, orphan-sweep coverage for referenced temps, containment, the
cancel contract (§4 of invariants: rename remains the commit point; cancel
observed after the rename is ignored), per-entry failure isolation, exit
codes, and the displayed ≡ extracted invariant are all unchanged. The chosen
granularity is machine-surfaced (`--json-summary` `durability` field) and
human-surfaced (switch echo in the run banner area + docs), never silent.

### 2.4 Why no time-based window and no boundary data-flush

Time-based windows are hostile to deterministic failure-matrix tests (a
timing-dependent batch is a timing-dependent contract). Data-flushing at
boundaries was measured (§0: flush-after-rename = flush-before-rename) and
declined: it preserves the big-file cost that the arc exists to recover,
while still weakening the journal guarantee — the worst of both shapes. The
shipped shape is the simplest one the measurements support: the window is a
**journal-sync cadence** (32 records), and data durability in batch mode is
writeback class by construction.

## 3. En-route finding: the non-contained commit path is not atomic on this host

While building the probe's rename-through-handle helper,
`SetFileInformationByHandle(FileRenameInformationEx, class 13)` — the call
`FileStream::commit_rename` uses — was found to fail with
ERROR_INVALID_PARAMETER (87) **unconditionally on this host** (NTFS,
Win11 26100): every flags variant (0/1/3), anchored-parent and full-path
forms, raw and FileStream handles (tools/ren_iso.cpp bisect). The direct NT
call the containment path uses (`NtSetInformationFile`,
`FileRenameInformationEx = 65`) succeeds on the same handles. Consequence:
`commit_rename`'s "unsupported capability" fallback classifies 87 as
unsupported and silently drops to `MoveFileExW` — correct results, but the
non-contained path (tests, DLL `durable_write_to`, any `AtomicWriter::open`
user) runs the documented NOT-atomic fallback on this machine, and has been
since v1.24. The containment path (the CLI extraction engine) uses the NT
call and is unaffected.

Disposition: rolled into this arc as a prerequisite fix — `commit_rename`
tries the NT call first (the containment path's proven call), keeping the
kernel32 class-13 attempt and the `MoveFileExW` fallback chain behind it for
genuinely unsupported filesystems. Without this, the durability contract
this arc revises would rest on a commit that is not the atomic rename it
claims to be on this host. The probe's pipeline numbers above price the
entry-granularity column through the fallback path; the real extraction
path's per-entry cost is the same class.

## 4. Exposure shape — decision

**Default-off; opt-in via `--durability=batch` (long form) / `-db` (short);
`--durability=entry` / `-db-` re-pin the default explicitly. Kill switch
`OPENRAR_NO_BATCH_DURABILITY=1` forces entry granularity and is surfaced
(the run reports the override). `--json-summary` gains a session-level
`durability` field (`"entry"` | `"batch"`).** The `-ds` letter was rejected:
WinRAR allocates it ("Do not sort files while adding to a solid archive",
Rar.txt:961) and a solid-add script passing `-ds` must not silently change
meaning; `-db` is unallocated in both switch spaces.

Rationale. A default flip would be a security regression today: the revised
contract is proven by the failure matrix (process-kill injection everywhere
the OS allows), but true power-loss injection is not CI-reproducible on any
leg (Risk Register 6 honesty), and the data-durability claim of batch mode
("writeback class") is precisely the part no test can fully certify — it is
disclosed, not proven. The v1.38 precedent (measured levers shipped; the
rest recorded) applies: the contract is proven to the extent the OS allows
us to prove it, shipped behind an explicit switch, with the default
revision explicitly deferred. The switch is not dead code: it is the
documented policy surface for backup-restore and bulk-extraction workflows,
it carries the kill switch and the JSON field, and the failure matrix makes
it a supported, tested mode. A future default flip needs: field soak of the
opt-in mode, the same failure matrix, and a new Gate 0 that re-argues the
default with the then-current evidence.

Per-surface policy (the v1.21.1 trace, settled here):

| surface | policy | mechanism |
|---|---|---|
| CLI `x`/`e` | switch-controlled | reader policy → session |
| CLI `t` | N/A — writes nothing (decode+verify only) | verified by absence |

| DLL file-mode handles | **entry granularity, unchanged** (per-call `durable_write_to` session; no export added) | documented in invariants §5 |
| DLL frozen `openrar_archive_extract_file_to_path` | direct-write, untouched | verified by absence |
| WASM | N/A — in-memory | by construction |

  claim is corrected — the v1.38 pattern (measured-and-declined is an

## 6. Security posture

The default path is untouched code (§4 trace) — the v1.24 contract keeps
its named tests green as-is. The batch path adds no parsing surface, no
format surface, no new allocation class; its fault hooks only ADD failures
or crash the process under env keys documented as test-only. The sweep's
forging resistance is untouched (same-directory + exact-shape + CRC
validation, now also exercised under batched records). The one semantic
deletion — the pre-rename `FlushFileBuffers` — exists ONLY behind the
explicit opt-in, is disclosed in three places (switch echo, JSON field,
docs), and can be overridden by the environment kill switch at any layer.

## 7. RAM invariant (docs/invariants.md §2)

Batching buffers no entry data: the temp stream is unbuffered OS writes
exactly as today; the journal gains ≤64 held journals + record bytes (tens
of bytes per record). Peak process memory delta: kilobytes. The OS page
cache holds more dirty data for longer in batch mode (OS-managed,
reclaimable; the same class of exposure every heavy writer has) — disclosed
in the contract, not a process-memory change.

## 8. Scope

In: §5 M1–M5, the §3 rolled-in commit fix. Out: any default-behavior change
beyond the opt-in switch (no default flip), any journal-record format
change (the v1 format is kept — sweep compatibility is preserved), any
change to solid-chain/decode/two-phase logic, any encoder change, O_TMPFILE
+ linkat orphan elimination (the extraction_journal.hpp post-1.24 note —
recorded, not this arc), time-based windows (§2.4), boundary data-flushes
(§2.4).

## 9. Architect Challenge Review (mandated before code)

**Plan reviewed:** v1.39.0 durability batching — the extraction crash-consistency

**Architect verdict:** 🟡 CONDITIONAL APPROVAL — revisions required before

### 9.1 Executive summary

The plan is unusually strong for a security-normative arc: the founding
premise is decomposed and measured (§0), the contract revision is stated as a
two-level granularity with explicit survival semantics (§2), the exposure
decision is default-off with a kill switch (§4), and the failure matrix is
first-class (§5 M3). The measured decomposition correctly identifies THREE
price components where the roadmap named two, and the flush-after-rename =
flush-before-rename measurement is the load-bearing finding that locks the
design away from boundary data-flushes.

The plan is approved conditionally. Six implementation directives (D1–D6)
must be recorded as binding before M1 begins. None reopens a locked decision;
each closes a gap between the contract as stated and the code as it exists.

### 9.2 Critical red flags

**R1 — `release_temp` is unconditionally destructive in batch mode.**
`ExtractionSession::release_temp` (extraction_journal.cpp:452) closes and
unlinks the directory journal whenever `in_flight` drops to zero. The plan
(§2.2, item 4') requires journals to be "held for the session (LRU cap 64)"
in batch mode. If `release_temp` is not made policy-conditional, batch mode
degrades to today's per-entry lifecycle and the entire performance claim
collapses — the journal would be re-created per entry exactly as it is today.
This is the single highest-risk implementation detail in the arc.

**R2 — LRU eviction has no backing data structure.**
The current `journals_` is a `std::map<std::filesystem::path, DirJournal>`
(extraction_journal.cpp:111) with no access-order tracking. The plan
specifies "LRU cap 64; an evicted journal is synced, closed, and unlinked"
but does not name the eviction structure. A correct LRU requires a separate
access-order list (e.g., `std::list<path>` with map iterators) — a
non-trivial addition that must be specified before implementation.

### 9.3 Weak assumptions and fragile invariants

**A1 — Boundary sync mechanism unspecified.** `append_record`
(extraction_journal.cpp:283) always calls `f.sync()`. The plan defers the
sync to "every 32 record appends, journal eviction under the LRU cap, and
session teardown" but does not specify whether `append_record` gains a
`sync` parameter or whether a separate deferred-append path is added. The
mechanism must be named.

**A2 — Flush elision spans four call sites, not two.** The plan (§5 M1)
names "AtomicWriter::commit paths and FileStream::commit_rename/
commit_rename_in/POSIX path". The actual flush sites are:
  1. `FileStream::commit_rename` (file_stream.cpp:423) — `flush()` before rename
  2. `FileStream::commit_rename_in` (file_stream.cpp:495) — `flush()` before rename
  3. `AtomicWriter::commit` POSIX containment path (extraction_journal.cpp:751) — `stream_.flush()` before `anchored_rename`
  4. `FileStream::commit_rename` POSIX path (file_stream.cpp:598) — `flush()` before rename
All four must gain the `flush_first` parameter (default true = today).

**A3 — NT-first fix must preserve the full fallback chain.** The current
`commit_rename` chain is: kernel32 class-13 → MoveFileExW. The §3 finding
is that kernel32 class-13 fails with GLE=87 on this host. The fix is
NT-first: `NtSetInformationFile(class 65)` → kernel32 class-13 → MoveFileExW.
The plan says "keep kernel32 + fallback chain behind it" — correct, but
the directive must be explicit that the kernel32 attempt is retained for
filesystems where the NT call is unavailable but kernel32 succeeds (the
reverse of this host's failure mode).

### 9.5 Actionable revision directives (binding before M1)

**D1 (critical):** `ExtractionSession::release_temp` must become
policy-conditional. In `batch` mode, `release_temp` is a no-op for journal
lifetime (the journal is held for the session; only the in_flight counter
decrements). In `entry` mode, behavior is unchanged. Record this directive
in the M1 implementation notes.

**D2 (critical):** The LRU eviction structure must be specified before
implementation. Recommended: a `std::list<std::filesystem::path>` as the
access-order queue + the existing `std::map<path, DirJournal>` storing
list iterators. On `register_temp` for an existing key, splice the key to
the back of the list. On insert, push to the back. On eviction (size > 64),
pop the front, sync + close + unlink that journal. Record the chosen
structure in the M1 implementation notes.

**D3 (required):** The boundary-sync mechanism must be named. Recommended:
`append_record` gains a `bool sync_now` parameter (default true = today).
In batch mode, `register_temp` calls `append_record(..., false)` and
increments a per-journal pending counter; when the counter reaches 32, the
journal is synced and the counter resets. Eviction and teardown sync
unconditionally. Record the chosen mechanism in the M1 implementation notes.

**D4 (required):** All four flush sites (A2 above) must gain a
`flush_first` parameter (default true). In batch mode, `AtomicWriter::commit`
passes `flush_first=false` to `commit_rename` / `commit_rename_in` and skips
the explicit `stream_.flush()` on the POSIX containment path. Record the
parameter signature in the M1 implementation notes.

**D5 (required):** The NT-first fix in `FileStream::commit_rename` must
preserve the full chain: `NtSetInformationFile(class 65)` →
`SetFileInformationByHandle(class 13)` → `MoveFileExW`. The kernel32
attempt is retained for filesystems where the NT call is unavailable but
kernel32 succeeds. Record the chain order in the M1 implementation notes.

**D6 (required):** The failure-hook placement must be specified.
`OPENRAR_TEST_BATCH_CRASH_AFTER=N` kills the process after the Nth
`register_temp` call in batch mode (before the boundary sync — the kill
point is deterministic). `OPENRAR_TEST_FAIL_JOURNAL_SYNC=N` fails the Nth
journal sync (not the Nth record append). Both hooks are no-ops in entry
mode. Record the placement in the M2 implementation notes.
