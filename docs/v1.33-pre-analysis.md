# v1.33.0 Pre-Analysis — Candidate Source and Block-Table Reuse (Gate 0)

Arc: "the m1/m3 ratio gap is a candidate-source gap, not a parse gap." Base:
v1.32.0 (tag `v1.32.0` @ 70f9b2c). Branch `arc/v1.33.0-candidate-source`.

Clean-room basis unchanged: `docs/spec` + `RAR5-FORMAT.md` for the format.
Mechanisms are derived from the published format plus our own measurements.
Outside analysis informed the *hypothesis set*; §3 records what it contributed
and exactly which of its claims were checked, refuted, or left unverified. No
reference implementation source or disassembly was consulted, per
`ARCHITECTURE.md` §1.2.

---

## 0. Gate 0 statement

**Claim:** the standing ratio gap to WinRAR (m1 17.6%, m3 2.8%, m5 3.0%) is
caused by *which candidates our encoder can express*, not by how it chooses
among them. Three specific deficits are named and each is independently
addressable without changing the parse: (1) we cannot emit a 2-byte match, (2)
we source candidates only from one hash-chain walk per position plus a fixed
four-distance rep scan, and (3) we re-emit all four Huffman tables every block
when the block header already carries a bit that suppresses that.

**Conditional approval requested, in three tiers.** Tier 1 (table reuse, clamp
fix) is independent of every open question and is approved outright. Tier 2
(length-2/3, sparse probes, the lazy ring) is approved as measured experiments
with per-item gates. Tier 3 (any parse) is **not** approved; it is explicitly
out of scope until the Tier 2 measurements land and the T9 premise is settled
(§4.6).

**The wire format is untouched by Tier 1 and Tier 2.** Every token they add is
one the decoder has always decoded. Legality proof remains the 24-stage interop
gate plus cross-engine decode (UnRAR 7.20 / WinRAR 7.20). The m3
non-regression bound and the v1.31-regression bound (zeros artifact ≤ 3,514 B,
m5 speed lead) remain standing.

### 1.3 What the parked arc measured, and the isolation that reframed it

`arc/v1.32.0-optimal-parse-parked` (`04408fb`) built a rolling forward DP over
`{literal, match, rep0..3, 257}`, priced from the previous block's real Huffman
code lengths. Measured at m3: code −1.95%, text −1.39%, random tie, runs/zeros
+28%, time ~3.9x against a 1.42x budget.

**The un-isolated `compress_tests` failure is now isolated**, and it changes
what those numbers mean:

- It is T9's pure-addition assertion (`tests/unit/compress_tests.cpp`,
  "suppressed-257 output drifted from v1.30.4 reference bytes").
- It fires on **zeros1m at m3 only**. text64k, rand256k and mixed match
  byte-exactly at both m1 and m3.
- **All eight cases decode byte-exact**, including the drifted one. The DP output
  is valid RAR5; nothing is corrupt.
- Cause: `dp_should_enable()` enables the DP for m3 unconditionally
  (`compressor50.cpp:1797-1802` on that branch — `{false,false,false,true,…}`)
  and the 257-suppression test helper does not disable it, so the DP rewrites
  token choice inside a path whose invariant is "suppressing 257 reproduces
  pre-M1 bytes exactly".

Two consequences, both load-bearing:

1. **T9's premise is structurally incompatible with any m3 token-selection
   change.** The gate exists to prove 257 was a *pure addition*; any parse change
   at m3 voids that proof by construction. This is a test-design decision to
   settle before Tier 3, not a hash to refresh — and it is why the parked
   branch's claim of being "a CORRECT engine with an honest measurement" is not
   supportable.
2. **The single drifting corpus is the run-heavy one, with 257 suppressed.**
   That is the runs-pricing failure appearing directly in a controlled A/B
   rather than being inferred. And on the other three corpora the DP reproduced
   greedy's choices byte-for-byte — so the −1.95% / −1.39% wins did not come
   from these inputs at all. The parked branch's headline numbers should not be
   cited as evidence for a parse until re-derived.

Arithmetic that supports the same conclusion independently: 8 MiB of zeros at the
512 KiB block quantum is 16 blocks at ~26 B of table description = 422 B, which is
exactly the number measured. The token payload rounds to zero, so that gate was
measuring table overhead, not parse quality.

## 2. The central question — and why it is open

**Can an encoder that never emits a 2-byte match, never probes a short context,
and re-tabulates every block be within 2.8% of WinRAR by better parse
selection — or is the gap in the candidate set itself?**

It is open because both readings survive the existing evidence. The descoped
arc's own conclusion was that the gap is "structural in the finder"; that
conclusion was drawn from a branch whose ratio numbers §1.3 has just shown to be
unreproducible from its own test corpora. The finder-side reading is therefore
*unfalsified* rather than *established*, and Tier 2 is designed to falsify it
cheaply.

The decisive cheap test is item 6: count length-2 and length-3 tokens in a
reference m1 stream against its m3 stream. If m1 carries them and m3 does not,
the two methods are structurally different parsers and the m1 gap is a parse gap
of a kind we have not built. Ten minutes; it gates a six-week arc.

## 3. Outside input, and what we could not verify

Part of the hypothesis set entered from outside this tree — an analysis of the
format and of our measurements rather than a derivation from our own sources.
Recorded honestly because two of its claims did not survive checking against our
tree:

**Refuted against our tree:**

- *A decompiled reference encoder exists in the working tree, containing both
  parsers.* No decompilation exists in this repository or any of its worktrees;
  the only sources are our own clean-room code. `ARCHITECTURE.md:12` forbids
  reverse-engineered source trees and `docs/spec/00-overview.md:3` is written so
  the format can be implemented without the reference implementation. The advice
  to read the mechanism directly is therefore both factually wrong and outside
  our provenance standard.
- *Literals are `LD` symbol + 8 raw bits.* `docs/spec/03-compression-m1-m5.md:105`
  already specifies a literal as `LD` Huffman only, 0–255. The error was in the
  input, not in the spec or the code. The *economics* point survives and is
  valuable — two short symbols can beat one literal symbol, and a length-only
  arbiter never compares symbol counts (§1.2) — but it is not a defect.
- *Q8: the LDD predicate is wrong.* Our emitter is already correct
  (§1.2). This was a confirmation, not a fix.

**Accepted as a hypothesis, not as specification.** The remaining mechanism
descriptions — the ~20-candidate per-position list, three sparse-context probes,
a recency list, the static log2 cost expression, the length→distance ring, the
table-reuse bit economics — are internally consistent and plausible, but they
are second-hand. We are not reading the reference binary. Each is therefore in
this arc an **experiment with a gate**, sized so that being wrong costs days, not
weeks, and so that no Tier 2 item is a precondition for another unless the
measurement says so.

**One claim is explicitly flagged as low-confidence** and gates
Tier 3: that the reference selects its shortest-path parse for the two lowest
methods via a `(method − 1) < 2` test. It is consistent with three independent
observations but is unverified. Item 6 confirms or kills it.

## 4. Candidate designs, argued honestly

### Design A — Block splitting with table reuse (Tier 1) — **BUILT, MEASURED, NOT INTEROPERABLE**

**Result: negative. Do not re-derive this.** The rule was implemented, gated, and
then removed because **both** reference oracles reject the output. The full
detail is in §10; the short form:

Block header flag bit 7 is "tables present" (spec/03). Our decoder has always
honoured it being clear (`decompressor50.cpp:417`, `:577`) while the encoder
hardcoded `0x80`. The rule — omit the table description when the freshly built
code lengths are **bit-identical** to the ones the decoder holds — is safe by
construction and does exactly what it claims on our own decoder.

Measured win, real and reproducible: 64 MiB of zeros, 128 blocks, **3,616 B →
3,392 B (−6.2%)**, with reuse firing on 32 blocks. On random data it fires on 15
of 16 blocks. So the arithmetic is sound and the mechanism works.

It is still not shippable, because the interop gate is this project's legality
proof:

| corpus | our decoder | UnRAR 7.x | WinRAR `Rar.exe` |
|---|---|---|---|
| 64 MiB text, m1/m3 | pass | **pass** | pass |
| random 512 KiB – 2 MiB | pass | **pass** | pass |
| zeros 1/4/16 MB | pass | **pass** | pass |
| zeros 20 MB | pass | pass | — |
| zeros **24 MB and above** | **pass** | **FAIL** (checksum) | **FAIL** (checksum) |

Our decoder round-trips every one of these. Both oracles fail from 24 MB of
zeros upward, at every method. A self-consistent-but-unreadable stream is worse
than no change, so the item is removed rather than gated around.

**Two things this raises, both more valuable than the 6.2%:**

1. **Our decoder's handling of bit-7-clear blocks is undertested against
   real-world data.** We implemented the reuse *read* path from the spec and
   never validated it against a stream written by anyone else — RAR's writer
   appears never to emit bit 7 clear, so there was no corpus. Self-roundtrip
   proves our encoder and decoder agree; it cannot prove either matches the
   format. If a third-party writer does emit reuse, we may mis-decode it. That
   is a decoder-side risk worth its own investigation, and it is the one thing
   here that outlives the negative result.
2. **Reuse behaves as a detector.** It surfaced a disagreement between our
   encoder+decoder and both oracles on long runs at ≥24 MB. Self-roundtrip
   tests cannot see that class of bug by construction. Whether the underlying
   issue is in our long-run encoding, in the reuse semantics, or in the oracles
   is unresolved — but "our tests pass" was demonstrably not sufficient evidence
   of correctness here.

Note the follow-up from the measurement below is also dead with the item:
capturing the remaining run-case table overhead needs the reuse bit, so it needs
a different lever entirely (a content-adaptive block-size controller would still
help, but it cannot be justified by a mechanism that does not interoperate).

### Design B — Length-2 and length-3 match support (Tier 2) — **SHIPPED**

`MIN_MATCH = 3` → 2 for m1–m3, 3 for m4/m5 (per-method, set in
`init_match_params`). 64 MiB text corpus: **m1 −1.49%, m2 −1.64%, m3 −0.04%,
m4/m5 byte-identical.** m4/m5 keep 3 because admitting short matches measured as
a *regression* there (+0.05%) — their depth-128 walk means a 2-byte match almost
never survives length arbitration and only costs table pressure.

**Who can emit the class is the important part.** The finder hashes four bytes and
only indexes positions with four bytes available, so **a chain walk can never
return a length-2 fresh match**. The reachable form is the **rep token** — the
rep scan compares bytes directly and has no length floor. So the shipped win is
a rep-path win, and length slot 0 on the LD-match table remains unreachable until
a finder that produces short matches exists. Measured, in `T12` and
mutation-checked.

### Design C — Sparse 1/2/4-byte context probes (Tier 2) — **BUILT, MEASURED, REJECTED**

Implemented as specified: two direct-indexed tables holding the most recent
position per 1- and 2-byte context, probed at every position, measured with the
same `rep_length()` the rep scan uses, competing with the chain match on equal
terms. (The 4-byte probe is not a new capability — `head_` already is a
4-byte-context most-recent-position table, which is what the chain walks from.)

**It regresses.** 64 MiB text, against the same tree without probes:

| variant | m1 | m2 | m3 | m4 | m5 |
|---|---:|---:|---:|---:|---:|
| probes admit ≥2 | **+0.76%** | +0.16% | −0.01% | +0.00% | 0% |
| probes admit ≥3 | **+0.67%** | +0.09% | −0.01% | +0.00% | 0% |
| probes ≥3, literal-rescue only | **+0.67%** | — | −0.01% | — | — |

Three gates were tried; all regress m1. The mechanism is the arc's own thesis
turned against the change: **selection is by length only, so an injected
candidate cannot be priced.** A fresh match must also pay for a distance symbol,
and at m1 the DD table is sparse — few distance symbols used means each one has a
long Huffman code — so every probe both costs more than the literals it replaces
*and* inflates the DD table that prices it. Restricting probes to positions with
no chain match does not help, which locates the loss in the literals-vs-match
comparison rather than in displacing chain matches.

This is the strongest evidence yet for the arc's central claim: the
ratio gap is not a shortage of candidates, it is an **arbiter that cannot price
them**. Adding candidates to a length-only arbiter makes ratio worse. That is
also why Design B's rep-path win is real (a rep needs no distance symbol, so its
cost is genuinely comparable) while Design C's fresh-match win is not.

Two incidental findings worth keeping: a fixed `core::uint64[65536]` member
overflowed the stack, because `Compressor50` is stack-allocated on worker
threads — the probe tables must be heap-allocated like `head_`. And probes were
never maintained on the large-window path, where `head64_`/`prev64_` already
dominate memory.

### Design D — Length→distance ring for the lazy step (Tier 2) — **REFUTED BY REASONING, not built**

The proposal: record every admitted `(length, distance)` at the current position
so the lazy test can look up "a distance yielding length `L−1` at `cur_+1`"
instead of paying a second chain walk.

It does not work against our lazy step, and the reason is structural. The ring
would be populated from the candidates the walk at `cur_` already produced — and
`best` **is** the maximum of exactly that set. So the best length derivable at
`cur_+1` from the ring is `best.length − 1`, at the same distance. The steal test
is `(next_len − inc) > (len − inc) + 1`; substituting the ring's best gives
`best.length − 1 > best.length + 1`, which is false for every input. The ring can
therefore never satisfy the steal criterion, so it never replaces the walk.

The proposal only carries information if the lazy step asks a *different*
question than ours does. Ours asks "is there a strictly better match at the next
position", which genuinely needs a fresh search. Refuted without building it.

### Design E — The parse, re-scoped (Tier 3) — NOT APPROVED THIS ARC

The descoped DP failed on architecture, not on bugs: it priced rep edges as rep
edges (state-coupled prices) and priced from the previous block's real code
lengths (a parse↔table fixed point that produces a cold start, stale prices and
an unused-symbol penalty). The proposed alternative is a static cost
function that never reads the tables, with a band-limited length ladder anchored
at each candidate's maximum, no state in the price, and one shallow chain call
per position.

**Not approved.** It is gated on three things that do not exist yet: item 6's
token count, Design B/C/D's measurements, and a settled T9 premise (§1.3).
Approving it now would repeat the descoped arc's actual mistake — committing to
a parse before establishing that the candidate set is what is missing. If item 6
says m1 and m3 are the same kind of parser, the honest answer is that the gap is
in the finder and Tier 3 never opens.

## 5. Failure modes

1. **Silent length corruption (highest severity).** `add_match` clamps the
   encoded base length into `[2, 4097]` while the decoder reconstructs
   `base + increment(d)`. An out-of-range `(len, dist)` therefore decodes to a
   **different length** — a one-byte desync, not a rejection, detected only by a
   CRC at end of file. The decoder validates nothing: no length-range check, and
   an out-of-window distance zero-fills rather than failing. The greedy loop
   guards it; any new candidate path (B, C, E) does not until we make it
   impossible. **Fix in Tier 1**, structurally: make the match API take the base
   length plus the distance and derive the covered length internally, so there is
   no quantity left to clamp. Filter, never clamp. Negative test asserts
   `len == base + increment(dist)` after *every* match emission, not just the
   greedy path's.
2. **Table-reuse predicate wrong in the profitable direction.** Reusing tables
   that have moved degrades ratio and, worse, can be silent. Needs an explicit
   drift measure and a bound, not a timer.
3. **A 257 emitted on a stale state.** Guarded by the shadow contract, but Design
   D's ring introduces a new way for a pending length to disagree with what the
   shadow believes. Any mismatch must fall back to the walk.
4. **Streaming identity broken.** Every item must be byte-identical for
   adversarial `feed()` chunking, and per-block state must survive the solid
   chain.
5. **Short-match admission outrunning the distance increment.** Length 2 at a
   distance > 0x100 is illegal by the same predicate as the clamp. B and C share
   this surface; one guard, one test.

## 8. Challenge invited on

1. **Is `increment(d) + 2 ≤ len ≤ increment(d) + 4097` the complete
   admissibility rule, or is a lower bound missing for the rep path specifically?**
   Rep lengths use a different length alphabet (RD, 44 slots) and we have not
   verified that the same predicate governs it. If it does not, Design B's guard
   is wrong on the rep side and we would not know from our own suite.
2. **Does Design A's win survive on mixed data, or is it a runs-only effect that
   inflates the headline?** A runs-only win is still worth having but is a much
   smaller claim than "the block quantum was mis-chosen", and the ROADMAP entry
   should not overstate it.
3. **Is the ~26 B/block table estimate right for our own table emitter, or was
   it assumed?** If our emitter emits tables more
   cheaply than assumed, Design A's payoff shrinks proportionally.
4. **Does admitting length-2 matches make the RD table so busy that Design A's
   win is cancelled?** B and A interact; §4 Design B says so, but the
   interaction has not been measured.
5. **Is `MIN_MATCH` load-bearing anywhere we have not looked** — WASM builds,
   the CDC chunker, the parallel compressor's chunk geometry? A global constant
   change with a per-target memory story behind it deserves more than one grep.

## 9. Challenges 1 and 5 resolved against the tree

**Challenge 5 — answered.** `MIN_MATCH` has exactly three uses, all in
`compressor50.cpp`: `:593` (finder result rejection), `:1410` (rep arbitration),
`:1440` (fresh-match emission), defined at `compressor50.hpp:194`. Nothing in
WASM, the CDC chunker, `parallel_compressor.cpp`, or the chunk geometry reads
it. The change is local to the compressor.

**Challenge 1 — answered, and the answer corrects Design B.** The predicate does
**not** govern the rep path, and must not:

- Fresh match: the decoder **adds** the increment back
  (`decompressor50.cpp:867-878`), so the wire carries `base` and the decoder
  reconstructs `base + increment(d)`. `add_match` correctly subtracts it and
  rejects when `length <= inc` (`compressor50.cpp:710-715`); the decision loop
  guards and clamps at `:1446-1449`.
- Rep: the decoder does **not** add any increment — `len = slot_to_length(...)`
  and `last_length_ = len` with no adjustment (`decompressor50.cpp:901-903`).
  `add_rep`'s comment at `:762-763` states this mirror and it is correct.

So rep lengths are stored increment-free on both sides and need no lower-bound
guard. Design B's admissibility guard applies to the **fresh-match path and to
any new distance-producing candidate** (Design C's probes), never to rep tokens.
Adding one there would reject legal rep tokens.

**This also refutes one of the imported claims.** It held that the decoder
"validates nothing — no distance-vs-window check (out-of-window distances
zero-fill rather than fail)". Our decoder hard-fails: `if (distance == 0 ||
distance > win_size_) return false`, on both the fresh-match path
(`decompressor50.cpp:882`) and the rep path (`:896`, both credited to report
M6). What survives from that claim is only the **length-range** half: the
decoder reconstructs `base + increment` with no range check, so a clamped base
does silently decode to a different length. Failure mode 1 stands; its severity
is "hard-fail at the CRC" rather than "zero-fill and drift", because our own
decoder catches the distance half.

## 10. Design A in full — the interop evidence

Recorded because the negative result must not be re-derived from scratch, and
because two of its findings outlive the item.

### What was built

`write_block` gained a `tables_reusable` predicate: bit-identical `LD/DD/LDD/RD`
code lengths against the previous block's, tracked in `prev_len_*` and recorded
at the *end* of `write_block` (after the empty-block early returns, which write
no table). On reuse, `emit_table()` is skipped and flag bit 7 cleared. Reset at
`begin_archive`, `start_file`, and `begin_stream`.

Exact equality is the safety argument, not caution: a block's tokens are encoded
with the tables just built, so any table the decoder does not literally hold
mis-decodes the payload. Identical lengths imply identical codes, so reuse is
free when it applies. A `T11` test walked the block headers and pinned "first
block always carries tables" plus "the rule is not inert".

### What it measured

- 64 MiB zeros, 128 blocks: **3,616 B → 3,392 B, −6.2%**; reuse on 32 blocks.
  (The 3,616 B baseline was measured in-tree by disabling the predicate, not
  read from the docs — the documented 3,514 B matches neither figure.)
- Random 512 KiB: reuse on 15 of 16 blocks.

### Why it was removed

A clean A/B on the same tree, 24 MB of zeros at m3:

| build | archive | our decoder | UnRAR | WinRAR `Rar.exe` |
|---|---:|---|---|---|
| reuse disabled | 3,616 B | pass | **pass** | **pass** |
| reuse enabled | 3,392 B | pass | **FAIL** | **FAIL** |

Threshold found by bisection on runs: 1/4/16 MB pass, 20 MB passes, **24 MB and
above fail**, at m1, m3 and m5. 64 MB of *text* passes at both methods, so it is
neither archive size nor block count — it is long runs specifically. A trace of
the encoder's per-block state showed the window size varying between blocks
(2/4/8 MiB) with reuse firing at identical positions in the passing and failing
builds, so the divergence is not attributable to a single block's state.

Two scoping guards were tried and are *not* the fix: disabling reuse on
carried-window streaming sessions fixed a solid-chain failure (Track 1) and
disabling it for multi-member instances fixed a CDC failure (Track 9), but the
long-run failure above survives both. Both guards are recorded because they were
real distinct failures, not because they are load-bearing now.

### Methodology warning

Part of this investigation was spent chasing a phantom. The interop gate
**silently falls back to an existing binary when its Release build fails**, so a
compile error in the change under test produced a run that appeared to test the
new code but actually re-ran a stale binary containing an earlier, broken state.
That produced a non-monotonic result (adding a guard appeared to *cause* a
failure that had been an artifact) and sent the investigation after a
nonexistent flake in `test_track1_solid_mixed`, whose input is
`os.urandom`-derived. Before trusting any negative gate result, confirm
`build/openrar64/Release/openrar.exe` is newer than the sources.

| B - length-2 matches | **shipped** 15da796 | m1 -1.49%, m2 -1.64%, m3 -0.04%, m4/m5 byte-identical |
| A - block table reuse | **rejected** 5c16571 | real -6.2%, but UnRAR *and* WinRAR mis-decode long runs >=24 MB |
| C - sparse context probes | **rejected** | m1 +0.67% at best of three gates |
| D - lazy length->distance ring | **refuted** | the ring's information is subsumed by best; cannot satisfy the steal test |

**The hypothesis is half-confirmed and the headline is wrong.** The ratio gap is
partly a candidate-source gap: Design B found real ratio (-1.5% at m1) in a token
class we could not express at all. But -1.5% against a 17.6% gap is ~8% of it,
and it came entirely from the rep path - the cheap path, where no distance symbol
is needed.

**The more decisive result is Design C's failure.** The candidate source was
expanded exactly as proposed and ratio got *worse*, because the arbiter selects on
length alone and cannot price an injected candidate. That is direct evidence, on
our own corpus and our own code, for the arc's central claim - and it reframes
the remaining work: the missing capability is not candidates, it is **cost-aware
selection**. Which is Tier 3, which this arc does not open.

**So: Tier 3 stays shut, now for a measured reason rather than a procedural one.**
The descoped arc failed because its price model was state-coupled and read the
previous block's real tables. Design C shows the same lesson from the other
direction - a *static* price is the minimum viable fix, and it is still a parse
change requiring its own Gate 0, the T9 revision settled first, and the
token-count test that says whether the reference even parses differently at m1.

### Item 6, answered indirectly

The plan's cheap decisive test was to count length-2/3 tokens in a reference m1 vs
m3 stream. We answered it from our own side instead, which turned out to be more
actionable: enabling length-2 on our encoder moved m1 by -1.49% and m3 by -0.04%.
If the reference's m1 advantage came substantially from a token class we could not
express, we would have expected a much larger m1 movement than that. So the
reference's m1 lead is **not** mostly short matches - and the direct token-count
measurement is worth running anyway, but as confirmation rather than as a gate.

The least-confident claim in the hypothesis set - that the reference selects a
shortest-path parse for the two lowest methods - remains unverified. Design C's
result is consistent with it: if the reference prices its tokens, it can afford
candidates that we cannot.

### 10a. Second attempt at Design A, and why it is dead for a different reason

A fresh reading of the decoder rules concluded the reuse idea is legal (the decoder's rule is
literally 'bit7 clear = do nothing, keep current tables'), so the optimisation was
rebuilt with those corrections: compare against the last description
ACTUALLY EMITTED (not 'the previous block'), force a description on the first
block of every non-solid member, and keep DD/LDD/RD sizes in lockstep with the
table size. Two candidate mechanisms from that reading were checked and refuted
before they cost time:

- *'The DD size flips on dictionary rounding, not on >4 GiB, which is why 20 MiB
  fails and 16 MiB passes.'* Refuted arithmetically: 1 MiB is exactly 4 x 256 KiB,
  so EVERY whole-MiB test size (1, 4, 16, 20, 24, 64) is an exact multiple of
  256 KiB. The proposed rule assigns all of them the same version code and cannot
  discriminate the passing cases from the failing one. Our own DD size is 64
  throughout this matrix anyway.
- *'BlockSize can exceed the 16 MiB ceiling.'* Already refused: write_block
  returns false rather than emit a block of 0x1000000 bytes or more.

It then reproduced exactly, and the mechanism turned out to be neither candidate.
Interop result on 64 MiB of zeros, method 3:

| build | reuse | threads | archive | UnRAR |
|---|---|---|---|---|
| A | off | 1 | 3,616 B | pass |
| A | off | 2 | 3,616 B | pass |
| B | on | 1 | 3,506 B | pass |
| B | on | 2 | 3,392 B | **FAIL** |

Reuse is safe single-threaded and broken multi-threaded, and **MT on its own is
fine** - which is the control that makes this attributable to reuse rather than to
MT. The reason is in our own code: parallel_compressor.cpp:251 gives each MT
chunk min(cfg_.win_size, seed_len + data_len()), so the final, smaller chunk
compresses under a SMALLER DICTIONARY than the one its member declares. Per the
review, per-chunk dictionaries are not expressible inside one member - each chunk
would have to be its own member with its own file header and its own mandatory
first table description. The decoder parses every description with the DD size
implied by the member header, so a chunk that built its tables under a different
dictionary is already divergent, and a bit-7-clear block removes the description
that would have let the stream resynchronise.

**And the win is in exactly the configuration that breaks.** Measured with the
corrected implementation:

| corpus | threads | reuse | archive | vs no-reuse |
|---|---|---|---|---|
| 64 MiB text | 1 | on | 2,173,003 B | -0.07% |
| 64 MiB zeros | 1 | on | 3,506 B | 0% (reuse never fires) |
| 64 MiB zeros | 2 | on | 3,392 B | **-6.2%, and corrupt** |

So the honest summary is: single-threaded, the optimisation is safe and worth
almost nothing (-0.07% on text, nothing on runs, because run tables genuinely
differ per block); multi-threaded, it is worth 6% and produces archives neither
oracle can read. Design A stays removed.

**The finding that outlives it.** Our MT encoder varies the dictionary between
chunks of a single member. That is a latent conformance divergence in its own
right, independent of table reuse - harmless today only because distances never
reach the difference and the DD alphabet size does not change below 4 GiB. It
should be fixed on its own terms (one dictionary per member, as the format
describes), and until it is, no optimisation that depends on a member's tables
being stable can be enabled on the MT path.

### 10b. An independent format description, and what verification did to it

An independent clean-room format description (a separate RAR reader/writer
project's format documentation, derived from 7-Zip and XADMaster rather than from
any proprietary source) was checked against the same questions. Its value here is
as a second reading to be verified, not as authority - and verifying it
overturned two
things, including one of this document's own conclusions.

**Corroborated.** Bit 7 is 'table present'; clear means reuse the previous
tables. Reuse requires tables to exist: a decoder starts a non-solid stream, and
the first file of a solid group, with none loaded, and must refuse a first block
that clears bit 7. That matches decompressor50.cpp:577 exactly. The corpus also
records that RAR 7.12 and UnRAR 7.20 both fail such a stream - with a data
checksum failure rather than a structural one, i.e. they decode against whatever
their table memory holds. Our refusal is the safer of the two behaviours.

**Refuted - and this overturns the MT conclusion in 10a.** That corpus states in
its overview section that 'the algorithm bit in the block header selects' the
distance-alphabet size (64 vs 80). Its own block-header flag table, four sections
later, lists bits 0-2, 3-4, 5, 6 and 7 with **no algorithm bit at all**. The
document contradicts itself, and there is no per-block signal on the wire.

Deciding it from the tree rather than the prose: decompressor50.cpp:238-239
selects 430 vs 446 from the member's declared dictionary, and the encoder uses
the matching rule; the corpus separately records that real RAR selects its
larger-dictionary algorithm only above 4 GiB, which is our rule. So our handling
is right, and the 'algorithm bit' sentence is wrong.

**Therefore the 10a explanation for the MT failure is also wrong.** It rested on
per-chunk dictionary variation at parallel_compressor.cpp:251. But every
chunk's window is clamped to min(cfg_.win_size, chunk size), so a chunk is
never LARGER than the dictionary its member declares: distances stay in range,
and the DD alphabet size is fixed for the whole member on both sides. The clamp
is safe, and is in fact a memory saving. 10a over-claimed, and the roadmap entry
has been corrected.

**The MT mechanism is therefore still unidentified.** What is established:
reuse is safe single-threaded and broken multi-threaded; MT alone is fine; the
failure is content-dependent (zeros fail, text passes at the same thread count,
and text is where tables rarely repeat identically); and the win exists only in
the broken configuration. The next experiments are the cheap ones - count reuse
blocks per configuration and see whether failure tracks the count, confirm blocks
are concatenated in stream order, and separate 'multi-threaded' from 'multiple
chunks' by forcing a single chunk at threads > 1.

### 10c. Third attempt, and the conclusion that our bit-7 model is incomplete

A third implementation followed the corrected invariant exactly: keep a
MEMBER-LEVEL slot holding the four length vectors of the last block that
actually EMITTED a description, compare reuse candidates against that slot,
update it only when bit 7 is set, clear it only at a member/session start, and
refuse reuse for any encoder that produces only part of a member (the
multi-threaded chunk workers). The corrected reading's side-effect hypothesis was refuted
first: a description reader writes only the four token tables, a scratch level
table used solely to decode that same description, and one sticky flag.

Results, 64 MiB of zeros at method 3, cross-checked against reference UnRAR:

| path | reuse | archive | our decoder | UnRAR |
|---|---|---:|---|---|
| multi-threaded chunk workers | off (by the new rule) | 3,616 B | pass | pass |
| single-threaded / streaming | on | **2,631 B** | **pass** | **FAIL** |

Two things fell out of this that correct the earlier record.

**The earlier 'single-threaded passes' was reuse being disabled.** The previous
attempt's predicate contained !streaming_, and the CLI's single-threaded path
for a large input IS a streaming session - so reuse never fired there and the
'pass' was vacuous. Removing the guard is what exposed the real failure. Reuse
has now been measured passing in exactly one configuration: where it does not
fire at all.

**'Our decoder passes' is not evidence of correctness here.** Our decoder
round-trips the 2,631 B archive perfectly while both oracles reject it. Since
our encoder only ever clears bit 7 when its four vectors match what it last
emitted, and a decoder's installed tables are by definition the last description
it read, the two should agree by construction. They do not. So the divergence is
in the MODEL, not the bookkeeping: either the encoder's notion of 'the vectors
I am encoding with' is not the vectors it writes into the description, or the
meaning of bit 7 clear is not what we believe.

**Leading suspicion, newly specific.** LD symbol 256 is the one token whose
meaning is genuinely unsettled: our docs/spec and our encoder treat it as the
filter marker, while the second reading retracted its own 'end-of-block' claim and then
described 256 as an in-band WINDOW/POSITION escape - a reserved symbol with a
table-independent code, excluded from the Huffman histogram - and noted that the
filter stream's own escape sits elsewhere, warning our label 'may be off by one
era'. Our filters do round-trip through both oracles, so whatever we emit is
producing a legal stream, but that is compatible with a mis-numbered symbol whose
escape happens not to fire on our inputs. If our LD alphabet disagrees with the
real one anywhere near 256, then make_tables is building and comparing length
vectors over a different symbol space than a real decoder uses - which would make
'identical' true here and false there, and would explain a reuse block that our
own round-trip accepts and no external decoder does.

**Disposition: Design A stays removed, for the third time, and the reason is now
recorded rather than guessed.** It is not a legality problem (the legality
analysis confirms
the construct is legal and that our MT design is legal in principle) and it is
not the chunk-boundary bookkeeping it appeared to be. It is that we cannot make
an emitted reuse block agree with an external decoder, and we cannot yet explain
why. Continuing to iterate on reuse without first settling symbol 256 and
re-validating our table construction against a real decoder's would be guessing.

## 12. RESOLVED — the failure was decoder-side slot seeding, and Design A is revived

The dead end §10c recorded did not last. The mechanism was found, and it
dissolves every remaining suspicion including symbol
256: **our streams were always well-formed.** The failure lives in a reference
decoder's *multithreaded driver*, which pre-scans block headers and hands each
block to a work item that owns a PRIVATE copy of the table state, initialised
empty, assigning blocks to the slots round-robin in batches of
`2 x decoder_threads`. A description seeds the slot it lands in; a bit-7-clear
block inherits whatever its slot accumulated; a reuse block landing in a
never-seeded slot decodes against empty tables and degenerates. This is a
behavioral model, confirmed entirely by black-box experiment — the `-mt`
splits, the seeding matrix, and the cap sweep (Entry 8); no reference
implementation source informs it. The full
measured record now lives in `docs/question-log.md`; what follows is the
summary.

Confirmed by experiment (`question-log.md` Entry 8):

- The same archives that fail under a multithreaded oracle **pass `-mt1` at
  every size and every configuration**. A stream defect would fail the
  sequential path too. This also retires §10c's symbol-256 suspicion: a wrong
  LD alphabet would break sequential decoders as well.
- The period is exactly `2 x threads`: forcing descriptions on the first `N`
  blocks fixes an `N/2`-thread decoder and nothing stronger.
- A periodic cap ("describe every K blocks") provably cannot work: a period
  populates a single residue class, and only the first `P` consecutive blocks
  cover all `P` slots. Every cap from 2 to 1000 failed; only never-reuse passed.

§10c's single-threaded "FAIL" is explained too: the oracle's default thread
count is load-dependent, so an unqualified `unrar t` ran the MT driver. Never
gate on `unrar t` without an explicit `-mt`. And 'our decoder passes' was
structurally blind for the simplest possible reason: our decoder is
sequential-only and never implemented the slot model at all.

**The shipped rule.** Emit descriptions on the first
`2 x MAX_DECODER_THREADS = 16` blocks of every member — 16 because decoder
worker pools cap at 8 threads — and treat every table-set change as a re-seed
event (a change refreshes exactly one slot). Reuse is unbounded between
changes. Implemented in `write_block` as `seed_remaining_`, reset at
`begin_archive`/`start_file`; validated 32/32 oracle checks across
`-mt1/2/4/8` on zeros (including both previously failing sizes) and on
heterogeneous input forcing a mid-member table change (Entry 22). The MT chunk
floor is raised to 16 MiB so a chunk amortises its re-seed; MT on zeros went
from 0.56x to 1.27x single-threaded throughput while shrinking 14.4%.

The investigation also surfaced one wire rule unrelated to threading, now in
the spec: **`BlockBitSize` does not bound token decoding** — reference
decoders consume the whole final payload byte as tokens, so block tails must be
byte-aligned (`question-log.md` Entry 4, spec 06).
