# OpenRAR v2.3.0 Implementation Plan — Adversarial Pre-Implementation Review

**Subject:** [`docs/milestones/v2.3.0-implementation-plan.md`](../milestones/v2.3.0-implementation-plan.md) (binding plan of record, self-contained for external review)
**Reviewer posture:** Adversarial (Red Team) — pre-implementation
**Method:** Line-by-line cross-check of every plan claim, constant, gate, and code citation against the shipped tree at HEAD (`162300a`), the tooling under `tools/`, and the governing documents (`docs/invariants.md`, `docs/v2.0-charter.md`, `docs/milestones/roadmap.md`, `docs/milestones/v2.2.0-implementation-plan.md`, `docs/reviews/review-master-plan.md`).
**Date:** 2026-11-08

## 1. Verdict

🟡 **NOT WATERTIGHT — conditional approval. The plan may not be executed as written.**

The plan's architectural thesis — zero dynamic allocation on the decompression hot path, fail-closed filter saturation handling, SIMD mechanical sympathy, and empirically gated kill switches — remains sound. The hazards it names (wildcopy overshoot, filter DoS, allocator-hook noise) are real and some are already mitigated in the shipped tree.

However, pre-implementation adversarial review against HEAD found three defect classes that block an unamended start:

1. **Factual drift:** several plan claims reference symbols, constants, files, and baseline attributions that do not match the tree the plan purports to describe.
2. **Stale scoping:** the plan re-proposes work already landed (VM-reserved windows, bounded filter queues, landed hypothesis fixes) without diffing against HEAD.
3. **Unrunnable verification:** the plan's proof mechanisms (ScopedAllocTracker, kill-gate instrumentation) are described but do not exist as specified.

**Blocking defects (must be amended before Chunk 1 begins):**

- F-1: `DecompressErrorCode::CorruptedArchive` does not exist.
- F-2: Filter-queue capacity in the plan (256) contradicts the shipped bound (65536).
- F-3: Zero-alloc tracker / `process_available` API do not exist as the plan sketches.

**High-risk findings (must be amended before the affected chunk begins):**

- F-4: W1 problem statement describes a pre-lazy `WindowBuffer`; much of W1 is already shipped.
- F-5: Invariant numbering/citation drift (I-15, `MAX_FILTER_BLOCK_SIZE`).
- F-6: Ratchet/baseline version attribution drift (v2.2.0 vs. recorded v2.1.1 ratchet vs. v2.0.23 comparison baseline).

**Structural findings (must be resolved during implementation):**

- F-7: Hypothesis register IDs are being reused for different hypotheses across plan/review/research documents.
- F-8: The plan is billed "self-contained for external review" while citing files that do not exist yet and invariants that are not recorded.

## 2. Factual Drift — Plan vs. HEAD

### F-1 (BLOCKING): `DecompressErrorCode::CorruptedArchive` does not exist

- **Plan references:** §2.2 mermaid fail-closed label (`Fail-Closed: CorruptedArchive`), §2.2 security bullet, §6 red-flag resolution.
- **Actual enum** — `src/compress/decompressor50.hpp:147-154`:

  ```cpp
  enum class DecompressErrorCode {
      Ok = 0, DictionaryTooLarge = 1, AllocationFailed = 2,
      InvalidInput = 3, LimitExceeded = 4
  };
  ```

- **Adversarial impact:** the plan's fail-closed rejection path cannot compile or be wired to the error surface as written. The fail-closed verdict must map to an existing code (`InvalidInput` or `LimitExceeded`) or a conscious internal-enum addition recorded as a decision.

### F-2 (BLOCKING): Filter-queue capacity contradicts the shipped design

- **Plan:** `FixedFilterQueue<256>`; fail-closed if `> 256` pending filters (`§2.2`, `§6`).
- **Shipped:** pending-filter saturation guard at `src/compress/decompressor50.cpp:1146` and `:1828`:

  ```cpp
  if (engine_.filters_.size() - engine_.filters_head_ >= 65536) return false;
  ```

  with the recorded rationale ("memory (65536 entries ~= 2 MiB) — large legitimately-filtered files emit one region"; `CHANGELOG.md:2764` notes the bound was raised 8192 → 65536 for exactly this legitimate case).

- **Adversarial impact:** adopting a 256-slot ring would *shrink* the DoS envelope and risk rejecting legal large-filtered archives. The plan must reconcile 256 vs. 65536 before writing any code.

### F-3 (BLOCKING): Zero-alloc verification design does not match the shipped API

- **Plan:** introduces `ScopedAllocTracker` in `tests/unit/tracking_allocator.hpp` and wraps an execution of `decompressor.process_available(chunk_ptr, chunk_len, is_final)`.
- **Actual state:**
  - No `ScopedAllocTracker` / `tests/unit/tracking_allocator.hpp` exists anywhere in the tree (repo-wide search).
  - `Decompressor50` exposes `decompress(...)` / `decompress_block(...)`; the incremental state machine lives on `StreamDecoder` (`src/compress/stream_decoder.hpp:21-68`) as public `feed` / `finish` / `take_output` / `reset` over private `process_blocks` / `process_buffer` / `retain_output`.
- **Adversarial impact:** the plan's verification snippet is not compilable as written, and the tracker scope (Decompressor50 only vs. StreamDecoder staging vectors vs. BitReader/error-string allocations) is underspecified.

### F-4 (HIGH): W1 problem statement is stale — much of the target state is already shipped

- **Plan (§2.1):** `WindowBuffer` starts at `INITIAL_WINDOW = 256 KiB` and grows geometrically via `vec_.resize`, claiming vector storage applies to windows ≤ 64 MiB.
- **Actual (`src/compress/decompressor50.hpp:83-89`):** on 64-bit native, a large window *reserves address space* (VirtualAlloc/mmap) and commits pages lazily; only small windows and 32-bit/WASM use a growable vector.
- **Adversarial impact:** the plan re-implements an already-shipped mitigation. Chunk 1 must be re-scoped as a diff against HEAD, not written as if the geometric-growth hazard were live.

### F-5 (HIGH): Invariant numbering and citation drift

- **Plan:** governs "Invariants I-1 through I-15" and introduces **I-15** (64-byte tail margin).
- **Elsewhere:** v2.1 plan → I-1..I-12; v2.2 plan, roadmap, research doc → I-1..I-14; `docs/invariants.md` → no I-15; `MAX_FILTER_BLOCK_SIZE` cited to `docs/invariants.md` §2 which does not contain it (the shipped code comment at `decompressor50.hpp:511-512` carries the same stale citation).
- **Adversarial impact:** the plan's governance chain is internally inconsistent and cannot be enforced until I-15 is actually recorded in `docs/invariants.md` and the numbering range is unified.

### F-6 (HIGH): Baseline / ratchet attribution drift

- **Plan (§0):** baseline is "Official frozen v2.0.23 release binary + **v2.2.0** deterministic size ratchet (`RATCHET_BYTES`)."
- **Actual:** `tools/release_regression_guard.py:57,145-155` — `BASELINE_VERSION = "2.0.23"`; ratchet values recorded at **2.1.1**; fail condition `cur_size > ratchet + RATCHET_SLACK_BYTES (64 B)` on any of the 30 deterministic cells; growth allowances in `KNOWN_SIZE_ALLOWANCE_PCT` relative to the v2.0.23 baseline.
- **Adversarial impact:** the plan's version attribution is wrong and the fail-closed arithmetic should be restated precisely.

### F-7: Test-count drift

- **Plan (Step 4.1):** "full CTest suite (all **55** test targets green)."
- **Evidence of drift:** 52/52 (v2.0.0), 53/53 (v2.0.1), 54/54 + 56/56 (v2.1/Linux), 49/49 (v2.22-era), 55/55 (v1.46); CI lanes use `--min-tests 20` and exclude sanitizer suites. The number "55" appears in multiple releases with no single canonical current count.
- **Adversarial impact:** the release step cites an unverified, drifting figure.

### F-8: Hypothesis-register drift (IDs reused for different hypotheses)

- **Plan H-10** = AVX2 batch hashing in `hash_range` → conflicts with the registered H-10 = `BitOutput::put_bits` vector-resize fix (now landed; source comment `compressor50.hpp:25`).
- **Plan H-11** = BMI2 + branchless Huffman decode → conflicts with registered H-11 = branchless log₂ in `price_fresh` (source comments at `compressor50.cpp:17,1052,1143` now record H-11 = hardware bit scans).
- **Plan H-12** = pipelined prefetch in `find_match` → conflicts with registered H-12 = prescan per-block heap allocation (now fixed via `TableLengths`; `decompressor50.hpp:288`).
- **Plan scope** omits H-13 (Inflate `window_copy`) and H-14 (BLAKE2sp 8-way) which exist in the master register, while re-numbering/re-purposing lower IDs.

- **Adversarial impact:** the plan's W2 reads like an open research arc, but the register shows most low-level items are already closed in the working tree.

## 3. Weak Assumptions & Unverified Claims — High Risk

### W-1: Zero-allocation proof scope is too narrow
The plan's tracker wraps the decompressor; it does not enumerate `StreamDecoder::in_queue_`/`output_`, `BitReader::buf_`, error-string allocations, or scratchpad state. The "zero alloc" claim must cover the full call graph or the invariant is vacuous.

### W-2: Kill gates lack measurement provenance
H-09 (≥15% decompression gain), H-10 (≥3% end-to-end), H-11 (≥10% branch misprediction), H-12 (≥4% prefetch gain) specify no benchmark identity, repetition count, environment disclosure, or integrated-vs-isolated measurement — contrary to Rule G-3 (Fingerprinted Measurement) and the charter's integrated A/B requirement (A-8).

### W-3: G-9 compliance for gates
No fail-closed behavior is specified for unavailable benchmark hardware (Apple Silicon, QEMU NEON, CI runners).

### W-4: Greedy-quality gate inputs underspecified
The four-binary arbiter set and the "zero static distance concessions (k)" measurement are not defined.

### W-5: WASM ceiling unverified in-plan
Invariant I-6's 1.5 MiB / 1.2 GiB figures should be re-checked against `docs/wasm-limitations.md` during implementation.

## 4. Structural Gaps

1. **Self-containment is overstated:** the plan points to `tests/unit/tracking_allocator.hpp` and `src/compress/arch/wildcopy_simd.hpp` (which does not exist — only `match_simd.hpp` / `match_avx512.cpp` are present under `src/compress/arch/`) as if they were context, then mandates their creation.
2. **The embedded architect challenge is self-review:** §6 is an internal review authored as part of the plan; it cannot serve as the plan's own adversarial gate. It should be a draft pending independent re-review.
3. **Release engineering scope thin:** Step 4.4 covers version bump only; CHANGELOG, regression-guard execution, interop gate, static analysis, and fuzz legs are not enumerated as gates.
