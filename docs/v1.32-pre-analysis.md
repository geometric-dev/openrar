## 0. Gate 0 statement

**Claim: emitted bytes are IDENTICAL at every method.** v1.32.0 is scoped as a
*scheduling and parallelism* arc, not a *parse* arc. The only lever that
changes bytes — the token parse — was measured this session and is known to
be unaffordable (`docs/ROADMAP.md`, descoped section: an optimal parse costs
~3.9x the finder time to buy ~2%). So this arc takes the position that the
remaining headroom is in **how work is divided**, not **what is emitted**.

The wire format is untouched, the decoder is untouched, m0 store is
bit-identical, and **T8-style byte-identity is the arc's primary safety
property** — not a fallback valve but the defining constraint. Legality proof
is unchanged (UnRAR + WinRAR decode our streams via the 24-stage interop
gate); the cross-engine risk is much lower here because output does not move.

**Conditional approval sought**, with the binding constraint stated up front:
*if the 2x target turns out to require match-level parallelism (which would
change bytes), the arc must stop and re-Gate rather than quietly absorb an
emission change.*

## 1. Current state (measured, v1.31.0 matrix, canonical 135.5 MB)

| Config | OpenRAR | WinRAR | OpenRAR lead |
|---|---:|---:|---:|
| `-m3 -mt1` | **8.43 s** | 16.47 s | 1.95x |
| `-m3 -mt4` | **5.72 s** | 7.43 s | 1.30x |
| ST→MT scaling | **1.48x** | 2.2x | — |

Facts this arc is built on, all measured:

1. **We are already 1.30x faster MT.** This arc is not about catching WinRAR
   on wall clock; it is about the *shape* of our curve, because the ST lead
   (1.95x) is exactly what a poor MT curve erodes. At 2.2x scaling the ST
   lead would be ~1.6x; the 1.95x ST advantage is the asset at risk.
2. **Chunking costs us no ratio at m3.** MT archive = 54.14 MB = the ST
   archive byte-for-byte. The canonical corpus's matches are short-range
   enough that splitting into 1–4 MiB chunks loses nothing. This is a
   *measurement on one corpus*, not a guarantee (§5, T-risk).
3. **The parallel path is chunk-parallel, not match-parallel**
   (`src/compress/parallel_compressor.cpp`): 1–4 MiB chunks, each compressed
   by an independent `StreamEncoder` with `chunk_win = min(win_size,
   chunk_size)`, workers clamped to 16, bounded in-flight memory. There is
   no shared match index and no cross-chunk match.

## 2. The central question — and why it is open

**Is our 1.48x limited by Amdahl (per-chunk fixed cost) or by bandwidth/ILP?**

This is the whole arc, and it is not answered. Two very different programs
follow from the answer:

- **If per-chunk fixed cost dominates** (table builds, window allocation,
  per-chunk warm-up, thread ramp): the fix is *scheduling* — larger chunks,
  fewer/longer-lived workers, amortized state. **Output stays identical.**
  Cheap, safe, and plausibly most of the gap.
- **If it is a parallel ceiling** (the finder's chains are inherently serial,
  and 4 workers already saturate memory): no scheduling change reaches 2x,
  and the only route is **match-level parallelism** — partitioning the hash
  chain search — which **changes output** and drags in the entire
  cross-engine interop burden and a new bit-exactness surface.

M0 exists to measure this before M1 writes any of it. Committing to a
2x-scaling program before knowing which regime we are in would repeat the
optimal-parse arc's mistake in a new place: designing for a ratio-shaped goal
when the binding constraint was elsewhere.

## 3. Candidate designs, argued honestly

### Design A — Scheduling (no byte change) [PROPOSED for M1]

- Tune chunk size against worker count (the 1–4 MiB clamp is unexamined; it
  was set for memory, not measured for scaling).
- Reuse a per-worker `StreamEncoder` across chunks instead of constructing
  one per chunk, so window/table state is not rebuilt N times.
- Amortize the per-chunk warm-up (each chunk pays a greedy warm-up block
  before its tables are useful — the same seam the descoped arc found).
- Load-balance the tail: the last chunk is a serial tail; at 135 MB / 1 MiB
  ≈ 135 chunks it is <1% — but at 4 MiB on a small file it is most of the
  work.

For: output identical by construction; no interop risk; attacks the regime
that §2 says is most likely.
Against: bounded ceiling. If we are in the parallel-ceiling regime, A might
buy 1.6x and not 2x.

### Design B — Match-level parallelism (byte change) [NOT PROPOSED this arc]

Partition the hash-chain walk across workers.

For: the only route to 2x if §2 says we're bandwidth-bound.
Against: **changes emitted bytes**, so it re-opens the whole interop
gate; needs a bit-exactness proof for the *merged* candidate ordering; a
chain partition is a *quality* trade (each worker sees a subset of
candidates), so the ratio cost is unknown and could eat the scaling win —
the same shape as the descoped arc. **Explicitly deferred**: if M0 says
this is the only route, that is a new arc, not a milestone here.

### Design C — Shared match index across chunks (byte change) [NOT PROPOSED]

Let chunk N read chunk N-1's match candidates so cross-chunk matches exist.

For: closes the ratio cost on corpora where it is NOT free (see T-risk).
Against: makes chunks order-dependent, which destroys the bounded in-flight
memory property and the deterministic per-chunk identity T10 currently pins.
Large blast radius, for a benefit §1 says is currently zero.

## 4. Failure modes

| New path | Failure mode | Behavior |
|---|---|---|
| A: scheduling | chunk size / worker count regress single-thread or small-file paths | gate ST unchanged; MT-only knobs, off the ST path |
| A: encoder reuse | stale per-worker state leaks across chunks (tables, rep-state, window) | per-chunk reset contract, pinned by a new test |
| A: warm-up amortization | cheaper warm-up → worse first block of each chunk | per-chunk size non-regression check |
| A: any | **emitted bytes drift** | T8 byte-identity across every method and chunk geometry; this is the arc's tripwire |
| B/C (deferred) | ratio regression from partitioned candidates | not in scope; would need its own FMM |

## 5. Risks

- **R1 — the 2x target is unreachable without changing bytes.** Then this arc
  ships a smaller scaling win and records that honestly (the v1.31-M2
  discipline). Pre-agreed: the arc does **not** lower the ST lead to buy
  scaling, and does not absorb Design B.
- **R2 — "no ratio cost from chunking" is one corpus.** 54.14 MB == 54.14 MB
  is a fact about the canonical corpus, not a law. On a corpus with
  long-range matches (large binaries, tarballs) chunking WILL cost ratio,
  and today's MT number is quietly worse than ST there. M0 must measure a
  long-range corpus before the arc claims "free".
- **R3 — scaling is measured on a 4-core host.** 1.48x on 4 logical cores
  says little about 8–16. The matrix harness must state the core count and
  not generalise.
- **R4 — memory.** Larger chunks raise per-worker footprint; the 16-worker
  clamp exists for this. Chunk-size work must respect it.

## 6. What this arc deliberately does NOT do

- It does not touch the token parse (measured, unaffordable).
- It does not re-open m5 depth or the m1 ratio gap.
- It does not accept a scaling win that costs the ST lead.

## 7. Challenge invited on

(ii) Is "output identical" the right binding constraint, or is it a

## 8. Gate 0 challenge verdict — the premise was wrong

Answering (i)–(iv) required looking at the code rather than the matrix, and
the arc's premise did not survive.

### 8.1 MT was effectively switched off

`archive_mutator.cpp:1406-1418` chose the path as:

```cpp
bool use_parallel = eff_threads > 1 && !solid_packer;
if (use_parallel && filter_cfg.mode != FilterMode::DisableAll) {
    use_parallel = Filters50::detect_filter(sample, ...) != FilterType::None;
}
```

`FilterConfig::mode` defaults to `Auto`, so the second branch always runs.
Combined with the parallel path forcing filters **off**
(`parallel_compressor.cpp:32-33`, `no_filters.mode = DisableAll`), the
selection was a double inversion:

- **no filter detected** → `use_parallel = false` → **sequential; no MT at
  all** — which is text, source code, and most real data;
- **filter detected** → `use_parallel = true` → MT, but with the filter it
  had just detected **discarded**.

The comment immediately above it stated the opposite intent ("if a filter
would trigger, take the sequential path so -mc is honored"). Confirmed
empirically: `detect_filter()` returns `None` for code, text, random and
binary-sequence inputs, i.e. every input tested takes the sequential branch.

So MT scaled 1.48x in the v1.31.0 matrix **without this path running** for
filter-free data. That matrix row is not a measurement of the MT encoder.

### 8.2 What the fix actually buys (M0, measured)

With the condition corrected to `detected == None`, on 24 MB of synthetic
text-like data with no long-range redundancy, `-m3`, 4 logical cores:

| | archive | wall | parallelism |
|---|---:|---:|---:|
| `-mt1` | 7,317,904 | 5.4–6.9 s | 0.9x |
| `-mt4` | 7,316,218 | 1.5–3.0 s | **2.1–3.8x** |

MT engages, scales **2.3–3.7x** (not 1.48x), at **−0.02% size** — chunking
is free on this data, as §1.1 predicted. The host was under load, so treat
the range as indicative, not a matrix entry.

This answers challenge question (i) empirically: the "1.48x curve" was never
the real curve. There was no Amdahl-vs-ceiling question to answer, because
the feature was off. M0's measurement obligation is discharged, and it
discharged differently than the arc expected.

### 8.3 The finding that matters more than the scaling

Chunking is **not** free in general, and the cost is unbounded. On a corpus
built by repeating one 4.25 MB file ten times (42.5 MB, maximally
redundant), ST with its 8 MiB window compresses to **141,956 B** while MT's
independent 2 MiB chunks produce **2,911,494 B** — a **20x** ratio
regression, and MT was also *slower* in wall clock.

So R2 is confirmed and is far worse than "chunking might cost a little on
long-range data": the MT path trades an **unbounded** amount of ratio for
speed, silently, on exactly the data where compression matters most
(backups, archives, deduplicated blobs, container images). The canonical
corpus happens not to exhibit it, which is why nobody measured it.

This is the arc's headline, and it reorders the work: making MT *faster* is
worth much less than making it **predictable**.

### 8.4 Verdict on the four challenges

- **(i)** Moot — the question was unanswerable because the subject was not
  running. M0 found a bug instead of an attribution, and the arc now has a
  real baseline.
- **(ii)** "Output identical" was the right constraint *as a safety
  property*, and the fix respects it for ST (the ST path is untouched). But
  it was applied to the wrong thing: MT's output was never going to be
  identical to ST's, and pretending otherwise is what hid the bug. Corrected
  reading: **ST output is the invariant; MT output is the thing that was
  never measured.**
- **(iii)** Chunk-parallelism is still the right frame, but the question is
  no longer "tune it" — it is "bound its damage" (§8.3) and then tune.
- **(iv)** The 2x target is now met incidentally (2.3–3.7x measured), and
  the ST lead is intact because ST is untouched. But a 2.3x speedup that can
  cost 20x ratio is not a win, and the arc should not ship it uncharacterised.

### 8.5 Scope this implies

1. **Fix the selection bug** (done, M1-a) — restores the intended behaviour.
2. **Characterise and bound the ratio cost** (M1-b) — the arc's real work.
   Options, in preference order: share a match index across chunk
   boundaries (changes bytes, Design C), bound the damage by declining MT
   when a redundancy probe says chunks will lose, or document it loudly and
   leave it opt-in. **This is the decision the arc still owes.**
3. Scheduling work (encoder reuse, throttle) stays in scope but is now
   second-order: scaling is already ~2.5x, and correctness of the
   enablement decision matters far more than the last 20% of speed.

### 8.6 M1-b outcome, and the finding that reframes the arc

The probe shipped (see the plan's M1-b) and the arc's decision is made. But
the measurement that mattered most was not the one the arc set out to take.

**Chunking's cost is unbounded, and it is a defect in OUR MT, not a property
of RAR5.** On the benchmark payload's code third (18 MB):

| | `-mt1` | `-mt4` | |
|---|---:|---:|---|
| WinRAR | 396,313 | 396,331 | **+0.005%** — MT is flat |
| OpenRAR | 428,242 | 3,855,663 | **+800%** — and 3x slower |

WinRAR's multi-threaded encoder does not lose those matches. Ours does,
because each chunk is compressed with no access to its neighbours. So the
honest statement is not "MT trades unbounded ratio for speed" — it is **"our
MT is 9.7x worse than WinRAR's MT on redundant input"**, which is a
competitive gap, not a tradeoff. It was invisible for two independent
reasons: the v1.31.0 matrix recorded MT == ST size only because MT was not
running at all (§8.1), and when it was switched back on, the canonical corpus
declined it, so the row looked fine.

**The canonical corpus cannot measure MT scaling.** Its code third is
deliberately repetitive (`make_bench_payload.py`: "repeated to exercise
long-range matches"), so the probe correctly declines MT there. The matrix
row is therefore *not* a parallel-scaling measurement: `-mt8` finishes in
2.26 s against `-mt1`'s 3.40 s with **byte-identical output**, which is the
sequential fallback being faster than the ST path, not four workers
compressing. Measured on the non-repetitive third alone (`text.txt`, 17 MB),
MT is a genuine **2.0x at +0.08% size**.

Both numbers belong in the matrix, and the release records them separately
rather than quoting the flattering one.

**The residual gap is documented, not hidden.** The probe cannot see
long-range matches spanning chunk boundaries when the input contains no
repeated 64 KiB window and is too small for the compression probe: the code
third *alone* regresses 9x (measured above), while the whole corpus is
declined safely. `test_parallel_probe_known_gap` pins it with that number so
it cannot regress silently.

**The fix is not more detection.** Three probe designs were built and
measured, and the general one costs more than it saves (on clean text it made
MT slower than sequential). The real fix is to stop losing the matches — give
each chunk a dictionary-only prefix of its predecessor. That changes emitted
bytes, so it is a follow-up arc, and it is the single highest-value item in
the roadmap.

### 8.7 The root cause, measured: chunk size IS the ratio lever

M2 was dropped as "second-order, scaling is already ~2.5x". That was wrong,
and the sweep that proves it is the most useful measurement in the arc.
Holding everything else fixed and varying only the chunk size, on the
benchmark payload's code third (18 MB, 4.25 MiB repeat period; ST 428,242 B,
WinRAR `-mt4` 396,331 B):

| our chunk size | our `-mt4` | vs our ST | time |
|---|---:|---:|---:|
| 2 MiB (the current cap) | 3,855,663 | +800% | 1.28 s |
| 4 MiB | 2,139,969 | +400% | 0.86 s |
| 8 MiB | 1,284,227 | +200% | 0.49 s |
| 16 MiB | 856,975 | +100% | 0.55 s |
| 24 MiB (a single chunk) | 428,228 | **0%** | 0.43 s |

The loss is *exactly* proportional to the number of chunk boundaries and
vanishes at one chunk. So the ratio is not a quality wobble that a probe can
absorb: **our MT resets the LZ dictionary at every chunk boundary, and the
requested `-md` window is silently truncated to the chunk size.** For a
redundancy period of P, roughly every chunk boundary inside a copy costs a
full re-compression of P.

Two consequences, and they are the arc's actual conclusions:

1. **M2 is not second-order, but it is not the fix either.** Chunk size is
   the lever that *exposes* the bug — the sweep bisects the dictionary reset
   exactly — so raising the cap reduces the symptom without repairing the
   cause, and it trades directly against parallelism (fewer chunks than
   threads means idle workers). The `min(4 MiB, …)` cap exists for memory
   (16 workers x 16 MB of `prev_`).
2. **The fix is to stop resetting the dictionary, not to enlarge it.** RAR5
   scopes the LZ dictionary to the **member**; blocks are framing and
   entropy-coding boundaries only. There is no format field expressing a
   block-independent dictionary, so resetting the window at a chunk boundary
   is a **conformance bug, not a tuning choice**. A decoder reading such a
   stream would misread it. (Verified in the other direction: our decoder
   extracts a WinRAR `-mt4` archive byte-exact, so the decoder is member-scoped
   and correct; the fault is confined to the encoder.)
   The encoder therefore needs per-thread contexts that each own a window
   *and* hash tables, seeded from the predecessor with
   `min(dictionary_size, member_offset) - 1` bytes of its tail, re-indexed
   position by position — sharing a window pointer is not enough, the index
   is the expensive part. Two constraints carry over from the encoder's
   existing structure and must be preserved: the prefill must be **post-filter**
   bytes taken from the predecessor's filtered window (never re-read from the
   file — silent corruption whenever a filter fires), and no block may open
   with a rep-distance or 257 (our per-chunk fresh state already does this).
   Acceptance target is WinRAR's, not zero: within a few tens of bytes of
   `-mt1` on redundant input, i.e. ~396,331 rather than 3,855,663.
