## 0. Gate 0 statement

**Claim: emitted bytes are IDENTICAL at every method.** v1.32.0 is scoped as a
*scheduling and parallelism* arc, not a *parse* arc. The only lever that
changes bytes — the token parse — was measured this session and is known to
be unaffordable (`docs/ROADMAP.md`, descoped section: an optimal parse costs
~3.9x the finder time to buy ~2%). So this arc takes the position that the
remaining headroom is in **how work is divided**, not **what is emitted**.

The wire format is untouched, the decoder is untouched, m0 store is
bit-identical, and **T8-style byte-identity is the arc's primary safety
property** — not a fallback valve but the defining constraint. Legality proof
is unchanged (UnRAR + WinRAR decode our streams via the 24-stage interop
gate); the cross-engine risk is much lower here because output does not move.

**Conditional approval sought**, with the binding constraint stated up front:
*if the 2x target turns out to require match-level parallelism (which would
change bytes), the arc must stop and re-Gate rather than quietly absorb an
emission change.*

## 1. Current state (measured, v1.31.0 matrix, canonical 135.5 MB)

| Config | OpenRAR | WinRAR | OpenRAR lead |
|---|---:|---:|---:|
| `-m3 -mt1` | **8.43 s** | 16.47 s | 1.95x |
| `-m3 -mt4` | **5.72 s** | 7.43 s | 1.30x |
| ST→MT scaling | **1.48x** | 2.2x | — |

Facts this arc is built on, all measured:

1. **We are already 1.30x faster MT.** This arc is not about catching WinRAR
   on wall clock; it is about the *shape* of our curve, because the ST lead
   (1.95x) is exactly what a poor MT curve erodes. At 2.2x scaling the ST
   lead would be ~1.6x; the 1.95x ST advantage is the asset at risk.
2. **Chunking costs us no ratio at m3.** MT archive = 54.14 MB = the ST
   archive byte-for-byte. The canonical corpus's matches are short-range
   enough that splitting into 1–4 MiB chunks loses nothing. This is a
   *measurement on one corpus*, not a guarantee (§5, T-risk).
3. **The parallel path is chunk-parallel, not match-parallel**
   (`src/compress/parallel_compressor.cpp`): 1–4 MiB chunks, each compressed
   by an independent `StreamEncoder` with `chunk_win = min(win_size,
   chunk_size)`, workers clamped to 16, bounded in-flight memory. There is
   no shared match index and no cross-chunk match.

## 2. The central question — and why it is open

**Is our 1.48x limited by Amdahl (per-chunk fixed cost) or by bandwidth/ILP?**

This is the whole arc, and it is not answered. Two very different programs
follow from the answer:

- **If per-chunk fixed cost dominates** (table builds, window allocation,
  per-chunk warm-up, thread ramp): the fix is *scheduling* — larger chunks,
  fewer/longer-lived workers, amortized state. **Output stays identical.**
  Cheap, safe, and plausibly most of the gap.
- **If it is a parallel ceiling** (the finder's chains are inherently serial,
  and 4 workers already saturate memory): no scheduling change reaches 2x,
  and the only route is **match-level parallelism** — partitioning the hash
  chain search — which **changes output** and drags in the entire
  cross-engine interop burden and a new bit-exactness surface.

M0 exists to measure this before M1 writes any of it. Committing to a
2x-scaling program before knowing which regime we are in would repeat the
optimal-parse arc's mistake in a new place: designing for a ratio-shaped goal
when the binding constraint was elsewhere.

## 3. Candidate designs, argued honestly

### Design A — Scheduling (no byte change) [PROPOSED for M1]

- Tune chunk size against worker count (the 1–4 MiB clamp is unexamined; it
  was set for memory, not measured for scaling).
- Reuse a per-worker `StreamEncoder` across chunks instead of constructing
  one per chunk, so window/table state is not rebuilt N times.
- Amortize the per-chunk warm-up (each chunk pays a greedy warm-up block
  before its tables are useful — the same seam the descoped arc found).
- Load-balance the tail: the last chunk is a serial tail; at 135 MB / 1 MiB
  ≈ 135 chunks it is <1% — but at 4 MiB on a small file it is most of the
  work.

For: output identical by construction; no interop risk; attacks the regime
that §2 says is most likely.
Against: bounded ceiling. If we are in the parallel-ceiling regime, A might
buy 1.6x and not 2x.

### Design B — Match-level parallelism (byte change) [NOT PROPOSED this arc]

Partition the hash-chain walk across workers.

For: the only route to 2x if §2 says we're bandwidth-bound.
Against: **changes emitted bytes**, so it re-opens the whole interop
gate; needs a bit-exactness proof for the *merged* candidate ordering; a
chain partition is a *quality* trade (each worker sees a subset of
candidates), so the ratio cost is unknown and could eat the scaling win —
the same shape as the descoped arc. **Explicitly deferred**: if M0 says
this is the only route, that is a new arc, not a milestone here.

### Design C — Shared match index across chunks (byte change) [NOT PROPOSED]

Let chunk N read chunk N-1's match candidates so cross-chunk matches exist.

For: closes the ratio cost on corpora where it is NOT free (see T-risk).
Against: makes chunks order-dependent, which destroys the bounded in-flight
memory property and the deterministic per-chunk identity T10 currently pins.
Large blast radius, for a benefit §1 says is currently zero.

## 4. Failure modes

| New path | Failure mode | Behavior |
|---|---|---|
| A: scheduling | chunk size / worker count regress single-thread or small-file paths | gate ST unchanged; MT-only knobs, off the ST path |
| A: encoder reuse | stale per-worker state leaks across chunks (tables, rep-state, window) | per-chunk reset contract, pinned by a new test |
| A: warm-up amortization | cheaper warm-up → worse first block of each chunk | per-chunk size non-regression check |
| A: any | **emitted bytes drift** | T8 byte-identity across every method and chunk geometry; this is the arc's tripwire |
| B/C (deferred) | ratio regression from partitioned candidates | not in scope; would need its own FMM |

## 5. Risks

- **R1 — the 2x target is unreachable without changing bytes.** Then this arc
  ships a smaller scaling win and records that honestly (the v1.31-M2
  discipline). Pre-agreed: the arc does **not** lower the ST lead to buy
  scaling, and does not absorb Design B.
- **R2 — "no ratio cost from chunking" is one corpus.** 54.14 MB == 54.14 MB
  is a fact about the canonical corpus, not a law. On a corpus with
  long-range matches (large binaries, tarballs) chunking WILL cost ratio,
  and today's MT number is quietly worse than ST there. M0 must measure a
  long-range corpus before the arc claims "free".
- **R3 — scaling is measured on a 4-core host.** 1.48x on 4 logical cores
  says little about 8–16. The matrix harness must state the core count and
  not generalise.
- **R4 — memory.** Larger chunks raise per-worker footprint; the 16-worker
  clamp exists for this. Chunk-size work must respect it.

## 6. What this arc deliberately does NOT do

- It does not touch the token parse (measured, unaffordable).
- It does not re-open m5 depth or the m1 ratio gap.
- It does not accept a scaling win that costs the ST lead.

## 7. Challenge invited on

(i) Is the Amdahl-vs-ceiling question in §2 actually answerable without a
prototype, or is M0 measurement a disguised implementation phase?
(ii) Is "output identical" the right binding constraint, or is it a
self-imposed limitation that forecloses the only route to 2x?
(iii) Is chunk-parallelism the right frame at all, given the canonical
corpus shows no ratio cost — is there a better use of this arc?
(iv) Should the target be 2x at all, given we are already 1.30x faster MT and
the real risk is erosion of a 1.95x ST lead that a modest scaling win
preserves anyway?
