## 0. Gate 0 statement (what changes, what the claim is)

**Emitted-stream claim:** for the same input, compressed payloads produced
at methods 1..5 change:

1. **Run-collapse tokens (slot 257):** the encoder will emit the
   repeat-last-length token (LD symbol 257) when the next position repeats
   the previous match's `(length, OldDist[0])` exactly. Today the encoder
   never emits 257 (verified: no emission path writes symbol 257;
   `add_match`/`add_rep` cover only 262+ / 258..261). Format-legality:
   `docs/spec/03-compression-m1-m5.md` token table row `257` ("Repeat last
   length — re-emit LastLength with OldDist[0]"); the decoder implements it
   (`decompressor50.cpp:813-831`).
2. **Match-finder change (m4/m5 only):** binary-tree match finder replacing
   the 512-deep chain walk at m5 (and 128 at m4). This changes WHICH matches
   are found (ratio and bytes), not what is legal. m1/m2/m3 keep hash chains
   with today's depth (m3 = 32), so m3's match selection — and its emitted
   bytes apart from (1) — is unchanged.
3. **Parameter re-tune (m1):** chain/nice/lazy table values may change after
   the full-matrix validation; wire format unaffected.

**Not changing:** m0 store payloads (bit-identical); headers; filters
(04-filters.md untouched); the block framing (`tokens≥32768` /
`inputSinceBlock≥0x80000`); dictionary/`Compression information` encoding;
decoder code paths (the decoder already handles every token the new encoder
can emit — see §1.3).

**Interoperability position:** every token the new encoder emits is one the
decoder already decodes and one WinRAR 7.20 demonstrably emits into streams
we decode byte-exactly (`w_zeros_m1` row in `tools/perf/results.json`,
cross-extraction verified). The cross-interop gate (UnRAR + WinRAR decoding
our new streams) is the legality proof, per the arc brief.

## 1. Current-state facts (verified this session, file:line)

### 1.1 The length-alphabet maximum is 4097(+3), not "~64 KB" — the arc
brief's premise is corrected here

The v1.30 perf write-up (PERFORMANCE.md §"Where the remaining gaps live",
m1/zeros bullet) states "RAR5's length field allows ~64 KB" and infers
"≈7,800 long-match tokens" in WinRAR's 0.02 MB zeros archive. **This
document corrects that: the RAR5 wire format cannot encode a single match
longer than 4100 bytes.** Evidence, all from clean-room sources:

- The LD alphabet is fixed at `NC = 306` symbols
  (`compressor50.hpp:179`, spec 03 §Huffman Tables): 256 literals, 1
  filter, 1 repeat-last-length, 4 rep-distance, **44 match-length slots
  (main slots 262..305)**. There is no wire symbol beyond main slot 305.
- Length decode (spec 03 §Length encoding; mirrored verbatim by the
  decoder `slot_to_length`, `decompressor50.cpp:374-387`): slot < 8 →
  length 2..9; else `LBits = slot/4 − 1`, length `2 + ((4|(slot&3)) <<
  LBits) + extra`. Max slot 43: `LBits = 9`, base `7 << 9 = 3584`, extra
  511 → **max 4097**. The distance-dependent increment (spec 03; decoder
  `decompressor50.cpp:867-873`) adds +1/+2/+3 → **absolute single-token
  maximum 4100 bytes**. RAR7 ExtraDist (`TABLE_SIZEX = 446`) widens the
  DISTANCE alphabet (DCB 64→DCX 80), never the length alphabet.
- Our decoder already accepts the full range with no clamp
  (`slot_to_length` has no upper bound; the alphabet itself bounds it) and
  the encoder already emits the full range: `find_match` caps the raw
  search at `MAX_LZ_MATCH + 3 = 4100` (`compressor50.cpp:524`) and
  `add_match` subtracts the increment before slot encoding
  (`compressor50.cpp:709-718`). **"Raise the encoder cap" is therefore a
  no-op — the cap equals the format maximum.**
- Decisive arithmetic on WinRAR's zeros archive: 512 MB at ≤4100 bytes per
  token needs ≥125,000 match tokens. Every full match token carries ≥10
  length extra bits + ≥11 distance extra bits (dist 4100 → dist slot 24,
  4 LDD bits + 7 raw bits) ≈ 25+ bits minimum → ≥390 KB. The archive is
  0.021 MB (`results.json` row `w_zeros_m1`). **No stream of 125K full
  match tokens can occupy 0.021 MB; the only RAR5 token with no extra bits
  beyond one Huffman symbol is 257** (repeat-last-length: spec 03 token
  table; decoder emits output for it without touching RD/DD/LDD or extra
  bits). 125K × ~1.3 bits ≈ 20 KB — matches the observed 0.021 MB.
  **Conclusion: WinRAR's zeros advantage is the 257 repeat mechanism
  (~1 bit per 4100 bytes), not long single matches.**
- **M0 evidence (EXECUTED this session, before any encoder change).** A
  64 MiB zeros file was archived with WinRAR 7.20 (`rar a -m1 -mt1`,
  archive 2,865 bytes) and decoded through our v1.30.4 `Decompressor50`
  compiled with a temporary env-gated token tracer (throwaway harness,
  never committed; raw traces preserved outside the repo). Extraction is
  byte-exact (SHA-256 `3b6a07d0…1351` matches the source). Token census:

  | Token class | WinRAR m1 zeros (2,865 B) | OpenRAR m1 zeros (23,989 B) |
  |---|---:|---:|
  | literals | 1 | 4 |
  | fresh match (LD 262+slot) | 512 — all slot 43, max length **4096** | 1 — slot 43, length 4097 |
  | **slot 257 (repeat last length)** | **15,871** (each re-emits 4096) | **0** |
  | rep0..rep3 | 1 | 16,379 (all rep0) |
  | max distance | 1 | 1 |

  Arithmetic: 512 + 15,871 + 1 = 16,384 tokens × 4096 B = 64 MiB ✓.
  **Prediction confirmed: 257 dominates; every length ≤ 4096 ≤ 4100; no
  long single matches anywhere.** Cost per 4096-byte step: WinRAR ≈ 1-2
  bits (one Huffman code, zero extra bits); ours ≈ 11 bits (LD(258) +
  RD(43) + 9 length extra bits). Ratio ≈ 8.4× — the observed 8× archive
  gap. Our side of the census (0 × 257) confirms §1.2: the encoder has
  no 257 emission path at all.

### 1.2 What our encoder does today on runs — the real zeros gap

`process_available` (`compressor50.cpp:1349-1423`) already prefers
rep-matches: at each position it tests `old_dist_[0..3]` and emits
`add_rep` when `rep_best_len + 1 > best.length`. On a zero run the
emitted sequence is (M0 census, 64 MiB scale): four literals, one fresh
match (len 4097, dist 1, slot 43), then rep0 chains — each rep0 costs
LD symbol + RD length slot + **9 length extra bits** (slot 43, `LBits=9`)
≈ 11 bits per 4097 bytes → for 512 MB, ~125K tokens × ~11.5 bits ≈
180 KB ≈ the observed **0.182 MB** (`o_zeros_m1`). WinRAR replaces the
same chain with 257 tokens at ~1-2 bits. **The 8x gap is fully accounted
for by rep0-vs-257; no format change is needed to close it — only
emitting a token the decoder has always supported.**

### 1.3 Decoder parity for slot 257 (what the encoder must mirror)

`decompressor50.cpp:813-831`: 257 outputs `last_length_` bytes from
`old_dist_[0]`; **does not rotate OldDist; does not change `last_length_`;
emits nothing when `last_length_ == 0`; fails the stream when
`old_dist_[0]` is unset/0/>window.** `last_length_` is set to the full
length **including** the distance increment on the 262+ path
(line 878) and **without** increment on the rep path (line 903); reset to 0
on non-solid file start; carried on solid. The encoder must therefore keep
a `last_length_`/`old_dist_` shadow mirroring exactly these rules —
including the solid carry (`begin_stream(continue_window=true)`) and the
per-file reset. This is the M1 correctness core; named negative tests pin
each rule (plan §6).

**Emission invariants (architect-challenge directives 1-3, binding):**

1. **Byte verification (P0):** the decoder's 257 path copies
   unconditionally — it never checks the bytes match. The encoder emits 257
   only when the current position's bytes at distance `old_dist_[0]` are
   *verified by comparison* (via `rep_length`) to match for at least
   `last_length_` bytes. Shadow-state equality alone is never sufficient.
2. **Coverage is exactly `last_length_`:** a longer actual repetition
   re-decides at the next position; there is no "257 with extra length".
3. **Rep0-only:** 257 reads `old_dist_[0]` — repeats whose distance is
   `old_dist_[1..3]` keep the rep-token path.

### 1.4 Match finder / effort slope facts

- Parameters: `chains {0,4,8,32,128,512}`, `nices {0,256,512,1024,2048,4096}`,
  `lazies {0,0,0,1,1,1}` per method (`init_match_params`,
  `compressor50.cpp:1135-1142`) — as the brief states.
- Finder: hash chains, `HASH_BITS = 17` (131,072 heads), 4-position batch
  insert, `prev_` one `u32` per window byte for small windows,
  `head64_/prev64_` (`u64`) for windows > 4 GiB (`begin_archive`,
  `compressor50.cpp:294-305`). Walk cost at m5 = 512 candidates/position
  with lazy re-search at cur_+1 — the 9.7x m3→m5 slope
  (85.61 s vs 8.78 s, PERFORMANCE.md method sweep) is consistent with walk
  cost dominating (chain depth 512/32 = 16x, plus nice_len effects).
- Default windows (dict_size=0, `archive_mutator.cpp:1160-1176`): m1 512
  KiB, m2 1 MiB, m3 8 MiB, m4 16 MiB, m5 64 MiB. Memory today at m5:
  `prev_` 64 MiB × 4 B = 256 MiB + heads.
- Filter interaction: matches are clamped to the active filter token
  region end (`rem < cur_max_lz` clamp, `compressor50.cpp:1321-1334`), so
  matches never cross the region the decoder un-transforms — the v1.21.25
  chunk-boundary contract. 257 emission must respect the same clamp
  (a 257 chain stops where a match would).
- FailCount skip heuristic is present (`compressor50.cpp:1336-1344`).
- WASM: the block codec IS this C++ class compiled by Emscripten
  (`src/wasm/wasm_api.cpp`; `wasm/README.md`) — currently ~70 KB against
  the 500 KiB budget (block codec) asserted by the wasm build gate. Code
  added by this arc is a few KB; the budget is safe unless large static
  tables are introduced (none planned). Runtime WASM memory follows the
  2 MiB default window (`compress_buffer` default) — tree arrays at that
  window are trivial.

- Golden fixtures: `tests/fixtures/golden/{mutator,writer}` +

## 2. Both sides, argued (the brief's challenge areas)

### (a) Run-collapse (257) emission now vs later

**Now (chosen).** The zeros loss is the single worst ratio number in the
matrix (8x) and the fix is small, format-legal, decoder-proven (our decoder
implements 257; WinRAR's own archive proves the token class decodes in
family), and independent of the finder work — it composes safely. It also
plausibly helps the m1 canonical gap (runs and repeats exist in text/code
corpora) at zero perf cost (fewer emitted tokens than the rep0 it
replaces). **Later** would split the compression-quality arc into two
arcs for no isolation benefit: the golden re-baseline cost is paid once
either way, and both changes alter the same streams.

Counter-side (recorded honestly): 257 emission changes bytes for ALL
methods, so it alone forces the full re-baseline + interop cycle; shipping
it without the finder means two golden re-baselines per version line if
the finder slips. Mitigation: the finder (M2) and re-tune (M3) are gated
into the same arc release; if M2/M3 slip, v1.31.0 ships with M1 only and
the re-baseline is still exactly one.

### (b) Binary-tree finder vs tuned chains for m4/m5

**Tree (chosen for m4/m5 only).** Chain-walk cost scales O(depth) per
position with a cache-miss per hop (512 hops × ~100 ns-class misses ≈ the
observed 1.5 MB/s). A binary tree examines ~O(log) nodes for the same
best-match quality (the tree maintains the same candidate set as an
exhaustive chain, ordered by position); expected walk reduction ~8-15x at
m5 against insertion cost ~2x — the only structure that beats the 9.7x
slope without lowering effort. Chains stay the m1/m2/m3 finder (32-deep
walk is cheap; replacing it would churn m3 bytes/behavior for little gain
— m3 is already 1.9x faster than WinRAR).

**Tuned chains (rejected as the primary, kept as fallback).** Cutting
depth at m5 (e.g., 512→128) recovers ~3-4x but is a ratio give-back the
method's contract forbids (m5 IS the effort method; PERFORMANCE.md shows
WinRAR m5 is also ~2% tighter — lowering effort widens that gap). Fallback
trigger: if the tree misses the M2 perf gate (m5 ≥ 2x vs current), tune
chains as the release fallback and re-scope the tree.

**Memory bound (directive-level constraint):** tree needs one extra
window-sized array (children0/children1 replace `prev_`; net +1 × 4 B per
window byte ≈ +256 MiB at the m5 default 64 MiB window; +64 MiB at m4's
16 MiB). Bound: tree only for windows ≤ 64 MiB and only methods 4/5;
explicit `-md` overrides keep chains if the requested window plus tree
arrays would exceed a documented ceiling (2 GiB process budget on 32-bit
is already guarded by `MAX_RETAIN`, `compressor50.cpp:272-281`). WASM
keeps chains: its 2 MiB default window makes the walk cheap, and artifact
budget hygiene says the block codec stays minimal.

**Bit-exactness (v1.22 lesson):** the tree is dispatch-independent —
candidate comparison uses the existing bit-exact
`arch::match_length_simd` — and one-shot/streaming/solid paths share
`process_available` verbatim, so parity tests across
{one-shot, streaming, parallel, solid-carry} × {scalar, SSE2, AVX2} pin
byte-identical output per method per input (the tree changes bytes vs
v1.30, never across paths of the same build).

### (c) Milestone split and sequencing

- **M0 — Gate 0 evidence + spec-doc corrections (no encoder code):**
  instrumented-decoder histogram of WinRAR's zeros archive (confirms §1.1
  prediction); PERFORMANCE.md m1/zeros bullet rewritten to the corrected
  root cause; spec 03 gets the explicit "+3 distance increment → single-
  token max 4100" note and the 257 encoder-shadow contract.
- **M1 — slot-257 run-collapse emission (all methods):** shadow state
  machine + emission + clamps; named negative tests (§6 of the plan);
  interop gate green; zeros row targeted ≤ 0.05 MB.
- **M2 — binary-tree finder for m4/m5:** memory-bounded, chains kept for
  m1/m2/m3 and >64 MiB windows; parity matrix; m5 ≥ 2x vs current.
- **M3 — parameter re-tune (m1 primary):** chain/nice/lazy sweep validated
  on the full matrix; m1 targets ratio ≤ 5% of WinRAR's (from 14%) at ≤
  current runtime.
- **M4 — re-baseline + docs + release:** golden re-baseline with
  UnRAR+WinRAR verification, PERFORMANCE.md + README perf rows, CHANGELOG,
  MINOR bump v1.31.0 (PATCH = commit counter from the v1.31.0 anchor).

Sequencing rationale: M1 first because it is independent, highest-ratio-
per-risk, and its golden re-baseline is unavoidable anyway; M2 second so
M3's tuning sweep runs on the final engine (tuning before the finder would
be invalidated by M2).

### (d) m3 non-regression strategy

m3 keeps hash chains (depth 32), its match-selection logic, and its lazy
heuristic unchanged; the only m3 byte changes come from M1's 257 emission
(cheaper tokens, no extra search work — strictly fewer Huffman bits for
repeated `(len,dist)`). Non-regression gates: (1) `perf_vs_winrar.py`
diff after M1 and after M2 — m3 ST median within noise (±3% protocol
spread) and m3 archive size not worse beyond noise; (2) `openrar_bench
--strict` kernel suites unchanged; (3) the M1 emission path adds O(1) work
per token (one comparison against the shadow) — no loop-structure change to
`process_available`, so no compile-level perturbation of the hot path.
If the m3 diff regresses beyond noise on any config, the release blocks
(M4 gate), and the default method stays m3 regardless.

## 9. Independent Challenge Pass (owner session, post-reconciliation)

🟡 **CONDITIONAL APPROVAL — five directives, all applied to the plan in
this revision; none structural.** The core design survives adversarial
review: the 257 shadow semantics mirror `decompressor50.cpp:813-911`
exactly, the decoder is untouched, and the FMM/negative-test registry is
complete (Pillar-7 screen: clean after the additions below).

1. **257 rides inside the rep-win branch, not a new competition path.**
   Unconditional 257 preference would re-open the lazy/greedy surface
   the existing `rep_best_len + 1 > best.length` rule already
   adjudicates (a near-free 257 at `cur_` can shadow a longer fresh
   match at `cur_+1`). 257 now fires only where `add_rep(0)` would have
   fired and `rep_best_len ≥ last_length_` — a strictly cheaper encoding
   of the same decided span; lazy/FailCount interactions are inherited
   unchanged (plan §1 M1).
2. **Golden re-baseline moved M4 → M1** (resolves the contradiction with
   §2d): M1 changes m3 bytes, so the committed golden SHA256s fail from
   the M1 commit; re-baseline (cross-engine verified) happens WITH M1,
   M4 only re-verifies stability (plan §5).
3. **EOF-tail dest-clamp** added to T4: the decoder keeps `last_length_`
   pre-clamp; the byte-verification condition provably suppresses 257 at
   the clamped tail — now pinned by test.
4. **M2 solid-carry and OOM-notice hygiene:** tree child arrays join the
   `begin_stream(continue_window)` KEEP set explicitly; the OOM
   chains-fallback emits a visible `W:`-class notice (silently-degraded
   effort = fail-open); T8 wording pinned (per-engine ISA parity;
   streaming ≡ one-shot; parallel deterministic per chunk geometry).
5. **T3 covers both filter transform paths** (in-loop and
   `compress_buffer` pretransformed) — their region-remainder arithmetic
   differs.

Gate 0 status after this pass: **CLEARED for M1** (slot-257 emission).
M2 (tree finder) is conditionally approved with its pre-agreed kill

**Post-measurement refinement (R1 closed with data).** The first A/B on
an identical corpus (fingerprint `4909205a40387c4c`, v1.30.4 CLI vs M1
CLI, same host) measured the `>=` verification rule as written in
directive 1's first cut: solid m3 +52.9% wall time at flat size — the
fragmentation failure mode this review flagged: a 257 with
`last_length_ < rep_best_len` advances fewer bytes than the verified
span, and every intermediate position re-runs the full match search.
The rule is tightened to **strict equality** (`rep_best_len ==
last_length_`): longer spans take the rep0 (re-anchoring a longer
`last_length_`), shorter spans keep rep0, and 257 fires only on exact
continuations — bit-optimal (a 257 plus a re-decision never beats one
rep0 for the same prefix) and fragmentation-free. The zeros win is
unaffected (continuation spans are exact there by construction).
