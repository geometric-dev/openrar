## 0. Gate 0 statement: zero format surface (stated, then confirmed)

**The claim, explicitly:** v1.30.0 emits no new archive bytes and consumes
none differently. Concretely, the arc must not touch:

- `src/format/header_writer.cpp` / `header_reader.cpp` record layouts
  (no new extra-record types — the `FHEXTRA_XATTR` 0x08 set shipped in
  v1.27.0 stays closed; no new service headers; no field changes);
- `src/archive/archive_writer.cpp` / `archive_mutator.cpp` emission
  behavior (byte-identical output for identical inputs and flags);
- the extra-area, data-area, service-header, or encryption framing in any
  way;
- the transcoder's *reading* of foreign formats is v1.29's surface — this
  arc adds nothing to it.

**How the Gate 0 review CONFIRMS this rather than assumes it:** the
challenge reviews the arc's actual diff surface — expected touched paths
are a new `src/sandbox/` module (broker/worker), `src/cli/main.cpp`
(dispatch + sandboxed-mode wiring only), `src/api/` + `src/dll/` +
`src/wasm/` (static_asserts, docs, conformance harnesses — no signature
changes to existing exports), new `bindings/` SDK trees, `tools/` (corpus,
differential stage, signing/SBOM), `.github/workflows/` (only AFTER the
v1.29 rebase per the coordination rules), docs, and tests. Any diff hunk
inside `src/format/` or the writers' byte-emission paths is a Gate 0
violation by definition. The interop gate must stay green UNCHANGED
through development, and re-run WITH the v1.29 stages after the rebase.
The golden bytes (`tests/fixtures/golden` + `tools/check_golden.ps1`)
run green unchanged. The same three-legged confirmation as v1.28
directive 10 runs explicitly in the Release milestone.

**One deliberate exception to state up front:** the sandboxed worker does
not change what bytes are emitted, but it changes WHO emits terminal
output for a run (the broker, not the worker — the worker has no
console contract at all). The non-TTY degradation contract (v1.28 M3)
must hold byte-identically in sandboxed mode; that is a named test, not a
format claim.

## 1. Current-state facts (verified this session)

### 1.1 ABI surface inventory (the freeze inventory's raw material)

**Native DLL C ABI** (`include/openrar/openrar_dll.h`, installed public
header; `src/dll/openrar_dll.h` is a forwarding shim):

- **API version:** `OPENRAR_DLL_API_VERSION 1` (openrar_dll.h:62) —
  unchanged since v1.1.0 by policy (additive exports must not bump it;
  embedders probe with strict equality per dll-integration-spec §3).
- **Exports:** ~60, in families: version probes
  (`openrar_version`/`openrar_archive_version`/

  (`openrar_alloc`/`openrar_free` + `openrar_archive_alloc`/`_free`
  aliases — single malloc heap, pairing mandatory), block codec
  (`compress`/`compress2`/`decompress`/`decompress2`), streaming block
  codec (`openrar_stream_create/feed/finish/free` +
  `stream_set_progress`/`stream_set_cancel`), error state
  (`openrar_last_error`/`openrar_archive_get_error` — thread-local),
  buffer archive one-shot (`archive_list`/`_list_free`/`_extract`/
  `_extract_all`/`_create`), handle API (`archive_open`/`_open_ex`/
  `_close`/`_handle_list`/`_handle_extract`/`_handle_extract_all`),
  file helpers (`list_file`/`extract_file`/`_to_path`/`create_from_paths`/
  `create_to_file`), `_ex`/`_pw` listing with progress/cancel, file-mode
  handles (`open_file`, `handle_extract_to_path`, `handle_test`,
  `read_entry_region` behind bit 16), mutation
  (`delete_entries_file`, `add_files_file`), creation
  (`create_file`/`_ex`/`_opts`/`_opts_mt`), extended metadata
  (`handle_entry_ex` + `entry_ex_free`, `handle_entry_owner` +
  `owner_free`, `handle_info`), repair family (`repair`,
  `create_rev_volumes`, `add_recovery_record`), limits
  (`handle_set_limits`), capability probe (`openrar_abi_features`).
- **Feature-bit registry** (openrar_dll.h:72–111): bits 0–16 assigned,
  each annotated with the version that shipped it; bit 17+ free.
  Registry convention: "assigned only when the gated exports ship" —
  the freeze doc records the registry verbatim and the next-free-slot
  rule (17), NOT speculative reservations.
- **Error enum** (openrar_dll.h:122–164): `RAR_OK=0`,
  `RAR_ERR_PARTIAL_OK=1`, negatives −1..−15 with **−8 and −10
  intentionally reserved** (documented in-header, binary-compat reason);
  **next available slot −16** (documented at openrar_dll.h:162).
- **Public structs (packed, fixed-size):** `openrar_archive_entry_t`
  64 B (openrar_dll.h:203–216), `openrar_entry_ex_t` 48 B (:659–672),
  `openrar_entry_owner_t` 20 B (:703–709), `openrar_archive_info_t`
  24 B (:725–735). `_pad` in the 64-byte entry is reserved by the shared
  WASM contract ("consumers must zero") — widening it is a documented
  non-goal (dll-enhancement-plan §5).
- **Calling conventions:** `OPENRAR_DLL_CALL` = `__cdecl` on Windows,
  default elsewhere; never `__stdcall`/COM (spec §3). Export macro
  `OPENRAR_DLL_API` dllexport/dllimport/visibility (openrar_dll.h:32–46).
- **Ownership conventions:** every `out_ptr` freed by caller via
  `openrar_free`/`openrar_archive_free` (never raw free/delete); empty
  output = `nullptr` + len 0 — `malloc(0)` never relied upon

  nonzero, 0 = failure; handle-table pin returns `shared_ptr` so no lock
  is held across host callbacks (L12, abi_contract.hpp:176–211 and the
  header contract comment at :14–20); callbacks run on the calling
  thread, no DLL lock held; thread-local error strings valid until the
  next archive call on that thread (openrar_dll.h:166–171).
- **Shared contract core** (`src/api/abi_contract.hpp`): the canonical
  error enum lives in `buffer_archive.hpp`; `ArchiveEntryOut` is the

  `pack_entries` shares the list path verbatim between DLL and WASM
  (:100–126, u32 path-width guard with 64-bit intermediate, L17);
  `ThreadError` (:139) and `HandleTable<T>` (:176) are the two
  infrastructure pieces both ABIs compile.
- **Compile-time enforcement today:** dll_api.cpp:58–84 asserts the C
  enum's equivalence to the canonical enum for every code, the 64-byte

### 1.2 Library-mode containment: what "non-disableable" means today (verified)

SECURITY_ARCHITECTURE §5.1 requires library mode to keep "memory bounds
checking, entry-count caps, and path containment **strictly
non-disableable by embedders**". The current facts, which the freeze docs
must state PRECISELY (today's docs conflate two different limit layers):

- **The non-disableable floor (verified, exists):**
  `Decompressor50::MAX_STREAM_OUTPUT` is a compile-time constexpr
  allocation cap enforced in-flight (decompressor50.hpp:203–206,
  decompressor50.cpp:942/952); KDF iteration ceilings (`lg2_count ≤ 24`)
  are pinned at both header paths (test_kdf_cap_pinned); dictionary
  window caps are structural; path containment (§4.1 openat2/NtCreateFile
  walk) has **no disable switch** — `--no-mmap`/`OPENRAR_NO_MMAP`
  downgrades the read engine only, never containment; header-walk loop
  bounds and entry-count caps are internal. None of these is reachable
  by any embedder-facing call.
- **The caller-tunable layer (by design, tunable up to unlimited):**
  `ExtractionLimits` (extraction_limits.hpp:33–58) defaults every field
  to `UNLIMITED`, and the DLL export
  `openrar_archive_handle_set_limits` documents `UINT64_MAX` = unlimited
  (openrar_dll.h:310–314). This layer is NOT a containment boundary —
  it is the embedder's own resource budget.
- **The freeze documentation must draw this line explicitly** (which
  floors are absolute, which budgets are the caller's) and pin the floor
  with named negative tests (`library_mode_limits_non_disableable`:
  `set_limits(UINT64_MAX…)` cannot raise `MAX_STREAM_OUTPUT`, KDF, or
  window caps; `library_containment_no_disable_switch`: no flag/env/API
  turns off the §4.1 walk). §5.1's spirit is satisfied by the floor +
  the documented advisory; the challenge should confirm this reading and
  the §7.3 embedder guidance (self-sandbox) becomes a normative doc row
  in dll-integration-spec §13 and SECURITY.md.

### 1.3 Sandbox: what exists, what does not

- There is no process-level isolation of the parser today. The precedent
  pieces that exist: v1.23's SFX **Job Object runtime policy** (resource
  caps, mitigation policy attributes — a cap mechanism, not a privilege
  boundary), v1.24's **syscall-level containment** (the write side), and
  the v1.25 `io::ReadSource` seam (one scan code path for both engines —
  the natural place a worker's read side plugs in).
- The engine is already thread-parallel for extraction (v1.24) — the
  sandboxed-worker design must state its relationship to that machinery
  (see §2 S-A parallel scoping).
- `tools/layer_check.py` ranks: cli/sfx = 5, api/dll/wasm = 6
  (boundary). A new `src/sandbox/` module that the CLI calls must sit at
  **rank 5 (beside cli, same-rank includes allowed)** so cli→sandbox and
  sandbox→archive are both legal; `layer_check.py`'s `LAYER_RANK` and
  ARCHITECTURE.md §2 get the same-change update (the verification-legs
  same-change rule).
- Platform facts that shape the design: Windows AppContainer/LPAC spawns
  via `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` with inherited
  handles; Linux unprivileged user namespaces + `seccomp()`(NO_NEW_PRIVS)
  allowlists; macOS Seatbelt `sandbox_init` profiles are compile-time
  strings with opaque validation errors. Known trap: `<windows.h>` must
  be included at global scope only (namespace inclusion breaks
  msvc-arm64; only the tag run catches it) — the AppContainer/JobObject
  code will hit this rule. Apple SDK rejects some qualified POSIX calls
  (`::sigemptyset` removed in v1.28 for this reason). glibc `termios.h`
  defines `CTIME` as a macro — new includes must be checked against
  `time_flags::*` collisions.

## 2. Candidate designs, argued honestly

### Design S-A — broker + sandboxed worker for the parse/decode engine (PROPOSED)

**Trust boundary (the property Gate 0 must confirm):**

- **Broker (in the host process — CLI or embedding app):** opens the
  archive volume files and the extraction destination; owns ALL
  filesystem handles; derives keys (PBKDF2) from the password; enforces
  ExtractionLimits, cumulative caps, wall-clock timeouts; performs ALL
  disk writes through the existing v1.24 containment + atomic-write
  machinery (ExtractionSession/AtomicWriter — unchanged); applies
  metadata policy (modes/owners/xattrs/MotW per §4.3); renders all
  output (sanitizer, JSON summary — the worker has no terminal surface).
- **Worker (sandboxed process):** receives exactly: (a) read-only file
  descriptors for the archive volumes (inherited at spawn — the worker
  never learns a path it could open), (b) a bidirectional socket pair
  (its only I/O), (c) derived key material where the archive is
  encrypted (raw passwords never cross the boundary — derived AES
  key/IV + PswCheck do; residual: derived keys live in worker memory,
  zeroized post-use, documented). The worker parses headers, runs
  decompression and CRC/BLAKE2sp verification, and streams decoded
  bytes + structured results back. It CANNOT: open/create/write/rename
  any file, execute or fork anything, touch the network, or read the
  filesystem namespace. Exit taxonomy unchanged: worker failures map to
  the pinned codes at the broker (§3.1 — no new exit-code namespace).
- **The worker is not trusted.** The broker validates every IPC frame
  (bounded length, bounded count, cumulative byte cap, structured
  parse) and re-runs all policy on everything the worker reports — a
  subverted or buggy worker can emit garbage bytes (which CRC
  verification catches downstream) but cannot widen its own privileges
  or reach the filesystem. This is the model that survives "the parser
  has a zero-day": the crafted input exploits the worker's parse of it,
  and lands inside a process that cannot touch anything.

**IPC protocol (bounded, versioned):** length-framed messages over the
socket pair — `u32 length (≤ 4 MiB) | u8 type | payload`; types: OPEN
(volume count), SCAN_RESULT (packed entries), EXTRACT_REQ, DATA_CHUNK,
ENTRY_RESULT (status/metadata), ERROR (code + detail — codes are the
shared RarError values), CANCEL, PING/SHUTDOWN. The frame parser on the
broker side is written to the same hostile-input standard as the archive
parser itself (it is the only new attack surface the design adds).

**Data flow decision — S-A1 (fd passing, PROPOSED) vs S-A2 (broker
streams archive bytes through IPC):** S-A1 passes read-only volume fds
(`SCM_RIGHTS` on Linux/macOS; inheritable handles on Windows
AppContainer spawn) so multi-GB archives never traverse the socket;
only DECODED bytes flow back (unavoidable — the whole point is the
broker writes them). S-A2 would also stream packed bytes IN, doubling
IPC for every archive; rejected except as the documented fallback
profile if a platform's sandbox cannot safely permit `pread` on an
inherited fd (none of the three models has that limitation — Windows
inheritance, Linux fd tables survive `CLONE_NEWUSER`/seccomp, macOS
descriptors survive `sandbox_init`).

**Per-OS models (§5.1 names all three):**

- **Windows — AppContainer (LPAC):** `CreateProcess` with
  `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`, empty capability list,
  LPAC (Less-Privileged AppContainer) where supported; all handles
  inherited via `bInheritHandles`; mitigation-policy attributes reuse
  the v1.23 SFX pattern; Job Object caps (process/memory/CPU,
  kill-on-close) wrap the worker as defense-in-depth. The worker's
  token carries no filesystem or network capability SIDs; its only
  writables are the inherited socket handles.
- **Linux — seccomp-BPF (+ unprivileged userns where available):**
  spawn worker, wait for its init-ready ping, then the worker installs
  `PR_SET_NO_NEW_PRIVS` + a seccomp user-notify-free allowlist filter
  (read/write/pread64/futex/munmap/madvise/rt_sig*/exit-group on its
  own fds only — no open/openat/execve/socket variants), with
  `CLONE_NEWUSER | CLONE_NEWNS` as an additional namespace wall where
  the kernel allows. Allowlist is data (a table), testable in CI, and
  the CI leg runs the real thing (ubuntu runners allow seccomp).
- **macOS — Seatbelt:** `sandbox_init` with a compile-time profile:
  `(deny default)`, allow read/write on inherited descriptors only
  (file-read restricted to the inherited fds' semantics via
  `(allow file-read* (require-any (global-name ...)))` is NOT
  per-fd — the honest profile is deny-default + explicit allowances
  for sysctl-read/mach lookup minimums + no `file-write*`, no
  `network*`, no `process-exec*`), documented against Apple's opaque
  validation errors. Apple SDK qualified-call trap noted (§1.3).

**CLI integration:** sandboxed mode is the DEFAULT for `x`/`e`/`t`/`p`/
`l*` where the platform model is available, with a first-class
`--in-proc` escape hatch + `OPENRAR_IN_PROC=1` env (the
`--no-mmap`/`OPENRAR_NO_MMAP` kill-switch pattern) and an explicit
`W:` notice when the worker could not be spawned and the run falls back
in-process (fail-open must be LOUD and policy-visible, never silent).
`a`/mutation/creation commands stay in-process (the writer path is not
the parser-attack surface §5.1 targets; mutating through a worker adds
IPC for the write side with no trust gain — the broker already holds
those handles).

**Parallel scoping:** the v1.24 parallel pipeline (slot readers) maps
onto a worker pool (each slot worker gets the fd set + its socket); the
solid-chain and phase-2/3 machinery are unchanged. This is attempted;
if the pool model exceeds its milestone budget, the documented
deviation is: sandboxed mode runs the sequential engine and PARALLEL
extraction auto-falls-back to in-process with the `W:` notice (a
perf-motivated, policy-visible degradation — the §5.1 requirement is
about the parser boundary, and the pool is the same boundary per
worker). Kill-signal criteria below decide.

**Sandboxed DLL export:** none in v1.30.0. The DLL keeps in-process
parsing (embedders who need the broker/worker model are §7.3's
self-sandbox audience; an in-host subprocess API is a policy decision
an embedder should own). The feature-bit registry stays additive-honest:
if a sandboxed open family lands post-2.0 it takes bit 17 (next free
slot) — no speculative reservation (registry convention: assigned only
when the gated exports ship).

### Design S-B — in-process hardening only (defer the worker) (REJECTED as primary)

Ship 2.0 LTS with library-mode floors + docs only. Fails ROADMAP
prereq 2 outright (it is blocking, and §5.1 is normative). Rejected as

### Design S-C — resource caps instead of privilege boundaries (Job Objects / cgroups / containers) (REJECTED as the sandbox)

Job Objects/cgroups cap resources, not capabilities (v1.23's pattern is
already the defense-in-depth layer inside S-A); containers are a
deployment posture, not a library architecture, and don't exist for
Windows/macOS end users. Rejected as the primary mechanism; retained as
the layering inside S-A.

**S-A both sides, stated:**

- FOR the full three-OS build: all three models are testable in this
  repo's CI (ubuntu/macOS/windows legs exist — the e2e suite runs real
  sandboxes on each); the design is one OS-abstracted interface
  (spawn/profile/fd-pass) with three small implementations; 2.0 LTS is
  the release whose headline IS sandboxing; shipping 2 of 3 makes the
  ROADMAP row and §5.1 dishonest or late-annotated; the e2e assertion
  suite is shared, so each additional model is mostly spawn-glue.
- FOR the scoped cut (AppContainer + seccomp shipped, Seatbelt
  documented follow-up): three privilege-boundary codebases each carry
  a real risk of silent misconfiguration — the worst outcome is a
  sandbox that does not actually sandbox, and Seatbelt is the most
  opaque of the three (compile-time profile strings, unhelpful
  validation errors, deprecation pressure on `sandbox_init`);
  seccomp allowlists rot with libc/kernel drift; AppContainer/LPAC is
  version-sensitive. A cut ships two solid models plus honest docs
  instead of three shaky ones, and the worker architecture is
  OS-abstracted so Seatbelt lands later as a profile + spawn glue with
  the broker/IPC contract unchanged.
