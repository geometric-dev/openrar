## 1. E1 — emit the shard-header state blob (the emission change)

**What changes.** `build_shard` (recovery_writer.cpp) currently zeroes three
regions the reference writer populates (probe §3/§5): `chunk_data_extent`
(+0x1E) becomes the unpadded byte count of the final data chunk
(`prot − (D−1)·group`, 0 when prot divides evenly); `data_shard_state[D]`
(+0x40..) becomes the raw CRC-64 (init 0, **no final XOR**) of each data
chunk's unpadded bytes; `final_state` (+0x40+D·8) stays a fixed **zero**
(the reference's per-run random seed — validator-ignored, probe §5). Shard
CRC-64/XZ is recomputed after filling (existing code path). Entries are
identical in every shard of the record (reference behavior, verified).

**Legality.** The field set is decoder-ignored by our spec comment and by
measured oracle behavior: the reference validator accepts zeroed and
populated records alike (`t` All OK on both, probe §5/§9); the reference
repairer fully functions on populated third-party records (expC: 0 phantom
accounting on pristine, byte-exact damage repair); our reader ignores the
region today and keeps ignoring it. The fields are redundant integrity
data, not new syntax — no new record types, no version bump (shard
versions stay 1.1).

**Determinism.** Entries are a pure function of the protected byte range;
seed fixed at zero → the record remains bit-for-bit reproducible from
`(rec_pct, archive bytes, parity)` — the recovery_writer.cpp layout comment
is updated accordingly (it currently claims zeros are emitted for this
reason).

**Cost.** One additional CRC-64 pass over the protected range (streamed,
same buffers as the parity fold), D ≤ 200 u64 stores. No new caps: the
region is bounded by the existing header geometry (≤ 1608 bytes at D=200).

**Scale>1 note.** Our scaled single-shard packaging keeps the entries in
the first unscaled region (`D·8+8` bytes); the scale-duplicated remainder
of the scaled header stays zero. The reference expresses scale>1 by
physical chunk-sharding instead (probe §6) — E3 keeps our packaging as a
deliberate, `t`-validated divergence; implementation must verify the
reference `t`/`r` against our populated scaled-shape records at 16 MiB
(test T-ORACLE-2).

**Gates.** Emitted bytes change → goldens re-baseline + full interop gate
+ oracle e2e (T-ORACLE-1/2 below). m0-store archives are bit-identical
except the RR region.

## 2. E2 — chunk-granularity multi-erasure repair (reader)

**Design: a new localization tier, fail-closed ordering.** The decode
machinery in `RecoveryManager::repair_data` already handles arbitrary
missing ≤ parity (proc_sectors mapping + RS decode); the single-erasure
limit is in the caller's damage scan (recovery_writer.cpp:1962 Tier-1).
New tier ordering in the inline-RR repair:

- **T0 (new, requires E1-style entries):** if the record's shard headers
  carry a non-all-zero entry set (and shard CRC-64s verify — already a
  precondition), recompute raw CRC-64 per data chunk over the *current*
  bytes; the erasure set is `{k : entry_k ≠ current_k}`. If
  `1 ≤ |E| ≤ valid_parity_count`, mark exactly those chunks invalid and
  decode. Any chunk count outside that range → refuse (fail-closed, same
  user-visible failure class as today).
- **T1 (existing, unchanged):** single-corrupted-shard syndrome-ratio
  identification — the fallback for zero-entry (legacy/foreign) records.
- **T2 (existing, unchanged):** header-CRC scan fallback.

**Security analysis.**

- Hostile/random entries: every chunk mismatches → |E| > parity → refuse.
  No repair, no writes, exit unchanged from today's damage-exceeds-parity
  class. A forged entry set that marks GOOD chunks bad is self-correcting:
  decoding reconstructs marked chunks from parity of the remaining good
  data, which reproduces the original values (and parity rows are gated by
  their own shard CRC-64s before use). The worst outcome is refusal, never
  corruption of data the archive-level checksums would have accepted.
- Erasure set bounded by D (≤ 200); decode buffers bounded by the existing
  `calculate_parity_buffer_size` guards; writes remain inside the existing
  splice region `[0, rr.header_offset)` + RR section. No new allocation
  surface, no new parser (entries are fixed-size u64s under an
  already-CRC-checked header).
- The repair path's existing property is preserved: an archive that fails
  repair is left byte-identical (temp + rename only on verified success —
  `headers_verify` post-condition).

**Gates.** Unit matrix: damage 1..NR−1 chunks × damage widths (1 byte …
whole chunk) × entry states (E1 entries / zeroed entries / hostile entries);
zero-entry records must take the T1/T2 path exactly as today (behavioral
pin); .rev path untouched. Oracle: multi-damaged RAR 7.20 archives (intact
reference entries) repaired byte-exact by us (T-ORACLE-3).

## 3. E3 — multi-physical record reassembly; writer packaging decision

**Reader.** The reference packages each logical parity shard as multiple
physical chunk-shards above D·64 KiB protected size (unscaled `D·8+0x48`
headers, `chunk_position` advancing in 64 KiB steps, logical fields
repeated; probe §6). The repair path gains a reassembly pass: group
physical shards by `shard_index`, require (a) per-piece shard CRC-64 +
unscaled-header geometry, (b) `chunk_position` coverage of
`[0, group_count)` with no gap/overlap, (c) logical fields (D, NR,
group_count, shard_size, prot, versions) **and the entries region**
identical across pieces, (d) piece-count bounds before any map insertion —
pieces per logical shard ≤ `ceil(group_count / 0x10000) + 1`, total pieces
≤ `NR × that` — any violation → fail-closed refusal. Concatenated payloads
then feed the existing decode path (E2's erasure set applies unchanged —
the entries live in every physical header and must agree across pieces).

**Writer decision — CONDITIONAL.** The default branch keeps the scaled
single-shard packaging (it is `t`-interoperable at 16 MiB with zeroed
entries, and the parity math is proven identical under both packagings).
**T-ORACLE-2 is decision-gating**: if the reference `r` refuses our
scaled single-shard shape once entries are populated (scale>1), the writer
switches to reference-style physical chunk-shard packaging for scale>1.
The implementation plan carries both branches with the decision point
explicit.

**Gates.** Unit: crafted multi-physical records (from the probe corpus
recipe) — valid, gapped, overlapped, field-disagreeing; oracle: our repair
on a damaged reference 16 MiB archive byte-exact (T-ORACLE-4).

## 4. E4 — resource forks + FinderInfo (v1.27 xattr allow-list extension)

**Capture.** `ArchiveMutator::xattr_capturable` gains two exact names:
`com.apple.ResourceFork`, `com.apple.FinderInfo`. These ride the existing
FHEXTRA_XATTR (0x08) mechanism — no new record type; the v1.27 legality
gate (unknown-record skip contract, oracle Track 10) already covers the
wire shape. Existing caps apply unchanged: over-cap values are SKIPPED,
never truncated (a ResourceFork larger than FHEXTRA_XATTR_VALUE_MAX is
skipped with the v1.27 fail-soft semantics — a partial fork would be
corruption-by-truncation); FinderInfo is 32 bytes.

**Restore.** `ArchiveReader::xattr_restorable` gains the same two names,
**default-on** (content-class metadata, the same class as user.* — not the
security.*/trusted.* admin-opt-in class), with one platform gate: Apple
namespaces restore only on `__APPLE__` builds (on Linux, writing
com.apple.* xattrs would succeed and create alien provenance noise; on
Windows the apply path is already a no-op). Capture is likewise
platform-gated by the existing io layer (these names do not occur on
non-Apple filesystems; the predicate itself stays pure and unit-testable
everywhere).

**Policy interplay.** None with SECURITY_ARCHITECTURE §4.3: quarantine and
provenance namespaces (`com.apple.quarantine`) are separate names and stay
excluded; FinderInfo carries type/creator/flags, not provenance; the
ResourceFork is file content. Extraction does not execute any of it.

**Gates.** Predicate unit tests on every platform; over-cap skip test;
macOS CI leg for the capture/restore e2e; byte-identity of extraction
roundtrips on the macOS leg.

## 5. Failure-mode matrix (summary; full rows in the implementation plan)

| # | Failure | Behavior |
|---|---|---|
| F1 | Hostile entries (all chunks mismatch) | Refuse repair, fail-closed |
| F2 | Forged entries marking good chunks | Self-correcting decode; refuse if > parity |
| F3 | Entry set present but shard CRC-64 bad | Record unusable (existing precondition) |
| F4 | Multi-physical pieces with gap/overlap/field disagreement | Fail-closed refusal |
| F5 | ResourceFork over VALUE_MAX / TOTAL_MAX | Skip attribute, never truncate |
| F6 | Non-Apple host restoring Apple namespaces | Platform-gated: no-op |
| F7 | Zero-entry record (legacy/foreign) | T1/T2 exactly as today (behavioral pin) |
| F8 | Repair verification fails post-splice | Temp discarded, original untouched (existing) |
| F9 | Entries match all chunks but parity shards invalid | Existing parity-rebuild branch (D14), never "already intact" |
| F10 | E4 fork > 64 KiB VALUE_MAX / TOTAL_MAX exhausted | Skip attribute with report, never truncate |

## 6. Diff-surface claim

Emitted bytes change ONLY in the RR shard header region (extent + entries +
their CRC-64); every other byte of every archive is unchanged. Reader
changes are confined to the repair command path (extraction untouched).
**RR behavior flows through two frozen C ABI exports —
`openrar_archive_add_recovery_record` and `openrar_archive_repair`;
signatures are unchanged (additive behavior per the freeze rules) and the
binding-layer conformance row (dll_tests through both exports) is part of
the arc's test plan — the C++-only green is not sufficient (Pillar 7).**
The 24-stage interop gate, golden bytes, and the Debug suite run on every
emission-touching commit per standing rules; `m0` non-RR archives must
remain byte-identical (T-REG-1).

## 8. Directives (post-review; all applied)

- **D1** Seed fixed at zero; never derive randomness — the record must stay
  reproducible.
- **D2** Entries computed over UNPADDED chunk bytes (tail chunk semantics
  verified, probe §5); full chunks are naturally unpadded. Chunk k is
  archive bytes `[k·group, min(k·group+group, prot))` from file offset 0 —
  the same coordinate frame as the parity fold (frame-stability gate).
- **D3** The layout comment in recovery_writer.cpp is updated in the same
  commit (zeros claim retired; expC reference recorded).
- **D4** T-ORACLE-1/2 must run against a wiped build (stale-binary rule).
- **D5** T0 requires verified shard CRC-64s AND a non-all-zero entry set;
  anything else falls through to T1/T2 unchanged.
- **D6** Erasure set > valid parity → refuse with the existing failure
  class; never partial-repair.
- **D7** Post-repair verification gates the rename, as today — and T0's
  acceptance check is normative: reconstructed chunks must re-verify
  against their entries (recomputed raw CRC-64 ≡ stored entry) before
  splice; a decode failing entry verification refuses the repair.
- **D8** Multi-physical validation is all-or-nothing per record (a single
  bad piece refuses the whole record); cross-piece agreement includes the
  entries region; piece-count bounds (per logical shard ≤
  `ceil(group_count/0x10000)+1`, total ≤ NR× that) are enforced before any
  map insertion.
- **D9** spec/05-recovery.md documents both packagings and the E1 blob
  semantics in the same arc.
- **D10** E4 restore is platform-gated to `__APPLE__`; predicate tests run
  everywhere.
- **D11** E4 over-cap values skip with report, never truncate (v1.27 rule);
  the 64 KiB VALUE_MAX / 1 MiB TOTAL_MAX practical limitation for large
  forks is stated in plan and CHANGELOG (dedicated fork-record mechanism
  out of scope).
- **D12** (review) E1's entry pass is traced through the serial and
  `threads>1` branches of `add_recovery_record` and pinned byte-identical
  by a threads=1 vs threads=4 test.
- **D13** (review) Structural validation order is pinned: shard-header
  checks (incl. the total_size u32 truncation rejection) precede any entry
  consumption in repair and reassembly.
- **D14** (review) T0 with an empty erasure set and invalid parity shards
  falls into the existing parity-rebuild branch (re-splice with new
  parity) — never reports "already intact" while parity is damaged.
- **D15** (review) dll_tests conformance rows through
  `openrar_archive_add_recovery_record` (E1 bytes) and
  `openrar_archive_repair` (E2/E3) — the frozen-export behavior surface.
- **D16** (review) The writer-packaging decision is conditional on
  T-ORACLE-2 (see §3); the plan carries both branches.
