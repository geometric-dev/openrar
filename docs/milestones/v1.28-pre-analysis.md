# v1.28.0 Pre-Analysis — Interactive TUI & Benchmark Engine (Gate 0 Review)

**Status:** pre-implementation analysis for the v1.28.0 arc, submitted for
architect-challenge (Gate 0 per docs/ROADMAP.md §v1.28.0 and Guiding
Principle 2). This document deliberately argues BOTH sides before
committing to a scope.

**Flagship claims under scrutiny:**
1. **v1.28.0 changes NO emitted archive bytes.** The TUI is a rendering
   layer over shipped operations; the benchmark engine measures shipped
   engines on corpora it builds with the shipped writers. Zero format
   surface; the `FHEXTRA_XATTR`/0x08 record set shipped in v1.27.0 stays
   CLOSED (no new record types, no new extras, no writer/reader format
   changes).
2. **Terminal-injection hardening is a release gate** (SECURITY
   ARCHITECTURE §7.1): the arc must PROVE the TUI cannot render an
   unsanitized byte — including the JSON machine path and any persisted
   artifact — and close the gaps this audit found in shipped surfaces.
3. **Non-TTY degradation is a contract with named negative tests**
   (pipe/file/CI: what renders, what is suppressed, exit codes unchanged).
4. **Benchmark reproducibility (<5% variance) is a protocol claim**, not a
   hope: warm-up, fixed pass count, median + spread reporting, hardware
   disclosure, and a versioned `--json` schema for CI trends.

**Normative inputs:** SECURITY_ARCHITECTURE §7.1 (terminal injection &
parallel isolation), §4.4 (UI invariant), §3.1 (exit taxonomy), §5.4
(limits); docs/ROADMAP.md §v1.28.0 + Shipped Baseline (v1.27.0 = starting

## 0. Gate 0 statement: zero format surface (stated, then confirmed)

**The claim, explicitly:** v1.28.0 emits no new archive bytes and consumes
none differently. Concretely, the arc must not touch:

- `src/format/header_writer.cpp` / `header_reader.cpp` record layouts
  (the v1.27.0 `FHEXTRA_XATTR` 0x08 record set is closed — no new types,
  no field changes, no new service headers);
- `src/archive/archive_writer.cpp` / `archive_mutator.cpp` emission
  behavior (byte-identical output for identical inputs and flags);
- the extra-area, data-area, service-header, or encryption framing in any
  way.

**How the Gate 0 review CONFIRMS this rather than assumes it:** the
challenge reviews the arc's actual diff surface — expected touched paths
are `src/cli/progress.hpp` (renderer), a new renderer unit,
`src/cli/main.cpp` (dispatch + output lines only),
`src/archive/extraction_report.cpp` (JSON escaping only),
`tests/bench/openrar_bench.cpp` + its new modules, and tests. Any diff
hunk inside `src/format/` or the writers' byte-emission paths is a Gate 0
violation by definition. The interop gate (17 stages, incl. the Track 10
crafted-0x08 archive vs the UnRAR oracle) must stay green UNCHANGED — a
byte-level regression would fail it even without a review catch.

**Why this needs saying:** the v1.27 Gate 0 argued legality of NEW bytes;
v1.28's Gate 0 argues the ABSENCE of new bytes. The failure mode being
gated is different (accidental format drift while touching shared
headers), and the confirmation step is different (diff-surface review +
interop gate, not spec-conformance argument).

## 1. Current-state facts (the §7.1 surface audit, verified this session)

### 1.1 The two-sanitizer model (what exists and what each layer owns)

- **Path layer** (`io::sanitize_archive_path`, path_util.cpp:169 +
  `make_safe_component`, path_util.cpp:34): builds the ON-DISK name.
  C0 controls 0x00–0x1F and Windows-forbidden chars → `_`; invalid UTF-8
  percent-encoded (`percent_encode_invalid_utf8`, the escaped name IS the
  filename, §4.4); trailing dots/spaces trimmed; DOS-device stems
  prefixed. Valid non-ASCII UTF-8 — INCLUDING RTL overrides, C1 controls,
  directional marks — passes to disk verbatim (they are legal filenames).
- **Display layer** (`cli::sanitize_for_display`, progress.hpp:40): builds
  TERMINAL-SAFE text. C0+DEL → `?` per byte; C1 U+0080–009F (incl. 8-bit
  CSI U+009B) → `?` per byte; invalid UTF-8 → `?` per byte (strict decode,
  overlong/surrogate/out-of-range/truncated); bidi/isolate/mark/line-sep/
  soft-hyphen → `?` per byte; valid non-ASCII passes through. Idempotent
  (its output contains only ASCII-safe and valid-UTF-8-passed-through
  code points — sanitize(sanitize(x)) == sanitize(x); verified by the
  category table below).
- The two layers intentionally DIFFER (RTL name: displayed `a?b`, on disk
  `a<RLO>b`). The §4.4 UI invariant ("displayed ≡ extracted") is pinned in
  its security-relevant form: the display never shows content the disk
  name does not have, the `--json-summary` name IS the on-disk name
  (extraction_report_tests.cpp:161 `test_displayed_equals_extracted`,
  :188 `test_percent_encoded_undecodable`), and the TUI never executes
  files. v1.28 must state this reconciliation explicitly and keep the
  JSON leg of it exact.

GAPS found by this audit (each becomes a named negative test):

1. **Archive comment printed BYTE-RAW** (main.cpp:479,
   `std::cout << "Comment:\n" << cmt_text`). The RAR5 archive comment is
   attacker-controlled bytes; it can carry any ESC/CSI/OSC payload, RTL
   overrides, or invalid UTF-8. This is the single largest §7.1 violation
   in shipped code — the exact attack the sanitizer exists for, on a
   surface nobody wired.
2. **`lt` owner names byte-raw** (main.cpp:535–536):
   `owner_user`/`owner_group` come from `FHEXTRA_UOWNER` — archive-
   controlled strings rendered without the sanitizer.
3. **`json_escape` passes invalid UTF-8 through** (extraction_report.cpp:5):
   it escapes `"` `\` and C0 controls, but bytes ≥ 0x80 that do not form
   valid UTF-8 go into the JSON verbatim — RFC 8259 requires JSON text to
   be valid UTF-8, so a hostile `report.archive` argv path (or any future
   raw-name field) can make `--json-summary` output unparseable for
   strict consumers. Entry names in the report derive from the ON-DISK
   path (already ASCII-hardened by `make_safe_component`), so the live
   risk is `report.archive` + `abort_reason` composition — the contract
   must hold for the whole document, not the happy path.
4. **Local-path `W:` lines unsanitized** (main.cpp:1605 `cannot stat`,
   :1773/:1857 `cannot read`): these print `p.string()`/`src_path` —
   LOCAL names. §2.2 "Local Racing" is in-scope for this threat model (a
   different local user can plant hostile names in a shared source
   directory), so these are defense-in-depth surfaces, not out of scope.
5. **VT detection is keyed to stdout, not the sink** (progress.hpp:110
   `is_vt_supported` checks `isatty(stdout)`): in `--json-summary` mode
   progress renders to `g_prog_out` = stderr (progress.hpp:130), so
   capability and sink can disagree (`x a.rar --json-summary` on a real
   terminal renders VT into stderr based on stdout's fd). Harmless in the
   common pipe case, wrong in principle; the TUI must derive capability
   from the stream it renders to.

### 1.3 Parallel extraction machinery (the v1.24 guarantees the TUI must not break)

- Workers are submitted per phase-1 index; each acquires a slot reader,
  extracts, runs the shared `restore_children` lambda, then
  `flags.finish(idx, okv)` under mutex and `Prog.note_file_done(...)`
  (mutex-serialized; sanitizes inside; renders under the lock).
  main.cpp:2594–2631.
- The report loop prints in ARCHIVE ORDER after `flags.wait(i)`
  (main.cpp:2691–2715) — output identical to the sequential run.
- Per-entry failure isolation: per-job try/catch + flags; one worker's
  exception cannot poison the run (main.cpp:2614–2616).
- Temp-name uniqueness across workers: ExtractionSession crypto-random
  temps + per-directory journals (SECURITY_ARCHITECTURE §3.3) — untouched
  by rendering.
- The rendering invariant today: every CLIProgress mutator holds `mu_`
  ACROSS its `render_locked()` call — rendering is serialized as a side
  effect of state mutation (progress.hpp:155–157). This is sound but
  couples render frequency to worker progress; the dual-progress TUI
  moves to a **single-renderer tick model** (workers mutate state under a
  mutex; ONLY the main thread renders, on a timer) — see §2 T-A.

### 1.4 Terminal state machine facts (what does NOT exist today)

- No keyboard/interactive cancellation: no `signal()`/`SetConsoleCtrlHandler`
  anywhere in src/cli (verified by grep); today "cancel" = the OS kills
  the process (journal sweep handles temps on next run).
- No terminal-width awareness: BAR_WIDTH is a fixed 28 (progress.hpp:137)
  and the 4-line block (badge/bar/meta/file, progress.hpp:312–316) assumes
  each logical line occupies exactly one terminal row. A long display name
  WRAPS on a narrow terminal → `lines_drawn_` no longer matches reality →
  the `\x1b[<n>A` cursor-up redraw garbles the region. Cosmetic today;
  a hard correctness requirement for a 6-line dual-progress region.
- No resize handling (no SIGWINCH, no `WINDOW_BUFFER_SIZE_EVENT`).
- Non-TTY behavior exists informally: `is_vt_supported()` false ⇒
  `spin()`/`render_locked()` no-op and `done()` has a plain-text branch;
  per-file `Extracting … OK/FAILED` lines print only when
  `!is_vt_supported()` (main.cpp:2486/2530/2693). It works but is NOT a
  tested contract — nothing pins "zero ESC bytes reach a piped stdout".

### 1.5 Benchmark facts

- `tests/bench/openrar_bench.cpp` (target `openrar_bench`): RS16 fold +
  match-length kernels (best-of-3, deterministic corpora) + the v1.25
  50 GB-class sparse listing (SINGLE timed run; Windows FSCTL sparse with
  skip-if-unsupported; POSIX relies on cp sparse support). Grep-able
  `[bench]` lines; exit code always 0; "informational, never a gate".
- The v1.26 CDC three-number reduction gate (store / plain-solid /
  CDC-packed) lives as a unit test (cli_tests.cpp:1283), NOT as a bench
  suite — rollover item 2 folds it into the engine this arc.
- README "Performance" quotes hand-run numbers (50 MB / 1 GB vs WinRAR)
  with NO documented protocol — no warm-up, no pass count, no hardware
  disclosure. The v1.28 reproducibility claim needs the protocol BEFORE
  the claim ships (ROADMAP v1.28.0 addendum c).
- CI runs the bench harness informationally on native legs (ROADMAP
  v1.22.0). `--json` for CI trends = a machine-readable artifact with a
  versioned schema; trends are computed by the CI consumer, not the tool.

## 2. Candidate designs, argued honestly

### Design T-A — dual-progress in-place renderer + interactive cancel (PROPOSED)

A new renderer (replaces CLIProgress' rendering core; its public API
survives so call sites do not churn):

- **Region:** ≤ 6 lines — badge / OVERALL bar (bytes + files across the
  whole operation) / CURRENT-FILE bar + display name (the "dual progress":
  operation-level and file-level, WinRAR-style) / meta line (count, ETA,
  rate) / optional per-worker hint. During parallel phase 1 the
  current-file slot shows the most recently STARTED file; the overall bar
  is driven by completed bytes only (counters never regress).
- **Tick model:** workers mutate a shared state struct under one mutex
  (atomic counters + last-started/last-done names); ONLY the main thread
  renders, coalesced to a ~30 ms tick. Rendering under the lock is
  replaced by snapshot-then-render — the render function is PURE:
  `render(state, width) → string`, unit-testable without a terminal.
- **Width discipline:** every rendered line is clamped to the detected
  terminal width (Windows `GetConsoleScreenBufferInfo`; POSIX
  `ioctl(TIOCGWINSZ)`, re-queried per tick, POSIX SIGWINCH triggers an
  immediate tick). Truncation is UTF-8-aware (never splits a sequence)
  with a `…` tail. This fixes the wrap-garble class for the existing
  4-line block too.
- **Interactive cancel:** ESC or 'q' on a raw-mode stdin poll thread
  cancels the run cooperatively (workers observe the flag between jobs;
  in-flight extraction finishes or aborts at its next check) →
  `EXIT_USER_BREAK` (255), journal sweep, JSON `aborted`. Terminal state
  (raw mode, VT flags, cursor) is RAII-restored on ALL exits, including
  the cancel path itself. Ctrl+C maps to the same cooperative cancel via
  a console ctrl handler (Windows) / SIGINT flag (POSIX) — no new exit
  code (255 is the pinned user-break).
- **Sanitizer choke point:** the renderer sanitizes EVERY name-shaped
  field at render time with the idempotent `sanitize_for_display` —
  callers may pre-sanitize (and do), the renderer does not trust them.
  One place proves the property for every current and future call site.
- Non-TTY: the whole engine bypasses (see N-A) — same binary, same exit
  codes.

- **Cost:** ~1 new source pair + progress.hpp rewrite of the render core;
  keyboard thread only when BOTH stdout and stdin are TTYs.
- **Risk:** terminal-state restore bugs (mitigated by RAII + the
  state-machine tests); raw-mode stdin swallowing input mid-prompt
  (keyboard thread starts ONLY around long operations, prompts keep
  cooked mode — the prompt paths never run concurrently with the TUI
  region).

### Design T-B — full-screen alternate-buffer interactive browser (REJECTED)

Alternate-buffer, cursor-addressable archive browser (list + select +
extract). Rejected: scope explosion (a second UI paradigm with its own
state machine), alternate-buffer/raw-mode edge cases on Windows conhost
vs Windows Terminal vs POSIX terminals, zero WASM/DLL applicability, and
the interactive-selection surface duplicates consent machinery the CLI
already has (§6.1). The security value is in the RENDER gate, not in a
browser. Revisit only if a real user demand exists post-2.0.

### Design T-C — status quo single progress (REJECTED)

Keep the 4-line single bar. Fails the roadmap's dual-progress requirement
(operation vs file granularity matters exactly when a huge entry hides
behind a fast-moving overall bar) and leaves the wrap-garble class
unfixed. Rejected.

### Design G-A — render-time idempotent sanitizer as the choke point (PROPOSED)

The renderer (and the two legacy direct-print paths that remain — the
`l` listing and the comment/owner lines) sanitize at render time.
Rationale: `sanitize_for_display` is idempotent, so double-sanitizing is
free; a render-time gate cannot be forgotten by a future call site the
way a call-site discipline can. The release-gate proof becomes: (1) unit
tests per category (exist, extended to the new surfaces), (2) an e2e
hostile-corpus test driving EVERY command against an archive whose names
AND comment AND owner names carry one payload per §7.1 category, with
assertions on captured stdout/stderr (zero attacker-payload substrings
survive; non-TTY mode additionally asserts ZERO ESC bytes total),
(3) the JSON path asserts UTF-8 validity of `--json-summary` output.

### Design G-B — call-site discipline only (REJECTED)

"Every call site sanitizes before printing" is what exists today — and
the audit still found three shipped gaps (§1.2). Discipline does not
compose; a gate must be checkable. Rejected as the primary mechanism
(retained as documentation).

### Design G-C — new safe-string type threaded through the renderer (DEFERRED)

A `SafeText` wrapper that only `sanitize_for_display` can construct gives
compile-time enforcement. Correct, but it churns every progress/list call
site for a guarantee the runtime choke point already delivers (the
renderer is the only writer of terminal bytes). Revisit with the 2.0 ABI
freeze. Rejected for v1.28.

### Design N-A — three-level non-TTY contract (PROPOSED)

Formalized, with named negative tests:

- **L1 stdout-not-a-TTY (pipe/file/CI):** NO VT bytes from the renderer
  anywhere (the renderer is never engaged); per-file
  `Extracting <name> ... OK/FAILED` lines print (name = display_name,
  sanitized); `done()` plain-text branch; spinners suppressed; `W:` lines
  unchanged; **exit codes byte-identical to the TTY run for the same
  archive** (the pinned taxonomy: 0/1/2/3/7/10/11/13/255). `--json-summary`
  stdout purity unchanged (existing test extended to hostile names).
- **L2 stdout-TTY, stdin-not-a-TTY:** TUI renders; interactive keyboard
  cancel is DISABLED (no raw-mode thread); Ctrl+C/console-close still
  cancels via the signal path. This is the `openrar x a.rar | tee log`
  shape.
- **L3 suppression switches:** `-q`/`-inul`/`-idq` (quiet) and
  `-plain`/`--plain`/`-idp` (plain) and `NO_COLOR`/`TERM=dumb` behave as
  today (existing `is_vt_supported` gates), now PINNED by tests instead
  of implied.
- VT capability follows the SINK: `is_vt_supported_for(FILE*)` on the
  stream `g_prog_out` actually points to (fixes §1.2 gap 5).
- The prompt paths (`ask_overwrite`, SFX consent) are UNCHANGED: they
  already detect non-TTY stdin and default Yes (main.cpp:108–116) — batch
  semantics preserved; their exit codes are part of the parity assertion.

### Design B-A — benchmark engine v2: protocol + `--json` in `openrar_bench` (PROPOSED)

- **Measurement protocol (the reproducibility claim's definition):**
  per suite: 1 warm-up pass (untimed, page-cache/branch-predictor settle),
  then N = 7 timed passes; suite result = MEDIAN; reported spread =
  (max−min)/median over the timed passes. The <5% variance claim is:
  *on a quiescent host (no concurrent load, fixed power plan), every
  compute-bound suite reports spread ≤ 5%* — verified on the dev host for
  the release notes, machine-checked per run, and REPORTED honestly when
  a shared runner is noisy (spread > 5% prints `VARIANCE` + the number;
  exit code stays 0 because the tool is informational — a `--strict`
  flag turns spread > 5% into exit 1 for CI hosts that want the gate).
  I/O-bound suites (50 GB listing) are excluded from the <5% claim (disk
  cache state dominates) and labeled `kind:"io"` in the JSON.
- **Hardware disclosure:** one `[bench] host` line + JSON `host` object:
  CPU brand string (cpuid/`__cpu_model`), logical cores, OS family,
  build type + compiler, clock source (`steady_clock`), passes, warm-up.
  A benchmark without hardware disclosure is not reproducible — the
  disclosure is part of the schema, not a comment.
- **`--json` schema (versioned):**
  `{"schema_version":1, "host":{...}, "protocol":{"warmup":1,"passes":7},
  "suites":[{"name":"rs16_fold","kernel":"GFNI","kind":"compute",
  "unit":"MiB/s","median":1234.5,"passes":[...],"spread_pct":2.1}]}`
  printed to stdout (the human lines stay on stdout too — `[bench]` lines
  are grep-able; `--json` switches stdout to JSON-only, human lines to
  stderr, mirroring the `--json-summary` purity pattern).
- **Suites:** existing three (rs16 fold, match length, 50 GB listing) +
  NEW: extract throughput (engineered corpus: store + m3 solid), add
  throughput (m3), and the **CDC corpus entry** (rollover item 2: the
  three-number store/plain-solid/CDC-packed reduction measured by the
  engine, same engineered corpus as the unit-test gate). Suite selection:
  `--suite <name>` (repeatable), `--quick` (3 passes) for local loops.
- **Where:** the `openrar_bench` target grows modules; no new binary, no
  CLI verb. **Design B-C (a `b`/`bench` CLI verb, RAR-parity) REJECTED:**
  no oracle exists to compare numbers against, the tool target is where
  CI already runs, and a verb would put measurement argv surface into the
  shipped CLI for no interop gain.

### Design B-B — "variance <5%" as a hard CI assert (REJECTED)

Asserting spread ≤ 5% on shared CI runners fails on scheduler noise for
reasons unrelated to the code (the v1.22 lesson: "best-of damps scheduler
spikes" — runners are NOISY). The claim is protocol-bounded (quiescent
host), the CI artifact reports variance, `--strict` opts into the gate.
Rejected as an unconditional gate.

## 6. Risks

- **R1:** raw-mode keyboard thread bugs strand a terminal in no-echo
  mode — mitigated: RAII guard restores on every exit incl. exceptions;
  the thread never starts unless BOTH streams are TTYs; state-machine
  unit tests drive every transition (start/cancel/resize/EOF/exception).
- **R2:** the comment/owner sanitization changes output for hostile
  inputs — behavior change must be changelogged; clean archives are
  byte-identical (assert in the hostile-corpus test's clean control).
- **R3:** `json_escape` `\uFFFD` substitution loses bytes in the JSON
  NAME field for hostile archive paths — acceptable: `report.archive` is
