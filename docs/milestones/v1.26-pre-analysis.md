# v1.26.0 Pre-Analysis — Content-Defined Chunking (Gate 0 Format-Legality Review)

**Status:** pre-implementation analysis for the v1.26.0 arc, submitted for
architect-challenge (Gate 0 format-legality gate per docs/ROADMAP.md
§v1.26.0 and Risk Register item 4). This document deliberately argues BOTH
sides before committing to a scope.

**The flagship claim under scrutiny:** content-defined chunking (CDC) as a
deduplication mechanism delivering large archive-size reductions.

---

## 1. What RAR5 legally allows (spec constraints, from RAR5-FORMAT.md + decoder reality)

1. **Per-file compression streams are self-contained.** Each file header's
   data area decompresses independently given: the method bits, the
   dictionary window size, and (for solid chains) the dictionary contents
   left by the previous file in the chain (FCI_SOLID, spec bit 7 of the
   compression information; archive flag 0x0004).
2. **Cross-file backward references are legal ONLY via solid chains.** The
   LZ77 dictionary carry-over is the one mechanism the format provides. It
   is bounded by the window (≤ 4 GiB per the header field, ≤ 1 GiB in our
   decoder's ILP32-safe table, default 2 MiB … tuned per method).
3. **There is no chunk-reference record.** RAR5 extra records (FHEXTRA_*)
   carry metadata only. There is no legal "this range equals that earlier
   range" pointer. Any such scheme would be a format extension → WinRAR
   cannot read it → it violates the project's interop charter (dual-oracle
   cross-extraction is a shipped, tested contract).
4. **Exact whole-file dedup already exists legally:** `-oi` FILECOPY
   (FHEXTRA_REDIR type 5, packed size 0) — shipped in v1.21.2-era.
5. **Solid-chain ordering is a packer decision, not a format constraint.**
   The archive is free to place files in any order and mark runs solid;
   extraction honors the chain. This is the one legal lever CDC can pull.

## 2. The three candidate designs, argued honestly

### Design A — CDC-driven solid-chain packing (LEGAL)

Use CDC (e.g. FastCDC/Gear hash) to fingerprint blocks of every input
file; group files whose fingerprints overlap heavily; place those files
ADJACENTLY inside one solid chain, ordered so that repeated blocks land
within the LZ window of their earlier copy.

- **Legality:** full. The emitted stream is ordinary RAR5 solid
  compression; WinRAR reads it natively.
- **Expected reduction:** real but bounded — dedup only materializes when
  a repeat falls inside the window (default 2 MiB … up to 1 GiB with large
  dicts). For backup sets with duplicated multi-MB files this is exactly
  the case. For scattered small duplicates, `-oi` FILECOPY already
  removes them at zero cost.
- **Cost:** packer complexity (fingerprint index, ordering constraints —
  extraction ORDER changes with the packing, which users must see);
  decompression is unchanged.
- **Risk:** the reduction claim must be measured per corpus and stated
  honestly (window-bounded), not as chunk-level dedup ratios.

### Design B — CDC chunk-store inside one archive (NOT LEGAL)

Store unique chunks once in a side "chunk store" and emit file headers
that reference chunk IDs.

- **Legality:** none. No RAR5 record type can express it; WinRAR would
  see garbage or empty files. VERDICT: rejected — Gate 0 fails.

### Design C — CDC for cross-archive incremental backups (NOT LEGAL in-band)

Reference chunks from a PREVIOUS archive.

- **Legality:** none in-band (archives are self-contained by spec).
  Would require sidecar state files (a ".pbf"-style scheme) — a different
  product shape, breaks the single-file contract, and WinRAR still cannot
  read the increments. VERDICT: rejected — Gate 0 fails; possible future
  companion format, out of OpenRAR's RAR5 scope.

## 3. Gate 0 verdict (pre-challenge position)

- Design B and C fail format legality — do not build them.
- Design A survives the gate but MUST restate its reduction claim:
  "solid-chain-aware deduplication packing — reduction bounded by the LZ
  window and realized via ordinary RAR5 solid compression", with per-corpus
  measurements and an explicit statement of the extraction-order change.
- `-oi` FILECOPY remains the dedup mechanism for exact files; Design A is
  for *similar-but-not-identical* content (and exact files too large for
  FILECOPY's semantics to matter).

## 4. Proposed v1.26.0 scope (post-Gate-0, pending challenge)

1. **M1 — CDC fingerprinting engine**: FastCDC-style rolling-hash chunker
   (Gear hash, normalized cut points), bounded fingerprint index
   (honest memory model: N fingerprints × 16 bytes, capped), fed to
   `compress_plan.hpp` as a packing suggestion.
2. **M2 — solid-chain packing planner**: orders the file list into solid
   runs by fingerprint affinity (stable tie-break on original order so
   identical inputs produce identical archives); caps: runs bounded by
   dictionary window; `-oi` FILECOPY takes precedence for exact matches.
3. **M3 — CLI + measurements**: `-oi` extended (or new switch) to enable
   CDC packing; per-archive reduction report (logical vs packed bytes);
   oracle round-trips (WinRAR reads our CDC-packed solid archives).
4. **M4 — cumulative caps cross-check** (§5.4): dedup-expanded streams
   honor ExtractionLimits (they are ordinary solid streams — verify).
5. **Negative tests**: chunker boundary fuzzing (crafted inputs that shift
   cut points), ordering-stability pin, caps-on-packed-streams, FILECOPY
   precedence, reduction-report honesty (claim == measured).

## 5. Architect-Challenge Verdict (Gate 0 review, this commit)

🟡 CONDITIONAL APPROVAL — Design A survives Gate 0; B and C confirmed dead.
Seven directives applied to the implementation plan before M1:

1. **Baseline gate**: every reduction claim measured against (a) store,
   (b) plain solid original-order same window, (c) CDC-packed — three
   numbers per corpus or the claim does not ship.
2. **Failure-Mode Matrix required** (chunker, fingerprint index, planner,
   batch-write paths × crafted/OOM/disk-full/cancel classes) — Pillar-7
   hard gate.
3. **-oi collision resolved**: CDC packing extends -oi (value 5) rather
   than a new switch; FILECOPY redir entries cannot sit inside solid runs
   (no data area) — the planner emits them outside runs or accepts chain
   breaks, spec'd in the plan.
4. **Extraction-order change is user-visible** (header order = listing
   order); opt-in switch only; ordering-stability test pinned (same input
   ⇒ byte-identical archive at any -mt count).
5. **Index-cap fallback named**: cap hit → planner falls back to original
   order, reported on output (no silent degradation).
6. **Window selection stated by the planner**; reduction re-measured at
   that window (not assumed from -md1g runs).
7. **Degenerate inputs**: 0-byte/tiny files yield 0/1 chunks — planner
   handles empty fingerprint sets.

The revised analysis becomes the v1.26 implementation plan; re-run
architect-challenge on it before M1.

## 6. Risks

- **R1 (kept from the register):** the reduction claim is corpus-dependent;
  the changelog must carry measured numbers, not ratios.
- **R2:** extraction-order change may surprise scripts that expect
  original order → the packing must be opt-in (a switch), never default.
- **R3:** solid runs make random-access repair harder (RR covers the run);
  `-rr` interaction needs the recovery tests re-run with CDC-packed sets.
