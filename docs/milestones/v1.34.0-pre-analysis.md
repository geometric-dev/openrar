# v1.34.0 Pre-Analysis — Extraction Throughput (Gate 0)

Arc hypothesis, as scoped by the roadmap: batched durability, pipelined
verification, and QO/scan wins make extraction faster inside the v1.24
contract. This document tests that scope against measurement before any
design work, because the first numbers re-assign the arc's center of gravity.

## 0. Gate 0 statement

Fresh measurement puts **84% of single-member extraction time in the
decode+verify pass** and at most 16% in writes and durability — and our
decode-only pass is slower than UnRAR's *entire* extraction. The roadmap's
three levers address the minority of the time. The arc's central question is
therefore re-scoped: can the decode path be made ~2x faster — by kernel work,
by intra-entry parallel decode, or both — inside the v1.24 contract, with
durability batching as the bounded secondary? Everything below is measured,
not inferred; the machine is the PERFORMANCE.md host (i7-7500U laptop, single
disk), OpenRAR v1.33.5 MSVC Release, UnRAR/WinRAR 7.20 as oracles.

## 1. Current state (verified against the tree, 2026-10-04)

### 1.1 Extraction baseline (64 MiB single-file archives, median of 3 timed runs, fresh output dirs)

| corpus | openrar x mt1 | openrar x mt8 | unrar x mt1 | unrar x mt8 |
|---|---|---|---|---|
| text (bench-vocab) | 0.939 s / 68 MB/s | 0.921 s / 70 | 0.530 s / 121 | 0.418 s / 153 |
| random (stored) | 0.338 s / 190 | 0.346 s / 185 | 0.172 s / 372 | 0.171 s / 374 |
| zeros | 0.239 s / 268 | 0.241 s / 266 | 0.252 s / 254 | 0.348 s / 184 |

Two readings survive every objection we could raise:

- **We are ~2x slower than UnRAR on real extraction** (text 68 vs 121-153
  MB/s) — and **2x slower on the STORED path** (190 vs 372 MB/s), where no
  decoding happens at all. The stored gap is write/durability/verification
  path cost, not decode.
- **`-mt8` does nothing for us on single members** (all three corpora within
  noise) while it buys UnRAR 1.27x on text. Our extraction parallelism is
  across-entries only (`main.cpp:643`, ReaderSlots + out-of-order decode with
  in-order console output); a single-member archive has nothing to
  parallelize.

### 1.2 Where the time goes (decode-only split via `openrar t`, which decodes and verifies but writes nothing)

| corpus | t (decode+verify) | x − t (write + durability) |
|---|---|---|
| text | 0.787 s (**84%** of x) | 0.152 s (16%) |
| random | 0.202 s | 0.136 s |
| zeros | 0.175 s | 0.064 s |

The headline: our **decode-only** text pass (0.787 s) is slower than UnRAR's
*complete* extraction (0.530 s). CRC at this scale is tens of milliseconds
(secondary). The dominant cost is the Huffman token loop.

### 1.3 Tree facts the designs stand on

- **The decompressor is scalar and sequential.** No SIMD anywhere in
  `decompressor50.cpp`; no intra-entry parallelism. (The compressor's match
  kernel has SIMD; the decoder has none.)
- **Durability is per-record and bounded.** The journal fsyncs each record
  before temp-file publication (`extraction_journal.cpp:280, 661`); the
  measured ceiling for any batching win is the `x − t` column: ~0.15 s worst
  case on this host.
- **The reference's intra-entry MT driver is documented black-box.** The
  v1.33 arc established the slot model from oracle experiments
  (`docs/question-log.md` Entry 8: pre-scanned block headers, per-slot
  private table state, round-robin batches of `2 x decoder_threads`, our
  shipped encoder-side seed rule) and the trailing-bits condition (Entry 23).
  Our decoder is sequential-only and **has never exercised a bit-7-clear
  block** — the v1.33 line's decoder-conformance residue.
- **Solid and multi-volume archives already refuse parallel extraction**
  (`entries_independently_decodable`, `main.cpp:726`); the v1.24 contract
  (journal ordering) and the Three-Phase pipeline are the frame any change
  must hold.

## 2. The central question — and why it is open

Does v1.34.0 follow the measurement or the roadmap? The durability/
verification levers are real but capped at ~16%. The measured majority lives
in two places the roadmap did not name: the scalar decode kernel (A) and the
absent intra-entry parallel decode (B). B has an unusual property: the
design work is half-done — the slot model our encoder ships is the
decoder-side model we never implemented, and building it closes the v1.33
line's conformance residue as a side effect. The open design question inside
B is the **window half**: the slot model answers how TABLE state replicates
across worker slots; it does not answer how a block's matches reference
window bytes that a neighbouring worker has not yet produced. That question
is this arc's first design task, and it is genuinely open.

## 4. Candidate designs, argued honestly

### A — Decode kernel (Tier 1, the biggest single lever)

Scalar Huffman loop at ~85 MB/s on text-like data. Candidates in order of
invasiveness: multi-symbol fast-path decode tables (decode N bits per
step instead of 1), branch-reduced length/distance staging, and — only if
the per-block table build stays cheap — SIMD-assisted decode (the repo has
GFNI experience from the RS16 kernel). Gate: the text corpus `t` time must
drop proportionally with byte-exact output and the full unit + interop gates
green; the hostile-table fuzz corpus is the guard, because decode-side
micro-optimization is exactly where bounds checks get lost.

### B — Intra-entry parallel decode via the documented slot model (Tier 1)

The reference's own architecture: pre-scan block headers, assign blocks to
worker slots with private table state, join output in member order. Payoff:
MT extraction on single members (UnRAR demonstrates 1.27x on text at
`-mt8`), and the decoder finally exercises bit-7-clear blocks, closing the
v1.33 conformance residue. The window half (§2) is unsolved here — a block's
matches reference window bytes a neighbouring worker may not have produced;
candidate answers (replay buffer per slot, dependency-ordered batch
assignment, window mirroring) each carry memory and ordering costs. Gate:
the full oracle matrix at `-mt1/2/4/8` including the heterogeneous and
slot-seeding fixtures from the v1.33 line, byte-exact everywhere, plus the
fuzz corpus on the new parallel paths.

### C — Batched durability (Tier 2, bounded)

`x − t ≈ 0.15 s` worst case (~16% of text extraction, ~40% of the stored
case). Fewer journal/temp syncs per entry batch without weakening the
ordering/journal guarantee. Any reordering of journal-vs-rename is an
explicit security-architecture decision with its own Gate 0
(PERFORMANCE.md's standing note), default-on only if the contract holds.
Worth doing after A/B re-baseline, since A/B shrink the denominator C
competes against.

### D — Pipelined verification (Tier 3)

CRC overlap with decode: secondary at this scale (tens of ms per 64 MiB).
Fold into A or B only if free; never its own work package.

### E — QO/scan wins (Tier 3, orthogonal)

Listing/open path, not bulk extraction; kept in v1.34.0 only if A or B land
early (the roadmap already says this about the RAR 7.x items).

## 5. Failure modes

1. **Decode kernel optimization loses a bounds check.** The decoder reads
   untrusted tables; a fast path that skips a Kraft/length validation is a
   security regression, not a perf one. The fuzz corpus and the hostile-table
   unit tests are the guard, run on every gate.
2. **MT decode mis-orders filter regions or solid chains.** Filters span
   blocks within a member and solid chains share one window in order; the
   slot model's per-block independence does not automatically extend to
   either. The first design task (§2's window half) must answer both before
   any code.
3. **Stale-binary measurement artifacts.** Documented twice in the v1.33
   line (`question-log.md` Entry 19, pre-analysis §10 methodology warning):
   every gate in this arc runs from a wiped build directory with the sanity
   gate, or it did not happen.

## 6. Risks

- **B is the biggest payoff and the biggest blast radius** (decoder core,
  parallelism, the filter/solid interactions). The slot-model documentation
  reduces the unknowns but does not answer the window half.
- **The durability contract is load-bearing** for the extraction journal's
  crash guarantees; C that quietly reorders it is a security bug wearing a
  perf costume.
- **Scope creep into v1.33's closed line**: the floor re-gate taught us
  gates must re-run on the shipping tree; any A/B claim against older
  measurements is suspect by construction.

## 7. What this arc deliberately does NOT do

- No weakening of the fsync contract without its own security Gate 0.
- No compression-side changes: the v1.33 line is closed (floor re-gate,
  Entry 23), and this arc reads its documentation but does not reopen it.
- No QO/scan work unless A or B lands early enough to leave room.
- No new archive-format surface of any kind.

## 8. Challenge invited on

1. **The A-vs-B ordering.** Kernel first helps every path (including any
   later MT driver, whose workers inherit the faster scalar base); MT driver
   first buys multi-core scaling immediately and closes the decoder
   conformance residue but parallelizes a slow kernel. The measurement
   (84% decode, 2x kernel gap) argues both matter; the order is a judgement
   call this document deliberately leaves open.
2. **Whether C is worth its Gate 0 at all** given its ~16% ceiling on this
   host — or whether it belongs in the release notes as "measured, bounded,
   declined for now".
3. **The window half of B** (§2): anyone with a cleaner answer than
   replay-buffers or dependency-ordered assignment should say so before this
   arc writes code.
