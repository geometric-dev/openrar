# v1.34.0 Implementation Record — Extraction Throughput

Status: **closed as a measured negative on decode micro-optimization, with
the big levers scoped.** Evidence base: `docs/v1.34.0-pre-analysis.md`
(Gate 0), the gprof profile of the decode-only path, and three controlled
measurement campaigns on the decode kernel. The shipped change is
documentation; the decoder is byte-identical to v1.33.5.

## 1. What the exploration established

gprof (gcc `-pg`, WSL leg, decode-only `t` on the 64 MiB bench-text corpus)
attributed ~58% of decode self-time to BitReader plumbing
(consume_bits 20.8%, peek_bits 15.1%, refill 9.4%, get_bits 7.6%,
bits_remaining 5.7% — the last called 34.7M times, once per token) against
9.4% for the Huffman decoder itself and 7.6% for copy_match. Token counts:
35.7M tokens at m1 (56% literals), 27.3M at m3; the literal path runs at
~3.2 ns/token (stored-corpus decode) while the blended text path runs at
~20 ns/token — match tokens carry the cost.

## 2. What was built and measured (all byte-exact, full suite green)

| variant | change | result vs v1.33.5 |
|---|---|---|
| M1-M3 left-aligned | shift-only accumulator (`acc >> (64-count)` peek, `acc <<= count` consume), fused `get_bits`, inline-in-header hot methods, `exhausted()`/`has_bits()` guards | **+9.8% slower** (paired-delta protocol, 12 pairs, 11/12 positive) |
| M3 guards-only | v1.33.5 arithmetic kept; fused/inline methods + `exhausted()`/`has_bits()` guards | min-statistic **neutral (−0.6%)**, median **+14% worse tail** |
| v1.33.5 (reverted) | unchanged | shipped |

**Conclusion: the v1.33.5 decoder is the local optimum for its structure on
MSVC.** The gprof attribution was inflated by `-pg` call instrumentation
(which also defeats inlining); MSVC's inlined right-aligned bit reader was
already tight, and the structural refactor either regressed (left-aligned)
or bought nothing measurable (guards-only). The ~1.7x kernel gap to UnRAR is
real but not reachable through call-pattern changes — it needs the deep
redesigns below, each its own arc.

## 3. Measurement protocols this arc established (mandatory for any future
decode kernel work)

This machine cannot resolve <10% decode deltas with naive wall-clock
medians. Three confounders were caught and controlled:

1. **Thermal bias against the second runner** — controlled by alternating
   pair order and using paired deltas (new − old within each back-to-back
   pair).
2. **Antivirus/first-run interference** — produced +1.4 s outliers on a
   freshly built exe (visible as extreme pairs); eliminated when real-time
   scanning was disabled for the session, and controlled generally by the
   min-statistic (least-interference principle) over 15+ interleaved runs.
3. **Incremental-link layout luck** — a fresh configure+build of identical
   source measured differently from an incrementally relinked binary; all
   A/B comparisons must use freshly built binaries from wiped configure
   directories.

Additionally: cross-session comparisons on this laptop moved a write-path
number by 24% with no code change — Gate-0 baselines are only comparable
within a session.

## 4. The levers not pulled (scoped for a future arc)

- **SIMD-assisted or flat-table decode.** A flat 15-bit table (32K entries x
  4 alphabets) eliminates the quick/slow branch but costs ~131K table writes
  per block build (measured build cost today: ~7 us/block; the flat table
  would add ~0.3-0.5 s per 64 MiB member) — viable only with lazy second-
  level pages or per-member table reuse. SIMD decode needs the GFNI-class
  kernel work the repo has precedent for (RS16) but is a security-sensitive
  surface (untrusted tables).
- **PCLMUL CRC.** crc32_step measured ~7.6% of decode (gcc attribution);
  a PCLMULQDQ folding kernel would cut most of it (~4-5% of decode, ~4% of
  extraction). Contained, self-checking, CPU-dispatch infrastructure exists.
- **Intra-entry parallel decode (B).** The slot model is documented
  black-box (question-log Entry 8) and the encoder ships its seed rule; the
  decoder-side driver would close the bit-7 conformance residue and unlock
  MT extraction on single members (UnRAR demonstrates 1.27x at -mt8). The
  open design question is the window half: a block's matches reference
  window bytes a neighbouring worker may not have produced. Candidate
  answers (per-slot replay buffers, dependency-ordered batch assignment,
  window mirroring) each carry memory and ordering costs; filters spanning
  blocks and solid-chain ordering must be answered in the same design.
- **Batched durability (C).** Ceiling measured at ~16% of text extraction
  (x − t); any journal/rename reordering is a security-architecture Gate 0
  of its own. Declined for v1.34.0 on cost/benefit.

## 5. Addendum — the remaining "predicted winners" audited (2026-10-04)

Two of the scoped levers in §4 dissolved on contact with the tree, which is
why this addendum exists:

- **PCLMUL CRC was already shipped.** `crc32_step` has dispatched to
  `arch::crc32_step_pclmul` (16-byte folding, tail-skip contract, scalar
  chaining) since the v1.30 line, with an ARM64 ACLE path alongside; MSVC
  x64 builds always compile it and the runtime gate is
  `get_cpu_features().pclmulqdq`. The ~7.6% gprof attribution measured in
  §1 is therefore the ALREADY-optimized floor, not headroom. §4's "PCLMUL
  CRC" bullet is withdrawn.
- **The stored-path 2x gap is the durability contract's price, not slack.**
  Per-entry file-mode extraction pays: a durable-first journal record
  (append + fsync BEFORE the temp exists, `extraction_journal.cpp:292,
  661`), a temp-file `flush()` before the commit rename (`:751`), and the
  rename itself — at least two FlushFileBuffers-class operations per entry,
  plus per-session journal creation syncs. UnRAR's 414-458 MB/s stored
  throughput (vs our 205) is achievable because it pays none of this — a
  black-box inference from throughput, consistent with its absence of any
  resume journal. Recovering the gap means weakening per-entry crash
  consistency (batching journal records, deferring temp syncs), which is a
  security-architecture Gate 0 of its own per the roadmap's standing note —
  and the measured ceiling remains the ~0.15 s per 67 MB that Gate 0
  already priced.

**Net: the only remaining extraction lever with real headroom is the
intra-entry parallel decode driver (B), with the window half as its open
design question. Everything else is measured, shipped, or contractual.**
