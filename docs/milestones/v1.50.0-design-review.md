## 1. Architectural Scrutiny

### 1.1 Correctness & Invariant Proof (Pillar 1)
- **Cut-Set Identity Invariant:** S-15 mathematically proved that restart halos of any fixed size (including 256 KiB `CDC_MAX_CHUNK`) suffer cut-lattice drift on periodic and constant data. The candidate-then-stitch design solves this completely by decoupling the parallel 64-byte rolling window evaluation from the sequential cut-decision phase.
- **Warmup Length:** The Gear hash state $h$ is 64 bits with an update rule of $h \leftarrow (h \ll 1) + T[b]$. The contribution of byte $b$ is shifted left by 1 for each subsequent byte, dropping out after 64 shifts. Thus, an overlap of exactly 63 predecessor bytes guarantees that the 64th byte produces the bit-exact rolling hash value of the sequential stream.

### 1.2 Resource Bounds & Memory Explosion (Pillar 2)
- **Candidate List Density:** On constant runs where every byte satisfies the mask, a naïve `vector<uint64>` would record 1 million entries for a 1 MB chunk, causing severe memory bloat and allocation thrashing.
- **Directive 1 (Interval Encoding):** Adjacent candidates must be coalesced into `(start_offset, count)` intervals. This reduces $O(N)$ candidate memory to $O(1)$ on constant runs.
- **Directive 2 (Hard Allocation Cap):** Slices must enforce a hard candidate ceiling of `slice_len / 1024`. On overflow, the slice falls back to sequential processing with a logged diagnostic (Invariant G-9).

### 1.3 State-Machine Singularity (Pillar 5)
- **Directive 3 (Single Cut Decision Source):** The cut-selection logic between strict/light/forced cuts must be factored so that sequential `CdcStreamChunker::feed` and the parallel stitcher share a single authoritative function or template. Having two parallel implementations is guaranteed to produce behavioral drift.
