## 1. Executive Summary & Problem Formulation

In OpenRAR v1.56.0 and v1.57.0, we introduced the cost-aware forward-arrival dynamic programming parser with terminal horizon padding ($H = 16$) and the fast uncontested literal bypass. These deliveries resolved the foundational ratio gap identified in census finding S-5 / RAT-D and elevated compression throughput by over $7\times$ on high-entropy data.

However, two critical capabilities remain unexploited in the match-finding and symbol-arbitration pipelines, directly addressed by Pillar 1 of the v2.0 Charter:

1. **Unconstrained Hash-Chain Traversal in Distant Bands:**
   In `Compressor50::find_match_impl`, hash-chain candidate traversal evaluates candidates deep into the chain even when their distance is orders of magnitude larger than a previously discovered close match. In RAR 5.0 Huffman coding, distant matches require up to 17 distance extra bits plus higher distance symbol costs. If a distant candidate cannot exceed the length of a closer candidate by enough bytes to offset this logarithmic distance penalty, performing expensive memory accesses, cache-line fetches, and SIMD byte scans is computationally wasted and can lead to emitting net-expanding matches.

2. **Omission of Slot 257 in Horizon Forward-Propagation ($i > 0$):**
   In `Compressor50::evaluate_forward_arrival`, token Slot 257 (repeat last length at distance `OldDist[0]`) is only considered at offset 0. At lookahead offsets $i \in [1, h_{eff}-1]$, even though the arrival state rigorously tracks `arrival[i].last_len` and `arrival[i].old_dist[0]`, the DP propagation loop evaluates only literals and general Rep0..3 codes. Because Slot 257 requires **zero length extra bits and zero distance extra bits** (it is a single Huffman symbol in the main alphabet), it is 5 to 8 bits cheaper than an equivalent Rep0 token. Missing this transition at $i > 0$ prevents the graph parser from discovering optimal multi-step repeated-length sequences.

v1.59.0 closes both gaps, delivering the final phase of **Pillar 1 of the v2.0 Charter**.

## 2. Technical Specifications

### Specification 1: Distance-Costed Hash-Chain Pruning (`find_match_impl`)

1. **Wire Admission Floor Pre-Screening:**
   In RAR 5.0, `length_increment(distance)` defines the distance band:
   - Band 0 ($D < 256$): $inc = 0$, minimum legal match length = 3
   - Band 1 ($256 \le D < 16\text{ KiB}$): $inc = 1$, minimum legal match length = 3
   - Band 2 ($16\text{ KiB} \le D < 256\text{ KiB}$): $inc = 2$, minimum legal match length = 4
   - Band 3 ($D \ge 256\text{ KiB}$): $inc = 3$, minimum legal match length = 5

   Before fetching buffer memory or executing `arch::match_length_simd`:
   ```cpp
   size_t cand_dist = static_cast<size_t>(pos - static_cast<core::uint64>(cand));
   core::uint32 inc = length_increment(cand_dist);
   size_t min_legal_len = static_cast<size_t>(inc) + 2;
   if (min_legal_len < min_match_) min_legal_len = min_match_;
   if (limit < min_legal_len) {
       cand = next_cand;
       continue;
   }
   ```

2. **Distance-Costed Length Hurdle:**
   When a closer match `best.length > 0` has already been recorded at distance $D_{best}$:
   Any subsequent candidate in the chain has $D_{cand} > D_{best}$.
   For $D_{cand}$ to be viable under distance symbol overhead, it must satisfy:
   $$req\_len = \max(best.length + 1, min\_legal\_len)$$
   If $inc(D_{cand}) > inc(D_{best})$, the candidate's distance band requires additional bits:
   $$req\_len = \max(req\_len, best.length + (inc(D_{cand}) - inc(D_{best})))$$
   If `limit < req_len` or `buf_cand[req_len - 1] != buf_pos[req_len - 1]`, skip immediately.

3. **Diminishing Returns Chain Termination:**
   When $best.length \ge 32$ and $D_{cand} > 1\text{ MiB}$ after having examined at least $\min(max\_chain / 2, 16)$ candidates, terminate the walk early. The probability of discovering a match that overcomes both $best.length$ and the 17-bit distance penalty is negligible.

### Specification 2: Optimal Rep-Code & Slot 257 Horizon Expansion (`evaluate_forward_arrival`)

In the forward propagation loop over horizon offsets $i \in [1, h_{eff}-1]$:
1. When evaluating rep candidates at offset $i$ for stream $r = 0$:
   If `!lastlen_suppressed_ && arrival[i].last_len >= min_match_` and `rep_len >= arrival[i].last_len`:
   Generate an arrival candidate for **Slot 257** (token_type 6):
   - Token length: $slen = arrival[i].last\_len$
   - Token distance: $0$
   - Cost: $arrival[i].cost + price\_slot257()$
   - Target offset: $j = \min(i + slen, h_{eff})$
2. If `new_cost < arrival[j].cost`:
   Store the candidate in `arrival[j]` with `token_type = 6`, `token_len = slen`, and preserve `arrival[j].last_len = slen`.

## 3. Governance, Invariants & Anti-Findings

- **Rule G-1 (Single Decision Function):** All parsing decisions continue to route through `Compressor50::evaluate_forward_arrival`.
- **Rule G-3 (Fingerprinted Measurement):** Throughput and compression ratios are measured against canonical benchmarks (`bench_target.exe`).
- **Rule G-8 (Charter Discipline):** Fulfills Pillar 1 of the normative v2.0 Charter.
- **Invariant I-2 (Bitstream Invariance / Reference Sync):** Any selection change updates canonical test digests in the same commit under `OPENRAR_REFCAP=1`.
- **Anti-Finding A-4 (Bounded DP):** Search horizon remains strictly capped at $H = 16$ bytes on a stack-allocated buffer (no dynamic memory allocations).
- **Anti-Finding A-5 (Wire Admission Floor):** Minimum legal length $min\_match\_ \ge 3$ and $len \ge inc + 2$ are strictly enforced.
