**Status:** pre-implementation analysis for the v1.27.0 arc, submitted for
architect-challenge (Gate 0 format-legality gate per docs/ROADMAP.md
§v1.27.0 and Guiding Principle 2: anything that changes emitted bytes is
reviewed against the RAR5 spec and the UnRAR oracle before implementation).

**Flagship claim under scrutiny:** POSIX/macOS extended attributes can be
carried in RAR5 archives as a NEW extra-record type without breaking any

## 1. What RAR5 legally allows (spec constraints, verified this session)

1. **Extra-record type numbering is verified against two public sources.**
   unrar `headers5.hpp` defines `FHEXTRA_CRYPT 0x01 … FHEXTRA_SUBDATA
   0x07` (`FHEXTRA_VERSION 0x04, FHEXTRA_REDIR 0x05, FHEXTRA_UOWNER 0x06,
   FHEXTRA_SUBDATA 0x07`), and bitplane/rar-research's RAR5 spec lists the
   same table with a file/service applicability matrix (0x04/0x05/0x06
   file-only, 0x07 service-only). **No type ≥ 0x08 is defined anywhere.**
   OpenRAR's `ExtraType` enum (src/format/headers.hpp:95) matches both
   sources exactly. → **0x08 is free.**
2. **Unknown record types must be skipped without error** (rar-research
   spec §5, verbatim). Skipping is a READER contract; preservation on
   re-write is a producer courtesy we cannot demand. Our interop claim is
   therefore bounded: *stock WinRAR/UnRAR list and extract archives
   containing the new record without error and byte-identical payloads.*
   OpenRAR's own verbatim-preservation mechanism (v1.24 unknown_extras:
   parse fallback header_reader.cpp:879, writer re-emit header_writer.cpp:393)
   is already proven by tests/unit/unknown_extras_tests.cpp.
3. **There is no RAR5 mechanism for extended attributes.** RAR 3.x carried
   OS/2 EAs as an `EA2` service header; RAR5 dropped it ("AV / EA2 were
   dropped" — rar-research §Service Header Names), and the spec says an
   encoder must not emit those service names. WinRAR's own RAR5 xattr
   story is: none (NTFS ACLs and ADS travel as `ACL`/`STM` child service
   headers, which carry raw blobs, not POSIX namespace attributes).
4. **The extra area lives inside the file header** (Header Size ≤ 2 MiB,
   3-byte vint). Any xattr payload is header payload — bounded by the
   same cap, and CRC-protected by the header CRC32 (no separate hash
   needed).
5. **Extra records are metadata-only** (v1.26 Gate 0 §1.3): the new record
   adds no data area, cannot express chunk references, and has zero
   interaction with solid chains (headers do not enter the LZ window).
   `-cdc`/`-oi`/`-s`/`-v` interactions are therefore none.
6. **WinRAR's actual MotW behavior (documented divergence, deliberate):**
   docs/spec/07-services.md records WinRAR's STM extraction algorithm:
   for an STM child named `:Zone.Identifier` WinRAR parses the
   archive-provided stream (≤ 16 MiB buffer), compares it with the host
   file's existing MotW, and writes it only if *more secure*. WinRAR
   therefore DOES trust zone content from inside the archive, gated by
   direction. SECURITY_ARCHITECTURE §4.3 is stricter and normative for
   OpenRAR: *never parse or trust zone/quarantine content from inside the
   archive*; zone data comes exclusively from the archive file's own
   filesystem metadata / transport context, with fresh content generated
   locally per extracted file. We accept the divergence (an
   attacker-supplied zone stream must never be written to disk, in either
   direction — the "more secure" gate still writes attacker-chosen
   content, including its HostUrl/ReferrerUrl strings, and creates a
   parsing surface). This is a documented, deliberate interop difference
   on a security boundary.

## 2. Candidate designs, argued honestly

### Design X-A — new extra-record type 0x08 `FHEXTRA_XATTR` (LEGAL, proposed)

Each file (and directory) header's extra area may carry one record:

```
Size      vint
Type      vint = 0x08
Flags     vint = 0        (reserved; nonzero → treat record as malformed)
Count     vint
per attribute:
  NameLen  vint  (1..255)
  Name     bytes  (UTF-8, full name INCLUDING namespace prefix, e.g. "user.foo",
                  "com.apple.metadata:_kMDItemUserTags")
  ValueLen vint  (0..65536)
  Value    bytes  (opaque — xattr values are byte blobs; no encoding, no NUL fixups)
```

- **Legality:** full. Unknown to every shipped RAR5 reader → skipped
  without error (contract 1.2). OpenRAR parses it (structured), re-emits
  it canonically, and its own mutation roundtrip stays byte-identical for
  well-formed records (same contract class as FHEXTRA_OWNER/HTIME).
- **Cost:** parser/writer branch + validation; io-layer xattr read/write
  per platform; capture/restore policy.
- **Risk:** none to readers; our own risk is malformed-record handling
  (→ §3 verdict: malformed ⇒ verbatim unknown capture, never abort, never
  misparse).

### Design X-B — xattrs as a new SERVICE header (e.g. "XATTR"), STM/ACL-style

A child service header per file with the blob in its data area and
per-attribute names in FHEXTRA_SUBDATA descriptors.

- **Legality:** technically legal (services are open-ended by usage
  convention) but strictly worse: adds a block per file (header overhead),
  introduces data-area/child ordering and solid-chain-adjacency questions
  the extra-record vehicle doesn't have, duplicates the
  FHEXTRA_SUBDATA-descriptor machinery for names, and differs from the
  one place RAR5 itself moved per-file metadata (EA2 → FHEXTRA_UOWNER
  extra record precedent: RARLAB moved ownership INTO the extra area).
  VERDICT: rejected — complexity without a gain; extra-record wins.

### Design X-C — smuggle xattrs through STM/ACL blobs (NOT CLEAN)

Encode POSIX xattrs as a fake stream name inside STM (e.g. `:user.xattr`).

- **Legality:** perversely legal (STM names are arbitrary) but it abuses
  the Windows-ADS semantics for non-ADS data, collides with real ADS
  names, and inherits the zone/ADS policy conflicts this arc exists to
  settle. VERDICT: rejected.

### Design Z-A — MotW from the archive file's own metadata only (§4.3, proposed)

At extraction, OpenRAR reads the **archive file's own** filesystem
metadata — Windows: the archive's `Zone.Identifier` ADS; macOS: the
archive's `com.apple.quarantine` xattr — takes only the zone/flag *value*
(provenance fact), and **generates fresh content locally** for each
extracted file: Windows writes `[ZoneTransfer]\r\nZoneId=<N>\r\n`
(standard IAttachmentExecute shape); macOS writes a freshly generated
`com.apple.quarantine` value (flag byte from the archive's xattr, fresh
timestamp + UUID + OpenRAR agent string). If the archive is unmarked,
nothing is written. **Nothing new is emitted into the archive** — zero
format impact, zero WinRAR impact (WinRAR/UnRAR simply do not implement
propagation; that is their gap, not ours).

### Design Z-B — WinRAR-style: store zone content in the archive, restore
if "more secure" (REJECTED by §4.3)

The shipped `-os` path today captures `Zone.Identifier` as an ordinary
STM child (win32_meta.cpp has no Zone filter) and `restore_children`
(cli/main.cpp:2335) writes STM children verbatim — **an archive-provided
zone stream lands on disk today**. This is exactly what §4.3 prohibits.
VERDICT: rejected as a design; the current behavior is a **policy
conflict this arc must close** (see §4 scope item 4): `-os` capture
excludes `:Zone.Identifier`, and extraction never writes any
`STM`/xattr-carried zone content regardless of producer.

### Design Z-C — store a per-file "was marked" flag bit in 0x08 (NOT BUILT)

An add-side hint so extraction "knows" the file was marked at pack time.

- **Legality:** legal. **Useless:** §4.3 forbids extraction-side marking
  decisions from archive-internal data (an attacker controls it in both
  directions, and the fail-safe direction — over-marking — invites
  SmartScreen-fatigue disabling). Zone provenance is a property of the
  ARCHIVE file's transport, not of member files. VERDICT: rejected —
  dead payload.

## 3. Gate 0 verdict (pre-challenge position)

- Design X-A survives (0x08 verified free; unknown-skip contract verified
  in two public sources); X-B and X-C rejected.
- Design Z-A is the only §4.3-conforming MotW design; Z-B is rejected and
  its shipped-code residue (Zone.Identifier via `-os`/STM) is closed in
  this arc. Z-C rejected.
- Emitted-bytes delta: one new extra-record type, opt-in via a new switch,
  skipped by every stock reader (spec contract). That is the entire
  format surface.

## 4. Proposed v1.27.0 scope (post-Gate-0, pending challenge)

1. **M1 — Format layer:** `FHEXTRA_XATTR = 0x08` model + parser + writer
   (one milestone, no drift window). Malformed/nonconforming records
   (flags≠0, name length 0/>255, value > 64 KiB, count/size overrun,
   duplicate names) fall back to verbatim unknown-extra capture — never
   abort the header, never misparse. Canonical re-serialization for
   well-formed records; unknown_extras tests extended.
2. **M2 — Capture side (`-ox`):** io-layer POSIX/macOS xattr reader
   (`flistxattr`/`getxattr`, `l`-variants only; Windows: none). Switch
   `-ox` = save extended attributes at add (files and dirs). Capture
   allow-list: `user.*`, `security.*`, `trusted.*`, `com.apple.metadata.*`
   (Finder tags ride here). Exclusions at capture (verbose report):
   `system.*` (POSIX ACLs stay with the `-ow` ACL path — no side door),
   `com.apple.quarantine`/`com.apple.provenance` (provenance — Design
   Z-A territory), `com.apple.ResourceFork`, `com.apple.FinderInfo`,
   `com.apple.decmpfs` (deferred to 2.1 with resource forks). Writer-side
   caps: value ≤ 64 KiB, name ≤ 255, total ≤ 1 MiB per file, count ≤
   4096 — over-cap attributes skipped with report, never truncated.
   Attributes sorted by name (deterministic bytes, Pillar 7.8). FILECOPY
   refs capture their own source's xattrs (mirrors times/owner handling;
   no inheritance ambiguity).
3. **M3 — Restore side:** xattrs applied to the committed file
   post-rename (mirrors the chmod/chown/STM pattern in restore_children),
   restore allow-list: `user.*` + `com.apple.metadata.*` always;
   `security.*`/`trusted.*` only with the new `--xattr-security` admin
   opt-in (the `--preserve-suid` model: default-deny + explicit opt-in +
   documented trust decision); everything else never restored. Per-
   attribute failure (EPERM/ENOTSUP/ENOSYS) → non-fatal warning +
   report; directory xattrs ride the deferred dir-meta path (bottom-up).
   `-oz`/`-ox`-less archives: zero behavior change.
4. **M4 — MotW `-oz` + zone-stream policy closure:** switch shape
   `-oz` / `-oz-` (model: `-ol`/`-ol-`). **Default ON** at extraction
   (fail-safe direction; WinRAR 6.23+ parity) — propagate MotW from the
   archive file's own metadata to extracted files per Design Z-A;
   `-oz-` disables. Provenance definition ("transport context"): the
   archive file's own Windows ADS / macOS quarantine xattr — nothing else
   (no path heuristics, no browser data). JSON flag `motw_propagated` +
   stderr line per file; archive ADS read once per session. Zone-stream
   closure: `-os` capture excludes `:Zone.Identifier`; extraction skips
   any zone-named STM child with `zone_stream_skipped` report + JSON
   flag (fail-safe against WinRAR-produced archives too). macOS
   quarantine propagation is compile-tested + unit-tested (value-format
   function); no Gatekeeper e2e claim. Windows-only ADS tests on the
   Windows leg; WSL leg covers the POSIX xattr surface.
5. **M5 — Rollover fixes + interop + docs:** FILECOPY caps debit (§0.2)
   + named test; `-oi3`/`-oi4` exit hygiene (§0.4); interop-gate Track 10
   (WinRAR/UnRAR read `-ox` archives — records skipped, payloads
   byte-identical; CI falls back to self-roundtrip); README `-ox`/`-oz`
   rows + "Not yet" row update; CHANGELOG; ROADMAP correction (§0.1).
6. **Release** — stamp 1.27.0 (MINOR), full preflight (Windows Debug
   ctest, WSL Release -Werror mirror, clang-format on touched files),
   release flow per v1.26.

**Named negative tests** (plan §-pattern; each lands with its milestone):
`xattr_roundtrip_self`, `xattr_malformed_captured_verbatim`,
`xattr_caps_enforced_store`, `xattr_hostile_record_no_alloc_beyond_caps`,
`xattr_system_namespace_never_captured`,
`xattr_security_namespace_not_restored_by_default`,
`zone_stream_never_restored` (crafted + WinRAR-shaped archives),
`os_excludes_zone_at_capture`, `motw_propagated_from_archive_ads`,
`motw_hosturl_never_copied` (archive ADS carries HostUrl/ReferrerUrl ⇒
extracted content is exactly `[ZoneTransfer]\r\nZoneId=N\r\n`),
`motw_disabled_by_flag`, `macos_quarantine_value_format` (macOS leg),
`filecopy_debits_caps`, `oi34_no_archive_no_dispatch`.

## 5. Answers to the open items (the brief's list, explicit)

- **Record type + layout:** 0x08 `FHEXTRA_XATTR`, layout in §2 X-A; flags
  reserved-0; opaque values; sorted names; caps §4.2.
- **`-oz` shape:** `-oz`/`-oz-`, extraction-side policy switch, default
  ON (fail-safe direction, WinRAR-parity), no add-side emission; `-ox`
  is the separate xattr save switch.
- **"Transport context":** the archive file's own filesystem metadata
  (Windows Zone.Identifier ADS; macOS com.apple.quarantine). Nothing
  else in v1.
- **Namespace scoping:** capture allow-list §4.2; restore allow-list
  §4.3 with `--xattr-security` opt-in for security.*/trusted.*; system.*
  never (ACL side door); provenance namespaces never.
- **macOS quarantine/Finder tags:** quarantine = provenance, never
  stored, propagated per Z-A; Finder tags = ordinary bytes under
  `com.apple.metadata.*`, stored/restored with `-ox`; resource forks +
  FinderInfo deferred to 2.1.
- **WinRAR interop story:** stock WinRAR/UnRAR skip 0x08 without error
  (spec contract, Track 10 pins it); OpenRAR preserves records verbatim
  across mutations (existing unknown_extras machinery + canonical
  re-serialization, pinned); MotW propagation is OpenRAR-only by design
  (WinRAR divergence documented §1.6).

## 6. Risks

- **R1:** the default-ON `-oz` is a behavior change (marked archives now
  mark extracted files) — the safe direction, WinRAR-parity, but scripts
  diffing extracted output ADS-bytes may notice; changelog states it.
- **R2:** xattr restore on foreign filesystems (FAT/exFAT/network mounts)
  fails per-attribute — non-fatal by design; must not degrade extraction
  status (entry still `extracted`).
- **R3:** `security.*` restore is a privilege escalation surface if
  mis-gated — the `--xattr-security` gate must be checked against the
  RECORD data only after the opt-in, and OS-level EPERM remains the
  final arbiter (fail-soft, reported).
- **R4:** 0x08 collision with a future WinRAR-defined type — mitigated by
  the reserved-flags-0 + strict validation (a foreign 0x08 with
  different semantics parses as malformed → verbatim, never misapplied).
- **R5:** platform divergence (WSL xattrs on DrvFs are partial) — tests
  probe-then-skip per the established environment-dependent pattern
  (Risk Register item 6).

## 7. Architect-Challenge Verdict (Gate 0 review, this commit)

🟡 CONDITIONAL APPROVAL — Design X-A and Z-A survive Gate 0; X-B, X-C,
Z-B, Z-C confirmed dead. The review VERIFIED this document's claims
against the code (`-z` swallows `-oz` via `sw_starts` at main.cpp:3245;
`debit_bytes` at archive_reader.cpp:275 vs the FILECOPY copy at 2532;
`is_prohibited_stream` has no Zone filter; `restore_children` is one
lambda shared by the sequential and parallel engines) and against both
public format sources. Ten directives applied to the implementation plan
before M1:

1. **Dispatch order:** `-oz`/`-oz-` and `-ox` (both verified free among
   `-o*` switches) register BEFORE the `-z`/`-ow`/`-os` prefix branches;
   both join the switch-parity test list.
2. **Zone-skip normalization:** the extraction-side skip matches
   case-insensitively AFTER `:$DATA`-suffix normalization of the SUBDATA
   name (hostile/foreign name variants must normalize to the same skip
   decision) — pinned by variant-named crafted children.
3. **Zone value contract:** parse only the archive's own ADS; malformed/
   out-of-range ZoneId → fail-safe 3; generated content is the pinned
   constant `[ZoneTransfer]\r\nZoneId=N\r\n`; never remove or downgrade
   an existing mark; unmarked archive ⇒ zero writes.
4. **Propagation scope:** files only (redirs excluded, FILECOPY-
   materialized files included); multi-volume probes volume 1 only; one
   ADS probe per session, cached.
5. **Redir metadata rule:** symlink/hardlink entries capture NO xattr
   records — an extracted hardlink IS the master's inode and already
   carries the master's xattrs; a record would re-apply onto shared
   inode state last-writer-wins. FILECOPY refs (separate inode at
   extraction) capture their own source's. Symlink capture itself is out
   of scope v1.
6. **Engine trace (Pillar 7.2):** xattr restore anchored in the shared
   `restore_children` lambda (sequential + parallel call sites) and dir
   xattrs in `apply_deferred_dir_metadata`; DLL/WASM apply surfaces
   explicitly out of scope v1 (consistent with STM/ACL); C ABI unchanged
   (no new exports; FileBlock is internal).
7. **Plan gates (Pillar 7.1):** the implementation plan carries the full
   Failure-Mode Matrix (format-parse / capture / restore / zone ×
   crafted / OOM-cap / privilege-denied / FS-without-xattr / cancel) and
   the named negative tests with their milestones; the hostile-record
   test runs under BOTH scan engines (io::ReadSource seam).
8. **Docs in-milestone:** README `-os` row amended (Zone.Identifier
   excluded by policy), `-ox`/`-oz` rows added, "Not yet" row updated;
   07-services.md gains the zone-policy note; `--xattr-security`
   documented as a trust decision (the `--preserve-suid` pattern);
   changelog carries the default-ON `-oz` behavior change.
9. **Malformed-record rule pinned:** any 0x08 validation failure →
   verbatim unknown-extra capture; never abort the header parse, never
   partially apply; duplicate names → malformed.
10. **Fail-soft policy both sides:** capture-side `trusted.*` reads fail
    EPERM unprivileged → per-attribute skip + report; restore-side
    EPERM/ENOTSUP → per-attribute warning, entry status unchanged.
