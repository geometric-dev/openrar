# v1.35.0 — RR probe record: RAR 7.20 inline recovery record (2026-10-04)

Black-box research record for the v1.35.0 "RAR 7.x parity" arc. Every claim
below is measured on this host against the installed oracles (Rar.exe 7.20
x64 console, UnRAR.exe 7.20, openrar 1.33.5 Release); nothing is inferred
from reference implementation source — clean room held throughout. Provenance
wording: "the reference writer/repairer" = the observed behavior of Rar.exe
7.20 on this host.

Tool: `tools/scan_rr.py` — CRC32-validated header walk (extends the
`scan_table_reuse.py` walk discipline with the header CRC32 check), `{RB}`
shard analyzer with CRC-64/XZ verification, generic unknown-layout prober,
and `--matrix` (RS writer-equivalence check). Corpus recipes in §8; artifacts
in `%TEMP%\opencode\rrprobe\` (ephemeral, deterministic payloads).

---

## 1. Headline result

**RAR 7.20's inline recovery record is the classic RAR5-era `{RB}` shard
scheme — byte-layout-identical to ours — in every probed configuration.**
The ROADMAP research state's premise ("WinRAR 7.0 changed the RR format, new
scheme default") is **not reproducible through the console oracle** and is
retired as the arc's driver (§6).

The RS core is not merely similar — it is **bit-identical** (§2): recomputing
the reference writer's stored parity from the archive's own protected range
with OUR Cauchy convention reproduces all 10 parity shards byte-for-byte.

## 2. Matrix + field equivalence: PROVEN

`tools/scan_rr.py --matrix` re-derives every shard's parity payload from the
protected range using our convention (`recovery_writer.cpp:108-114`):
Cauchy `MX[j][i] = inv((j+D) XOR i)` over GF(2^16) with polynomial 0x1100B,
`D` chunks of `group_count` bytes (final chunk zero-padded), consumed as u16
little-endian words.

Result on `r7_512k.rar` (reference writer, `-m0 -rr5`, 512 KiB random):
**shards 0..9 all BYTE-IDENTICAL**; same on our own archive (self-consistency
control). Proven equal, therefore: field polynomial, matrix form, orientation,
chunking, padding, and word order.

## 3. Wire-level deltas (shard header)

Shard layout constants are identical (magic `{RB}` = 7B 52 42 7D, CRC-64/XZ
at +0x04 over +0x0C..shard end — verified OK on every shard of every probed
archive, both writers; geometry fields at +0x0C..+0x3F; versions 1.1). Two
fields differ:

| Field | Ours | Reference 7.20 | Consequence |
|---|---|---|---|
| `chunk_data_extent` (+0x1E, u32) | 0 | final partial chunk length (e.g. 2259 for prot=524435, group=2624, D=200) | none: `t` ignores it (ours passes), `r` ignores it (expB, §5) |
| encoder-state region (+0x40..header_size, D·8+8 bytes) | zeros | populated blob | drives the reference repairer's behavior; see §5 |

Both fields are decoder-ignorable per our spec comment, and both experiments
confirm the reference *validator* ignores them.

## 4. Shared semantics confirmed

- **Protected range:** `protected_size` == file offset of the RR service
  header in BOTH writers (ours 524365 = RR@0x8004D; theirs 524435 =
  RR@0x80093). Parity covers archive bytes `[0, RR-header start)` —
  signature, main header, file headers, QO, file data.
- **Geometry formula:** D=200 for archives ≥ 200 KiB, `ceil(size/1024)`
  below (4 KiB → D=5); NR from percent (`-rr1` → NR=2, `-rr5` → NR=10,
  `-rr20` → NR=40, `-rr150` → NR=7 at D=5); `group_count` = even-rounded
  `ceil(prot/D)`. Matches our `compute_geometry` on every probe.
- **`.rev` containers** (multivolume `-rv5`): `Rar!\x1aRev` wrapper,
  version=1, DataCount=RecCount=5, RecNum=5, u32 RevCRC, per-volume
  u64 size + u32 CRC table, then the parity payload — structurally identical
  to our `write_rev_volumes` layout. Re-confirms the shipped `.rev` interop
  against 7.20.
- Probed configurations, all classic: 4 KiB / 512 KiB / 4 MiB; `-rr1`,
  `-rr5`, `-rr20`, `-rr150`; store and `-m5`; `-md1g`, `-md5g`; multi-file;
  all-zero payload. (The `MHFL_PROTECT` bit, locator `rr=` offset — which
  MATCHes the RR header position in every archive — and SubData percent vint
  all behave as our writer emits them.)

## 5. The shard-header state blob

Properties measured:

1. **Content-derived**: differs between archives with different payloads
   (same geometry).
2. **Parity-count-dependent**: differs between `-rr1` (NR=2) and `-rr5`
   (NR=10) over identical data — so it folds parity, not just data.
3. **Zero-preserving (linear)**: all-zero chunks fold to zero blob entries
   (`r7_zero`: blob[1..] all zero; blob[0] nonzero because chunk 0 contains
   the archive headers).
4. **Non-deterministic at the writer**: two RAR 7.20 runs over the same
   input and switches produce archives differing in exactly 160 bytes, all
   inside the RR data area, blob included. (WinRAR 7.30 beta's public
   changelog item "Same archive is produced for same data and options even
   if recovery record is included into archive" confirms this
   nondeterminism was later removed.) **There is no reproducible "correct"
   blob value for a third-party writer to emit.**

Causal role in the reference repairer (splice experiments on their own
archive, shard CRC-64s recomputed so `t` stays green):

- **expA** (blob zeroed, content pristine): `t` All OK; `r` reports
  phantom "176 blocks are recovered" (our archives: 175 — same class) and
  re-emits the record with the zero state preserved (linear re-fold).
- **expB** (`chunk_data_extent` zeroed, blob intact): `r` reports
  "0 blocks are recovered" — extent is irrelevant to the repair path.
- **Conclusion:** the reference `r` consumes the blob as per-chunk validity
  state. Real blob → repairs real damage byte-exactly (verified: a 1-byte
  flip and a 4096-byte wipe both reconstruct to sha256-identical pristines).
  Zero blob → it never touches data: damage survives the "repair" (our
  damaged archive came out with the flip intact, RR still valid, `t` still
  OK). The reference `t` command never consumes the blob — it validates our
  zero-blob records unconditionally.

**Consequence for us:** our zeros are the correct clean-room choice. The
`r`-path asymmetry is a property of the reference repairer w.r.t.
third-party records, not a defect in ours; our records are fully
self-consistent (§2) and every available validation oracle accepts them.

## 6. The "WinRAR 7.0 changed the RR format" premise — revised

- The 7.00 whatsnew entry (win-rar.com, fetched 2026-10-04) contains no RR
  format change; `Rar.txt` documents no legacy/new-format switch; and no
  probed trigger (dictionary size up to `-md5g`, RR up to 150%, volumes,
  multi-file, method, payload) produces anything but the classic scheme
  through the console writer.
- The claim's origin (a GUI-side default or a trigger outside the console
  oracle's surface) remains a **known-unknown**: WinRAR.exe (GUI) is not
  installed on this host, so a GUI-only default cannot be probed here.
- **Bookkeeping correction:** 0x11D is the GF(256) polynomial of the
  RAR4-era scheme. The RAR5-era inline `{RB}` record — including RAR 7.20's
  output — is GF(2^16) 0x1100B (§2). The v1.26 ledger's "RR vintage 0x11D"
  framing presumed a 7.x GF(256) scheme; no such scheme is observable in
  7.20 console output. README's Not-yet row is corrected in this commit.
- **Net for v1.35.0:** "RAR 7.x RR parity" as a wire-format gap is closed to
  the depth the available oracles can see. The real, measured gaps are
  reader-side (§7).

## 7. Measured gap in OUR repairer: single-erasure only

`RecoveryWriter::repair` on the inline-RR path:

| damage | result |
|---|---|
| 1 byte flipped (1 group) | repaired byte-exact to pristine (sha256 match) — both producers |
| 2 bytes in one group | refused ("damage exceeds parity...") — FAIL |
| 1 byte in each of 2 groups | refused — FAIL |
| 1 byte in each of 3 groups | refused — FAIL |

The boundary is exactly **one damaged unit** — the "Tier 1 Guaranteed:
uniquely identified single corrupted shard" scope documented at
`recovery_writer.cpp:1962` (the v1.26 ledger's deferred "single-erasure
repair" item, now measured). NR=10 parity supports up to 10 erasures in
theory; our decode path uses one. **This is the actionable v1.35.0 reader
item: multi-erasure repair.** No wire change is involved.

## 8. Interop matrix (behavioral summary)

| test | result |
|---|---|
| Rar 7.20 `t` on our `-rr5` archive | All OK, "Testing the recovery record OK" |
| UnRAR 7.20 `t` on our `-rr5` archive | All OK |
| openrar `t` on all reference archives | OK |
| openrar `r` on reference archive, 1 byte flipped | repaired byte-exact (sha256 ≡ pristine) |
| openrar `r`, multi-erasure | refused (§7) |
| Rar 7.20 `r`, its own archive, 1 byte / 4096-byte damage | detects the damaged RS groups (reports group-start offsets; 2624-byte group grid) and repairs byte-exact |
| Rar 7.20 `r`, our archives (zero blob) | phantom "175 blocks recovered" on pristine; damage NOT repaired; record re-emitted valid; `t` stays OK (§5) |
| Rar 7.20 `r`, reference archive with spliced zero blob | phantom reproduced → blob is the cause (expA) |
| RAR 7.20 writer determinism | non-deterministic in the RR blob (§5.4) |

Note: the reference `r` writes `fixed.*` / `rebuilt.*` into the **current
working directory**, not the archive's directory, then renames on success —
scripted probes must collect artifacts from the CWD.

## 9. Scoped v1.35.0 follow-ups

1. **Multi-erasure repair (reader)** — the real gap. Extend the inline-RR
   decode path from one erasure to `min(NR, damaged)` erasures per record
   (the RS16 decode matrix already supports it; the damage scan and the
   Tier-1 single-shard assumption at `recovery_writer.cpp:1962` are what
   bound it). Needs its own failure-mode matrix: which units are erasures
   (words vs groups), hostile damage patterns, CRC-64-valid but
   inconsistent records.
2. **No emission change proposed.** `chunk_data_extent` and the state blob
   are decoder-ignored, the reference blob is non-reproducible even by its
   own writer (§5.4), and byte-identity with the reference RR section is
   therefore unattainable and unnecessary. Emitting zeros stays.
3. **Resource forks / FinderInfo** via the xattr allow-list extension —
   unchanged from the ROADMAP scoping (macOS-only predicate, unit-testable
   everywhere).
4. Optional regression test to pin §2/§7: craft the probe corpus recipe in
   the test suite (our writer + our repairer; reference-behavior assertions
   stay oracle-gated, not CI-gated).

