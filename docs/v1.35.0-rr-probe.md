# v1.35.0 — RR probe record: RAR 7.20 inline recovery record (2026-10-04)

Black-box research record for the v1.35.0 "RAR 7.x parity" arc. Every claim
below is measured on this host against the installed oracles (Rar.exe 7.20
x64 console, UnRAR.exe 7.20, openrar 1.33.5 Release); nothing is inferred
from reference implementation source — clean room held throughout. Provenance
wording: "the reference writer/repairer" = the observed behavior of Rar.exe
7.20 on this host.

**Verification (same day).** The record was independently reviewed against
outside format analysis. Three corrections were demanded and applied after
re-verification against the measured wire data: the NR rounding is floor,
not ceil (§4); the shard-header state blob is per-data-chunk raw CRC-64
values plus one per-run random seed — not an opaque fold (§5), which also
refutes an earlier "parity-count-dependent" reading as seed-confounded; and
a second wire shape exists above D·64 KiB protected size that the original
4 MiB corpus never reached (§6), where our repairer refuses reference
records (§8). The review's predictions that were testable without source —
raw-CRC-64 entry values, seed-excluded NR-independence, the 160-byte
run-delta decomposition, scale>1 physical chunk-sharding — all matched the
wire byte-for-byte.

Tool: `tools/scan_rr.py` — CRC32-validated header walk (extends the
`scan_table_reuse.py` walk discipline with the header CRC32 check), `{RB}`
shard analyzer with CRC-64/XZ verification and shape classification
(`single` / `single-scaled` / `multi-piece`), generic unknown-layout prober,
and `--matrix` (RS writer-equivalence check). Corpus recipes in §11;
artifacts in `%TEMP%\opencode\rrprobe\` (ephemeral, deterministic payloads).

---

## 1. Headline result

**RAR 7.20's inline recovery record is the classic RAR5-era `{RB}` shard
scheme — byte-layout-identical to ours — in every probed configuration.**
The ROADMAP research state's premise ("WinRAR 7.0 changed the RR format, new
scheme default") is **not reproducible through the console oracle** and is
retired as the arc's driver (§7).

The RS core is not merely similar — it is **bit-identical** (§2): recomputing
the reference writer's stored parity from the archive's own protected range
with OUR Cauchy convention reproduces every parity shard byte-for-byte, at
scale 1 and at scale>1 (§6).

## 2. Matrix + field equivalence: PROVEN

`tools/scan_rr.py --matrix` re-derives every shard's parity payload from the
protected range using our convention (`recovery_writer.cpp:108-114`):
Cauchy `MX[j][i] = inv((j+D) XOR i)` over GF(2^16) with polynomial 0x1100B,
`D` chunks of `group_count` bytes (final chunk zero-padded), consumed as u16
little-endian words.

Results: `r7_512k.rar` (reference writer, `-m0 -rr5`, 512 KiB random) —
shards 0..9 all BYTE-IDENTICAL; our own archive passes as a
self-consistency control; and at 16 MiB (§6) the reference's logical parity
shards — reassembled from its 64 KiB physical pieces in `chunk_position`
order — are BYTE-IDENTICAL under the same whole-group fold (all 10 logical
shards). Byte-exact reproduction of a linear map over GF(2) pins the field,
matrix, orientation, chunking, padding, and word order simultaneously.

## 3. Wire-level deltas (shard header)

Shard layout constants are identical (magic `{RB}` = 7B 52 42 7D, CRC-64/XZ
at +0x04 over +0x0C..shard end — verified OK on every shard of every probed
archive, both writers; geometry fields at +0x0C..+0x3F; versions 1.1).
Three field-level observations:

| Field | Ours | Reference 7.20 | Consequence |
|---|---|---|---|
| `chunk_data_extent` (+0x1E, u32) | 0 | unpadded byte count of the final data chunk (2259 at prot=524435; 2587 for our o_512k geometry) | none observed: `t` ignores it, `r` ignores it (§5, expB) |
| encoder-state region (+0x40..header_size, D·8+8 bytes) | zeros | D per-chunk CRC-64 values + one random seed (§5) | drives the reference repairer's erasure localization; see §5/§8 |
| shard packaging above D·64 KiB protected size | one physical shard, scaled header | multiple physical chunk-shards, unscaled headers (§6) | `t`-level interop both ways; our REPAIRER refuses the reference shape (§8) |

## 4. Shared semantics confirmed

- **Protected range:** `protected_size` == file offset of the RR service
  header in BOTH writers (ours 524365 = RR@0x8004D; theirs 524435 =
  RR@0x80093). Parity covers archive bytes `[0, RR-header start)` —
  signature, main header, file headers, QO, file data.
- **Geometry formula:** D = 200 when protected size ≥ 200 KiB, else
  clamp(ceil(size/1024), 1, 200); **NR = floor(2·pct·D / 200) = floor(pct·D/100),
  capped at 10·D** (NR floor of 1 on the small-archive branch) — floor, not
  ceil: the measured `-rr150` tiny case yields NR=7 (7.5 floored), and our
  `compute_geometry` already implements exactly this integer floor;
  `group_count` = even-rounded `ceil(prot/D)`; `shard_size` =
  `header_size + group_count`. Matches on: 4 KiB (D=5, NR=1 at 5%),
  512 KiB (D=200; NR=10 at 5%, NR=2 at 1%, NR=40 at 20%), 4 MiB (NR=10),
  150% on tiny (NR=7), 16 MiB (NR=10, group=83888).
- **`.rev` containers** (multivolume `-rv5`): `Rar!\x1aRev` wrapper,
  version=1, DataCount=RecCount=5, RecNum=5, u32 RevCRC, per-volume
  u64 size + u32 CRC table, then the parity payload — structurally identical
  to our `write_rev_volumes` layout. Re-confirms the shipped `.rev` interop
  against 7.20. (`.rev` parity bytes themselves were not cross-verified;
  structure only.)
- Probed configurations, all classic: 4 KiB / 512 KiB / 4 MiB / 16 MiB;
  `-rr1`, `-rr5`, `-rr20`, `-rr150`; store and `-m5`; `-md1g`, `-md5g`;
  multi-file; all-zero payload. (`MHFL_PROTECT`, the locator `rr=` offset —
  which MATCHes the RR header position in every archive — and the SubData
  percent vint all behave as our writer emits them.)

## 5. The shard-header state blob — identified

The D·8+8-byte region at +0x40 consists of **D per-data-chunk CRC-64 values
followed by one 8-byte per-run random seed**:

- Entry k (0-based) = raw CRC-64 of data chunk k's bytes — **init 0, no
  final XOR** (nonstandard, and the reason it is zero-preserving) — over the
  chunk's *unpadded* length (the tail chunk's entry matches its 2259-byte
  unpadded form, not the zero-padded group). Verified byte-exact on five
  entries of `r7_512k` plus the all-zero-payload control (`r7_zero`: chunks
  1..198 fold to 0; chunk 0, which contains the archive headers, matches
  its raw CRC-64).
- Entry D (the trailing u64) is a per-run random value: two RAR 7.20 runs
  over identical input produce archives differing in exactly 160 bytes =
  10 shards × (8-byte seed + the 8-byte shard CRC-64 that covers it). All
  other bytes, including every data-derived entry, are identical. (Public
  WinRAR 7.30 beta changelog: "Same archive is produced for same data and
  options even if recovery record is included into archive" — the same
  nondeterminism, later removed.)
- The entries are NR-independent: `-rr1` and `-rr5` over identical data
  carry identical entry sets once the trailing seed is excluded.

Causal role, established by splice experiments on the reference's own
archive (shard CRC-64s recomputed so `t` stays green):

- **expA** (blob zeroed, content pristine): `t` All OK; `r` reports
  phantom "176 blocks are recovered" (our archives: 175 — same class) and
  re-emits the record with the zero state preserved.
- **expB** (`chunk_data_extent` zeroed, blob intact): `r` reports
  "0 blocks are recovered" — extent is irrelevant to the repair path.
- **expC, the positive direction (the decisive one):** splicing REAL
  per-chunk entries (raw CRC-64 as above) plus a **zero seed** into OUR
  `o_512k` archive: `t` All OK; `r` on the pristine spliced archive reports
  **"0 blocks are recovered"** — the phantom is gone; and `r` on the spliced
  archive with a real 1-byte flip detects the damaged group (group 99 start
  = 0x3F5FA exactly) and **repairs the data byte-exact** (extracted file
  sha256 ≡ original; the only archive-level delta is a 5-byte end-header
  rewrite by the reference's structure-reconstruction stage).

**Consequences:** (1) the reference repairer uses the entries as an
erasure locator — per-chunk checksums marking damaged chunks before matrix
reconstruction — which explains every `r` observation in one model; (2) a
third-party writer CAN emit a fully functional blob: real entries are a
pure, deterministic function of the archive bytes, and the seed is ignored
by the validator and can be fixed at zero — making the record deterministic
and clean-room reproducible (§10, candidate E1); (3) our current zeros are
accepted by every validation oracle but leave the reference repairer
without localization (phantom accounting, no actual repair of damage).

## 6. Scale>1 wire shapes (protected size > D × 64 KiB ≈ 12.8 MiB)

At 16 MiB protected size the two writers produce **different physical
packaging of the same logical record**:

- **Reference:** each logical parity shard is split into multiple PHYSICAL
  chunk-shards — 20 physical for 10 logical at 16 MiB — each with an
  UNSCALED `D·8+0x48` header (0x688), `chunk_position` advancing in 64 KiB
  steps (0, 65536), the logical `group_count`/`shard_size` repeated in every
  physical header, and a payload of `min(64 KiB, group − chunk_position)`
  bytes.
- **Ours:** one physical shard per logical index with a SCALED header
  (`(D·8+0x48)·scale` = 0xD10 at scale 2) and the full `group_count` payload.

Measured at 16 MiB: **`t` passes both ways** (the reference validator accepts
our scaled single-shard shape; our reader accepts the multi-physical chain);
the reference `r` repairs its own damaged 16 MiB archive byte-exact
(accounting shown as "relocated"); and the parity math remains equivalent —
our whole-group fold reproduces the reassembled logical shards
byte-identically (§2). The difference is packaging, not coding.

## 7. The "WinRAR 7.0 changed the RR format" premise — revised

- The 7.00 whatsnew entry (win-rar.com, fetched 2026-10-04) contains no RR
  format change; `Rar.txt` documents no legacy/new-format switch; and no
  probed trigger (dictionary size up to `-md5g`, RR up to 150%, volumes,
  multi-file, method, payload, archive size up to 16 MiB) produces anything
  but the classic scheme through the console writer.
- The claim's origin (a GUI-side default or a trigger outside the console
  oracle's surface) remains a **known-unknown**: WinRAR.exe (GUI) is not
  installed on this host, so a GUI-only default cannot be probed here.
- **Bookkeeping correction:** 0x11D is the GF(256) polynomial of the
  RAR4-era scheme. The RAR5-era inline `{RB}` record — including RAR 7.20's
  output — is GF(2^16) 0x1100B (§2). The v1.26 ledger's "RR vintage 0x11D"
  framing presumed a 7.x GF(256) scheme; no such scheme is observable in
  7.20 console output. README's Not-yet row is corrected in this commit.
- **Net for v1.35.0:** "RAR 7.x RR parity" as a wire-format gap is closed to
  the depth the available oracles can see. The real, measured gaps are
  reader-side (§8).

## 8. Measured gaps in OUR repairer

Two, both reader-side, no wire-format obstacle:

1. **Single-erasure only.** `RecoveryWriter::repair` on the inline path:

   | damage | result |
   |---|---|
   | 1 byte flipped (1 group) | repaired byte-exact to pristine (sha256 match) — both producers |
   | 2 bytes in one group | refused ("damage exceeds parity...") — FAIL |
   | 1 byte in each of 2 groups | refused — FAIL |
   | 1 byte in each of 3 groups | refused — FAIL |

   The boundary is exactly **one damaged unit** — the "Tier 1 Guaranteed:
   uniquely identified single corrupted shard" scope at
   `recovery_writer.cpp:1962` (the v1.26 ledger's deferred item, now
   measured). The correct target for the upgrade is **chunk-granularity
   erasure decoding**: the code is MDS (Cauchy matrices are totally
   nonsingular), so any E ≤ NR damaged CHUNKS with known positions are
   recoverable by selecting E valid parity rows, building the E×E subsystem
   over the erasure columns, and inverting — no pattern exclusions. The
   current single-erasure syndrome-ratio localization does not generalize to
   E ≥ 2; the binding constraint with our zeroed blob is **localization**,
   not capacity (§10, candidate E1 ties the two together).

2. **Scale>1 record shape refused.** Our repairer consumes one physical
   shard per logical index; on the reference's multi-physical 16 MiB record
   it fails with "no usable recovery data..." (and our own 16 MiB scaled
   shape repairs fine, byte-exact). Reassembly per logical shard in
   `chunk_position` order is the missing piece.

## 10. Scoped v1.35.0 follow-ups

1. **E1 — emit the state blob (writer + reader, Gate 0 required).** Emit
   real per-chunk entries (raw CRC-64, init 0, no final XOR, unpadded tail)
   plus a fixed zero seed, and populate `chunk_data_extent`. Deterministic,
   clean-room reproducible, changes emitted bytes (interop gate + goldens
   re-baseline apply). Behaviorally proven to restore full reference-repairer
   functionality on our records (§5, expC). Also gives OUR repairer native
   erasure localization, which unlocks 2 below without archive-level
   candidate search. Note our `compute_geometry` has a `scale` concept
   (scaled header) that the reference expresses by physical chunk-sharding —
   E1 should decide whether to also switch packaging (see 3).
2. **E2 — multi-erasure repair (reader).** Chunk-granularity erasure decode
   for any E ≤ NR damaged chunks with known positions (§8.1). With E1
   landed, positions come from the entries; without it, they need
   archive-level CRC-validated candidate search (fragile — E1 first is the
   cleaner sequencing).
3. **E3 — multi-physical record support (reader, and writer-packaging
   decision).** Reassemble reference-style chunked records per logical
   shard in `chunk_position` order in the repair path (and confirm the
   extraction-adjacent paths that already accept them). Decide whether our
   writer also switches to the reference's physical chunk-shard packaging
   for scale>1 — current scaled-single shape is `t`-interoperable, so this
   is a fidelity/robustness choice, not a correctness gap.
4. **Resource forks / FinderInfo** via the xattr allow-list extension —
   unchanged from the ROADMAP scoping (macOS-only predicate, unit-testable
   everywhere).
5. Optional CI pinning: a CRC-64/XZ known-answer vector against a real
   shard image, so the checksum parametrization is locked rather than
   oracle-gated.

## 11. Reproduction

```
# corpus (deterministic payloads, seed 0x11D)
python - <<'PY'   # ftiny.bin 4 KiB, f512k.bin 512 KiB, f4m.bin 4 MiB,
PY                # f16m.bin 16 MiB, zero512k.bin
openrar a -m0 -rr5 o_512k.rar f512k.bin
"/c/Program Files/WinRAR/Rar.exe" a -m0 -rr5 r7_512k.rar f512k.bin   # etc.

# walk + shard CRC-64 verification + shape classification
python tools/scan_rr.py *.rar
# RS writer-equivalence proof (single-shape records)
python tools/scan_rr.py --matrix r7_512k.rar o_512k.rar
```

Splice experiments (§5): zero or fill the blob region
`[shard+0x40, shard+header_size)` across shards (entries = raw CRC-64,
init 0 / no final XOR, of each chunk's unpadded bytes; trailing u64 = seed),
recompute each shard's CRC-64/XZ over `[+0x0C, shard end)`, re-run
`Rar.exe t` / `r -y` from the directory that should receive `fixed.*`.
